# 2026-11-15 W5: MCP 표면 (inbox, mcp-server, tests/e2e/mcp)

작업 묶음 W5([구현 계획](../../docs/design/implementation-plan.md#3-작업-묶음))의 실행 기록이다. 수신함과 전달 모드, 환경 변수 해석, tool 14개, instructions, 채널 알림, 확인 기록 파일, stdio 수명을 만들고 검증했다.

- 작업 ID: `2026-11-15-w5`
- 대상: `src/inbox/**`, `src/mcp-server/**` (각 `contract.ts` 제외), `tests/e2e/mcp/**`
- 기준 상태: 브랜치 `main`, 커밋 `a82ed0e` + 커밋하지 않은 작업 트리(W0 의 계약 골격과, 같은 시간에 다른 묶음이 쓰고 있던 파일). 이 묶음이 고친 것은 위 대상 파일뿐이다.
- 환경: macOS 27.2.1 arm64 한 대, Node v26.12.1, npm 11.20.0, `@modelcontextprotocol/sdk` 1.32.2, `zod` 4.6.7, `typescript` 7.0.2.
- 빌드와 실행: 묶음별 출력 폴더를 썼다. `npx tsc -p tsconfig.json --outDir .work/w5/dist`, 프로세스를 띄우는 시험은 `AGENT_CHAT_DIST=.work/w5/dist`. 공용 `dist` 와 `npm test` 는 쓰지 않았다.
- 검증 수준:
  - **대역**: `src/inbox`, `src/mcp-server` 의 단위 시험. 가짜 시계, 가짜 채널 전송 함수, 가짜 세션, SDK 의 메모리 전송, 가짜 스트림을 썼다. `channel-check.json` 시험만 실제 파일 시스템(임시 폴더)에 쓴다.
  - **로컬 실물**: `tests/e2e/mcp`. 제품의 `mcp-server`·`inbox` 가 실제 프로세스, 실제 stdio 파이프, 실제 타이머, 실제 신호에서 돈다. 호스트는 MCP SDK 클라이언트(또는 줄 단위 JSON-RPC)다. **세션은 가짜다**(`tests/e2e/mcp/fake-session.mjs`). 방 기능(시그널링, WebRTC, 공유 상태)과 실제 호스트(Claude Code, Codex)의 증거가 아니다.
  - **실제 환경**: 없음. 실제 호스트 세션은 띄우지 않았다(사람의 승인과 모델 호출이 필요하다).
- 참고한 이전 이력:
  - `2026-11-15-pre-implementation-assumptions`: PRE-MCP-03(고수준 `McpServer` + `mcp.server.notification`), PRE-MCP-04(취소된 요청에는 응답이 가지 않는다 → 취소 시 커서를 옮기지 않는다), PRE-MCP-05(SDK 클라이언트 기본 기한 60초), PRE-MCP-06(stdout 오염), PRE-MCP-07·09~11(stdin 종료, 부모 SIGKILL, stderr EPIPE), PRE-CH-07(meta 키 정규식), PRE-CH-10(SDK 1.32.2 는 2026-07-28 을 지원하지 않는다). 반영: 같은 방식으로 만들었고, 탐색 코드가 아닌 제품 코드로 같은 동작을 다시 봤다(아래 L-W5 실행).
  - `2026-11-15-w0-contracts`: 묶음별 출력 폴더와 `AGENT_CHAT_DIST`(W0-17), `tests/support/proc.mjs`(W0-12 등)를 그대로 썼다. `Subscribable` 적합성 시험(`protocol/testing.ts`)을 `inbox` 의 두 이벤트에 돌렸다.
  - `2026-11-15-design-review`: 문서 검토 기록이라 실행 조건에는 쓰지 않았다.
- 원문 증거: 명령 출력과 실험 스크립트는 세션 임시 폴더(`<scratch>` = 세션 임시 폴더의 `impl/w5/`)에 있었고 보존 대상이 아니다. 재현에 필요한 명령·조건·판정은 이 문서에 적었다. 요약에 채팅 본문, 방 ID, 토큰을 싣지 않았다.
- 실행 ID 접두어: `U-`(대역), `L-`(로컬 실물), `M-`(시험이 변이를 잡는지 본 것. 대역·로컬 실물의 보조).

| stdin 종료(SDK 클라이언트의 `close()`) 뒤 프로세스 종료 | 4~6ms | 400ms 이하 |
| `SIGINT` → 100ms → `SIGTERM`, 가짜 세션의 종료가 200ms 걸릴 때 | 207~210ms, 종료 코드 0, `shutdown` 사건 1건(원인 `SIGINT`) | 400ms 이하 |
| 가짜 세션의 종료가 끝나지 않을 때(예산 초과) | `closed` 까지 401~402ms(`forced: true`), 프로세스 종료까지 405~411ms, 종료 코드 0 | 예산(400ms)에 기다리기를 그만둔다. 호스트의 SIGKILL(SIGINT 뒤 500ms)보다 먼저 끝난다. **이 경로의 프로세스 종료는 400ms 를 넘는다**(예산이 찬 뒤에 끝내므로) |
| stdout 이 깨진 뒤(읽는 쪽을 닫음) | `shutdown{cause: stdout_error}`, `closed` 까지 0ms, 종료 코드 0, stderr 빈 문자열 | 잡히지 않은 예외 없이 끝난다 |
| 부모(SDK 클라이언트 프로세스) SIGKILL 뒤 MCP 프로세스 종료 | 4~5ms, 원인 `stdin_end` | 1초 안, 고아 없음 |
| 5000바이트 글 12건을 이어 받기 | 결과마다 사건 4건, 사건의 합 20596~20599바이트, 결과 전체 20675~20762바이트 | 사건의 합 24000바이트 이하 |
| `peer-script big 24000` (20건) | 결과 전체 24083바이트 | 사건의 합 24000바이트 이하. **결과 전체는 봉투만큼 24000 을 넘을 수 있다** |
| 사건 하나가 상한보다 큼 | 결과 전체 28236~28318바이트, 사건 1건, `more: true` | 그것 하나만 준다 |
| 다른 프로세스가 글을 넣은 뒤 채널 알림 도착 | 147~148ms(명령 실행과 50ms 주기의 조종 폴더 읽기 포함) | 기록만 |

## 관찰

- **결과 크기의 정의.** `WAIT_MAX_RESULT_BYTES` 는 계약(`inbox/contract.ts`)대로 "cursor 를 붙인 사건의 JSON 길이의 합"으로 쟀다. tool 결과의 텍스트 전체는 봉투(`ok`, `status`, `next_cursor`, `more`, `hint`, `notice`, 쉼표)만큼 더 크다. 20건을 꽉 채우면 24083바이트였다. `A-MCP-9` 를 볼 때 이 차이를 함께 본다.
- **예산 초과 경로의 종료 시각.** 세션 종료가 끝나지 않으면 `closed` 가 예산(400ms)에 resolve 하고, 프로세스는 그 뒤에 끝난다(405~411ms). 정상 경로는 3~6ms 였다.
- **`node --test` 는 끝나지 않는 대기에서 스스로 멈추지 않았다.** 가짜 시계 위의 대기가 풀리지 않으면 시험 프로세스가 2분 넘게 남았다(M-W5-01). 그래서 "기다리지 않는다"를 보는 시험은 기한 0 이나 틱 상한으로 바로 실패하게 했다.
- **SDK 클라이언트는 stdout 의 JSON 이 아닌 줄마다 `onerror` 를 부른다**(PRE-MCP-06 과 같다). e2e 는 이것이 0건인지와, 줄 단위로 읽은 stdout 이 모두 JSON-RPC 인지를 함께 본다.
- 입력 형식 오류의 결과는 SDK 가 만든다. JSON 이 아니라 `MCP error -32602: Input validation error: …` 글이다([mcp-interface.md 2절](../../docs/design/mcp-interface.md#2-공통-규칙)이 적은 대로다). 그 글에 받은 값은 실리지 않았다(표본 5가지).
