1. **재배포 필요(다음 단계):** SERVER-R2-01(판정 실패 분기의 판 삭제·superseded), SERVER-R2-02(`joined` 410 정리). 검토 1차의 SERVER-R1-01·03 도 아직 배포되지 않았다. 저장소 계약(`test:store`)은 바뀌지 않았다(새 포트 연산 없음). 배포 뒤 `verify.mjs`, `test:store`, 그리고 공용 서버 로그에서 `conn.join{outcome=gone}`·`superseded` 가 나오는지 본다. 지금 공용 서버는 옛 코드다.
2. SERVER-R2-01 남는 틈 1: 실패한 처리가 판을 지운 **뒤** 같은 `join` 의 나중 처리가 새 판으로 다시 판정해 통과하면 같은 요청에 실패와 `joined` 가 차례로 간다(무작위 섞기 2000회에 93회. 고치기 전 441회). 클라이언트는 첫 답을 따르고 소켓을 닫으므로 등록은 종료 통지에서 지워지지만 그때까지 자리 하나가 세어진다. 막으려면 거절한 `join` 을 연결 항목에 표시하는 저장소 연산(포트·두 저장소·조건식)이 필요하다. 남는 틈 2(같은 ms 의 판)는 그대로다.
3. SERVER-R2-01 의 새 경우 **[추론, 시험 없음]**: 판정을 통과해 판을 차지한 처리가 등록(`bind`) 전에 끝나면(Lambda 시간 초과 등) 아무도 답하지 않는다. 클라이언트가 3초마다 같은 `join` 을 다시 보내면 다음 처리는 같은 판을 다시 차지해 등록하거나(판정 통과), 판정이 실패면 superseded 로 또 답하지 않는다. 그러면 요청 기한(10초) 뒤 첫 입장은 `SERVER_UNREACHABLE`, 재접속은 새 연결로 다시 시도한다. 고치기 전에는 이 경우 실패 코드를 받았다. 차지된 고아 기록이 90초 남는 것은 고치기 전과 같다.
4. SERVER-R2-02 남는 경우: `joined` 전송이 410 이 아니었던 경우(닫히는 중에 전송이 성공하고 그 뒤 종료 통지가 먼저 처리됨, 전송 예외). 종료 표시(`closed`)로 막는 방법은 여전히 남은 과제다.
5. CONNECT-R2-01: 실제 잠자기·공용 서버에서 다시 재지 않았다(대역과 메모리 저장소 실험). 등록이 없는 상태의 `ping` `NOT_JOINED` 도 새 연결로 가므로 연결 하나를 더 쓴다(드물다 **[추론]**).
6. BOUNDARY-R2-01: 해석기는 TOML 해석기가 아니다. 읽지 못하는 문법(예: 비ASCII 맨 키, 파일 앞의 BOM)에서는 "사용자 조치 필요"로 멈춘다(안전 쪽이지만 재설치가 막힌다). Codex 가 설치가 읽는 파일 밖(다른 설정 층)에서 등록을 읽고 그 파일에 이름도 없으면 그곳의 승인 모드 키는 여전히 보지 못한다(`get --json` 이 내는 키는 막는다).
7. BOUNDARY-R2-02: 실제 fnm 으로는 실행하지 못했다(경로 모양은 fnm 기본값 기준). 알려지지 않은 다른 일회용 링크 관리자는 걸러지지 않는다.
8. PRODUCT-R2-01: PC 시계가 앞 프로세스 시작보다 뒤로 돌아가면 cursor 가 겹칠 수 있다. 누락 알림의 cursor 재사용은 안내로만 다룬다(에이전트가 안내를 따라야 한다).
9. 검토 1차의 남은 것 1(스로틀 값 사용자 결정, `V-P7` 나 실패), 3(answer 재전송 비용), 6(`a-rtc` 간헐 `ice/failed` 원인 미상), 7(Gate 3 의 남은 것) 그대로.
