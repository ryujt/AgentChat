# 2026-11-15 W9: MCP 진입점 조립과 전 구간 검증 (G5)

작업 묶음 W9([구현 계획](../../docs/design/implementation-plan.md#3-작업-묶음))의 조립 단계(G5) 실행 기록이다. `src/entry/mcp.ts` 를 조립하고, 실행기 `tests/e2e/run.mjs` 와 전 구간 시나리오 `tests/e2e/scenarios/**` 를 만들어 조립한 MCP 프로세스로 `V-L2`~`V-L8`, `V-L7`(나), A-RTC-4·6 을 돌렸다. 총괄 결정 두 가지(기본값이 아닌 `AGENT_CHAT_HOME` 의 등록, 종료 예산)를 반영했다.

- 작업 ID: `2026-11-15-w9-assembly`
- 기준 상태: 브랜치 `main`, 커밋 `a82ed0e` + 커밋하지 않은 작업 트리(W0~W8, G1, G2 의 산출물 전체). 이 단계에서 저장소의 작성자는 이 담당 하나였다. 병행 중인 재배포 담당의 소유(`deployments/aws/**`, `src/signaling-aws/**`)는 고치지 않았다.

## 총괄 결정의 반영

**(가) 기본값이 아닌 `AGENT_CHAT_HOME`.** 설치 뿌리가 `~/.agent-chat` 과 같은 곳이 아니면(끝의 `/`·상대 경로 표기는 같은 곳으로 본다) Claude Code·Codex 등록 환경에 `AGENT_CHAT_HOME=<절대 경로>` 를 넣는다. 기본값이면 넣지 않는다. 설치가 정하는 변수로 다룬다(관리 변수). 그래서 기존 등록의 값은 옮기지 않고, 다른 뿌리로 다시 설치하면 새 값으로, 기본값으로 다시 설치하면 빼고 다시 등록한다. `doctor` 는 등록 환경 그대로 띄우므로 같은 뿌리를 쓴다. 판정표 8행(`channel-check.json`)도 같은 곳을 본다. 확인: U-W9-T14, L-W9-T15, U-W9-01, L-W9-02(`install`).

**(나) 종료 예산.** 조립한 프로세스로 `V-L7`(나)의 "종료 400ms 이하"를 쟀다. 정상 경로는 10~35ms(한 번 119ms)라 예산과 거리가 멀다. 예산을 쓰는 경로는 서버가 멈춰 `leave` 의 닫는 악수가 끝나지 않을 때다(`signaling-client` 의 닫힘 대기 300ms). 이 경로의 세션 정리가 306~323ms 였다. 예산을 받은 그대로(400ms) 쓰는 구성이면, 세션 정리가 끝나지 않는 경우 W5 의 측정대로 400ms + 로그 닫기·종료(5~11ms)로 기준을 넘는다. 그래서 기준을 낮추지 않고 조립에서 예산을 나눴다: `mcp-server` 에 320ms, 남은 80ms 안에서 로그 닫기(남은 시간 − 20ms)와 `process.exit`. 서버를 멈춘 10회(`v-l7` 5, `a-rtc` 5) 가운데 1회는 세션 정리가 320ms 를 넘어 `forced` 였고 프로세스는 329ms 에 끝났다. 나머지는 312~332ms. 확인: L-W9-T02, L-W9-T16, L-W9-02(`v-l7`, `a-rtc`).

## 설계와 다른 관찰

1. **끊김 판정이 15초를 몇 ms 넘었다**(L-W9-T05). 판정 타이머를 기한에 딱 맞춰 걸면 타이머 지연(1~3ms)만큼 넘는다. `mesh` 에서 100ms 앞당겼고 `protocol.md` 4.5, `architecture.md` S5 를 고쳤다. 판정 시각은 이제 마지막 생존 증거 뒤 약 14.9초다.
2. **시간 제한 뒤의 `start_scenario` 코드**: 기한 타이머가 `stop{time_limit}` 을 먼저 쓰므로 실제로는 `TEST_STOPPED` 다(notice 의 reason 이 `time_limit`). `architecture.md` S12 표는 `TIME_LIMIT_REACHED` 만 적었다. 구현(`shared-state` 가 중단을 먼저 본다)이 맞고 표 문구를 고쳤다. `TIME_LIMIT_REACHED` 는 타이머보다 먼저 불린 호출에서만 나온다(이번에 그 틈을 만들지는 않았다).
3. **`scenario.over_limit` 사건은 작성자만이 아니라 그 시나리오를 한도 초과로 판정한 모든 참가자에게 간다**(`to: room`). S12 는 "그 작성자에게 사건으로 알리고"라고 적었다. 작성자도 받으므로 어긋나지는 않는다. 문서는 고치지 않았다.
4. **종료 예산을 쓰는 실제 경로는 서버가 답하지 않는 `leave`** 다. 세션 정리 306~323ms 로 예산(320ms) 근처라 가끔 `forced` 가 된다(5회 중 1회). 그때도 329ms 에 끝났다.
5. 실행기의 기본 묶음에 `wire`(`V-L1`, `tests/wire/run-local.mjs`)를 넣었다. `tests/e2e` 의 하위 폴더는 아니지만 구현 계획의 W9 메모가 실행기 명령 목록에 함께 적은 로컬 실물 시험이라 넣었다.

## 미실행 항목과 이유

- `V-L9`(130분): 지시대로 스크립트만 만들었다. 다음 단계에서 백그라운드로 돈다. 실행 방법은 `tests/e2e/scenarios/v-l9.mjs` 머리에 있다(`npm run test:e2e -- scenarios/v-l9`. 기본 설정이 판정 기준이다).
- `V-P2`(같은 `v-l2.mjs` 를 `--server wss://agent-chat.tools.camp` 로): 공용 스택을 다른 담당이 재배포하는 중이라 돌리지 않았다. 서버 쪽 메시지 수 비교(CloudWatch)는 스크립트 밖이다.
- 세션 정리가 끝나지 않는(멈춘) 경로의 종료 시간: 조립한 실물로는 "서버가 답하지 않는 `leave`"까지만 만들 수 있었다(가장 긴 정리 단계가 300ms 로 묶여 있다). 그보다 오래 걸리는 정리(디스크가 멈춤 등)는 만들지 않았다. 예산 배분상 `closed` 는 320ms 에 오고 로그 닫기는 남은 시간(최대 60ms)으로 묶인다.
- `entry/mcp.ts` 의 예상 못 한 예외 처리(자기에게 SIGTERM): 제품 코드에 시험용 분기 없이 일으킬 길이 없어 실행하지 않았다.
- 실제 NAT·다른 PC·공용 서버·실제 호스트(Claude Code, Codex): 이 단계 범위 밖이다.

## 남은 것과 위험

1. `V-L9`(130분)과 `V-P2`~`V-P7`, `V-S1`·`V-S2`, `V-I*` 는 다음 단계다.
2. 끊김 판정 타이머의 앞당김(100ms)은 같은 PC 의 타이머 지연을 보고 정한 값이다. 이벤트 루프가 100ms 넘게 막히는 부하에서는 15초를 넘길 수 있다.
3. 종료의 `forced` 경로에서 `mesh.shutdown()`(네이티브 정리)이 끝나기 전에 `process.exit` 을 부를 수 있다. 이번 `forced` 1회는 정상 종료 코드 0 이었다. 실제 망에서 `leave` 의 닫는 악수가 300ms 를 넘는 일은 흔할 수 있다(공용 서버의 왕복). 그때 bye 는 이미 보냈다(먼저 보낸다).
4. 실행기의 남은 프로세스 검출은 0.5초 간격 표본이다. 0.5초 안에 생겼다가 부모가 사라진 손자는 놓칠 수 있다. 시나리오마다 자기 추적기가 따로 남은 것을 본다.
5. G1·G2 의 남은 것 가운데 3번(`NOT_JOINED` 뒤 복구 한 주기 늦음), 4번(`V-L11` srflx 부분 검증), 5번(W3a 1차 실패 원인 미상), 6번(`leave` 정리 기한 없음), `deploy.sh` 재실행은 그대로다. 1번(`AGENT_CHAT_HOME`)과 2번(예산 초과 종료 시간)은 이번에 닫았다.
