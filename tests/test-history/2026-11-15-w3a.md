# 2026-11-15 W3: 연결 (`signaling-client`, `mesh`, 연결 단독 시험)

작업 묶음 W3([구현 계획](../../docs/design/implementation-plan.md#3-작업-묶음))의 구현과 단위 검증, 그리고 W1 의 서버·프록시에 붙인 연결 단독 시험의 기록이다. 시그널링 클라이언트(재접속 루프, `ping` 놓침, 게이트웨이 프레임, `join` 다시 보내기, `joined` 전 `signal` 전달)와 mesh(`node-datachannel` 네이티브 API. offer 규칙, `cid`, 후보 묶음과 두 큐, 시도 안 재전송, 연결 기한, 교체 확인, `ping` 생존 판정, relay 후보 버림, `netInfo`, `shutdown`)를 만들고 `V-U10`, `V-U11`, `V-L11` 을 실행했다.

- 작업 ID: `2026-11-15-w3a`
- 기준 상태: 브랜치 `main`, 커밋 `a82ed0e` + 커밋하지 않은 작업 트리. W0 의 산출물(`src/protocol/**`, 각 `contract.ts`, `src/boundaries.test.ts`, `tests/support/proc.mjs`)과 W1 의 산출물(`src/entry/server.ts`, `tests/support/signal-proxy.mjs`)은 고치지 않았다. 실행하는 동안 다른 묶음이 같은 작업 트리에서 일했다.
- 이 묶음이 만든 파일:
  - `src/signaling-client/`: `index.ts`, `client.ts`, `ws-socket.ts`, `emitter.ts`, `testing.ts`(시험 전용), `client.test.ts`, `ws-socket.test.ts`
  - `src/mesh/`: `index.ts`, `mesh.ts`, `native.ts`, `emitter.ts`, `testing.ts`(시험 전용), `mesh.test.ts`, `mesh-fake.test.ts`
  - `tests/e2e/mesh/`: `peer.mjs`(참가자 프로세스), `harness.mjs`(서버·프록시·참가자 띄우기), `v-l11.mjs`(시나리오). 사용법은 각 파일의 머리 주석에 있다
- 환경: macOS 27.2.1 arm64 한 대, Node v26.12.1, TypeScript 7.0.2, `ws` 8.23.0, `node-datachannel` 0.33.6. 프로세스는 모두 이 PC 안이다. 외부 주소는 IPv4 2개, IPv6 11개(인터페이스 12개). 포트는 전부 0(임의 포트)이다. 고정 포트는 쓰지 않았다.
- 빌드와 실행: `npx tsc -p tsconfig.json --outDir .work/w3a/dist` 뒤 `node --test --enable-source-maps ".work/w3a/dist/<모듈>/**/*.test.js"`. 프로세스를 띄우는 시험은 `AGENT_CHAT_DIST=.work/w3a/dist` 로 그 폴더를 읽게 했다. 공용 `dist`, `npm run build`, `npm test`, `npm run test:e2e` 는 지시에 따라 쓰지 않았다(아래 "미실행").
- 증거 수준: `signaling-client` 의 `client.test.ts` 와 mesh 의 `mesh-fake.test.ts` 는 **대역**(가짜 소켓, 가짜 네이티브, 가짜 시계). `ws-socket.test.ts` 는 이 PC 의 실제 `ws` 서버에 붙인 **로컬 실물**이다(서버는 시험이 만든 것이라 서버 규칙의 증거는 아니다). `mesh.test.ts` 는 실제 `node-datachannel` 로 한 프로세스에 인스턴스를 둘 세운 **로컬 실물**이다. `v-l11.mjs` 는 실제 프로세스, W1 의 실제 서버, 실제 `ws`, 실제 `node-datachannel` 을 쓴 **로컬 실물**이다. 어느 것도 서로 다른 PC·실제 NAT 의 증거가 아니다. 공개 STUN 서버(`stun.l.google.com:19302`)에는 `[netinfo]` 절만 닿았다.
- 참고한 이전 이력:
  - `2026-11-15-pre-implementation-assumptions`: PRE-RTC-03·04(같은 PC 연결 11~25ms, srflx 45~73ms), PRE-RTC-06·07(`failed`·`closed` 를 모두 처리, 응답 없음은 스스로 실패하지 않는다), PRE-RTC-09(작은 ID 가 offer), PRE-RTC-10(pc 를 모두 닫아야 프로세스가 끝난다), PRE-RTC-11(relay 는 TURN URL 을 줄 때만). 구현의 전제로 썼다. PRE-RTC-10 은 다시 재서 내용을 넓혔다(A-W3A-01~03). PRE-RTC-03·04 의 "링크가 srflx 보다 먼저 열린다"는 제품에서는 성립하지 않았다(아래 "설계와 다른 관찰" 3).
  - `2026-11-15-w0-contracts`: W0-36(ICE 서버를 `{hostname, port}` 로 넘긴다). `native.ts` 가 그대로 따르고 L-W3A-02 가 대표 값 일곱 가지로 다시 봤다.
  - `2026-11-15-w1`: L-W1-08(서버와 프록시의 최종 통과). 그 서버와 프록시를 고치지 않고 붙였다. 서버의 주소별 연결 한도(기본 20)는 실행 옵션 `--max-connections-per-ip 200` 으로 올렸다(프록시를 거치면 모두 127.0.0.1 이다).
- 원문 증거: 명령 출력과 탐색 스크립트는 세션 임시 폴더의 `impl/w3a/`(`probe1~7.mjs`, `mutate.mjs`, `v-l11-run1.log`, `v-l11-run2.log`)에 있었고 보존 대상이 아니다. 재현에 필요한 명령·조건·판정은 이 문서에 적었다. 이 문서와 시험 출력에 방 ID, key, SDP, candidate 원문은 없다.
- 실행 ID: 대역은 `U-W3A-NN`, 로컬 실물은 `L-W3A-NN`, 라이브러리 동작의 확인(탐색 코드)은 `A-W3A-NN` 이다. 시각은 KST 다.

## 설계와 다른 관찰

1. **네이티브 `cleanup()` 은 프로세스 전체에 작용한다** (A-W3A-01~03). 한 프로세스의 다른 mesh 가 가진 pc 까지 콜백 없이 닫고, "상대가 닫았는데 이쪽에서 `close()` 를 부르지 않은 pc"가 하나라도 있으면 10초 멈춘 뒤 던진다. 설계는 `shutdown()` 이 `cleanup()` 을 부른다고만 정했다. 구현은 설계대로 부르되 (가) 닫힘을 안 pc 는 항상 `close()` 를 부르고 (나) `shutdown()` 은 자기 pc 를 모두 닫은 뒤 한 박자(마이크로태스크) 늦춰 `cleanup()` 을 부르며 (다) 던지면 로그만 남긴다. 제품은 한 프로세스에 mesh 가 하나라 문제가 없다. **한 프로세스에 mesh 를 둘 이상 세우는 시험은 모든 mesh 의 `shutdown()` 을 같은 박자에 불러야 한다**(`src/mesh/testing.ts` 의 `shutdownAll`). 한쪽만 끝내면 다른 쪽의 링크가 `link-closed` 없이 죽는다.
2. **닫힘 통지가 마지막 프레임보다 먼저 올 수 있다** (A-W3A-07, L-W3A-01 의 실패). 네이티브 콜백은 종류마다 줄이 따로이고, 한 박자에 쌓인 것은 건 순서로 처리된다. 상대가 `bye` 를 보내고 바로 닫으면 `pc:closed` 가 `bye` 프레임보다 먼저 처리될 수 있었다. 구현은 프레임 콜백을 닫힘 콜백보다 먼저 걸고, 상대 쪽 닫힘으로 열린 링크를 끝낼 때 0ms 타이머로 한 박자 늦춘다. `closeLink`·교체·생존 기한으로 끝낼 때는 늦추지 않는다.
3. **같은 PC 에서 링크는 srflx 후보보다 늦게 열린다** (L-W3A-08 의 netinfo). 설계의 전제(PRE-RTC-03·04: 링크 11~25ms, srflx 45~73ms)는 후보를 낱개로 바로 보낸 탐색 코드의 값이다. 제품은 후보를 `CANDIDATE_BATCH_MS`(100ms) 모아 보내므로 링크가 약 110~170ms 에 열리고, srflx 는 그보다 먼저 나온다. "링크가 열린 뒤에 나온 후보를 세는 길"은 공개 STUN 으로는 10회 가운데 0회 지났다. 그 길 자체는 로컬 STUN 대역으로 봤다(실제 라이브러리, 두 프로세스). `V-L11` 의 그 항목은 이 PC 에서 계속 부분 검증으로 남을 가능성이 크다.
4. **링크가 열리면 그 뒤로는 후보를 보내지 않는다.** 설계의 재전송 표가 "채널이 열리기 전까지"라 그렇게 했다. 그래서 한쪽이 상대의 후보를 받아 바로 열리면 자기 후보 묶음은 한 번도 나가지 않는다(`V-L11` (나)에서 answer 쪽 후보 0건).
5. `joined` 의 `ping_interval_ms`·`stale_after_ms`·`max_peers` 는 쓰지 않는다. 설계가 클라이언트의 주기를 상수(`SIGNAL_PING_INTERVAL_MS`)로 정했기 때문이다.
6. 설계에 값이 없어 모듈 안에 둔 값: 응답이 사라진 `join` 을 같은 `id` 로 다시 보내는 주기(`SIGNAL_RESEND_MS` 3000ms 를 빌려 씀. 설계는 "다시 보낸다"만 정했다), `SERVER_ERROR` 를 받은 `join` 의 재전송 대기(게이트웨이 프레임과 같은 1~2초), `leave` 뒤 소켓 닫힘을 기다리는 시간(300ms), 기본 소켓의 닫는 악수 기한(2000ms. `ws` 기본 30초)과 받는 프레임 상한(65536바이트).
7. `join()` 이 게이트웨이 프레임만 받다가 기한을 넘기면 `SERVER_UNREACHABLE` 로, `SERVER_ERROR` 를 받다가 넘기면 `SERVER_ERROR` 로 끝낸다. 계약의 주석은 둘을 한 문장에 적어 어느 코드인지 분명하지 않았다.
8. 첫 `join` 중에 온 `REPLACED` 는 그 코드로 reject 한다(재접속하지 않는다). `NOT_JOINED` 는 같은 연결에 `join(mode=resume)` 을 같은 순번으로 다시 보내고, 같은 연결에서 또 받으면 연결을 버리고 재접속한다(설계는 "다시 보낸다"만 정했다).

## 남은 위험과 다음에 확인할 것

1. **L-W3A-06 의 실패(1/38)**: 양방향의 첫 후보 묶음을 버린 경우에 한 번, 3초의 재전송으로 후보가 양쪽에 들어간 뒤 ICE 가 약 7초 걸렸다(연결 10455ms, `resends` 3/3). 15초 기한 안이었지만 "resends 가 주입과 맞는다"는 어겼다. 같은 주입 37회(같은 절 7회, 따로 30회)에서는 3.1~3.4초였다. 원인을 가리지 못했다(라이브러리의 ICE 검사 재시도 간격으로 추정. 근거 없음). 그 실행은 mesh 사건을 남기지 않았다. 지금은 실패하면 `v-l11.mjs` 가 양쪽의 mesh 사건을 출력한다. G2 에서 `--only drop` 을 여러 번 돌려 다시 본다.
2. **닫기 직전의 큰 프레임은 사라진다** (A-W3A-06). `mesh.send` 직후 `closeLink` 나 `shutdown` 을 부르면 8000바이트 이하는 10/10 도착했고 16000바이트 이상은 0/10 이었다(같은 PC). `bye`(약 35바이트)와 작은 `state` 는 도착 범위지만, 큰 `state` 프레임 뒤에 바로 닫으면 잃는다. `closeLink` 가 보낸 것을 기다렸다 닫게 하려면 계약을 바꿔야 한다. W6 의 A-RTC-6 에서 본다.
3. **접속 순번은 클라이언트마다 1 부터다.** `key` 는 프로세스마다 하나인데 `SignalingClient` 는 입장마다 새로 만든다. 같은 프로세스가 같은 방에 같은 이름으로 다시 입장할 때 서버에 옛 기록이 남아 있으면(종료 통지 누락) 새 `join` 의 `seq`(1)가 저장된 값보다 작아 `REPLACED` 로 거절된다. 기록이 오래될 때(90초)까지 입장하지 못한다. 대역으로도 실행하지 않았다(추론). "계약 변경 요청" 1.
4. `v-l11.mjs` 의 `[live]` 는 날 클라이언트 하나로 요청을 보낸다. `--requests` 를 290 넘게 주면 서버의 연결별 속도 제한(60초 300건)에 걸린다.
5. 후보 묶음은 이 PC 에서 host 1건(+srflx 1건)뿐이었다. IPv6·VPN 주소가 11개 있었지만 라이브러리가 후보로 내지 않았다. 인터페이스가 많은 PC 에서 한 묶음이 32건을 넘는 경우는 나눠 보내게 만들었으나 실행하지 못했다.

## 계약 변경 요청 (통합 담당에게)

1. `SignalingClientDeps` 에 접속 순번의 시작 값(또는 프로세스가 가진 순번 공급 함수)을 더한다. 이유: "남은 위험" 3. 영향: `room-session`(W6. 클라이언트를 만들 때 넘긴다), `entry/mcp`(W9. 프로세스 수명의 순번을 가진다).
2. `Mesh.shutdown()`·`closeLink()` 의 주석에 "직전에 보낸 프레임은 작을 때만 도착한다"는 것과, 필요하면 보낸 것을 기다렸다 닫는 선택지를 정한다. 이유: "남은 위험" 2. 영향: `room-session`(W6. `bye`·`presence{left}` 의 순서와 대기), A-RTC-6.
3. `mesh/contract.ts` 의 `CreateMesh` 주석에 "한 프로세스에 살아 있는 mesh 는 하나다. 둘 이상을 세우는 시험은 함께 끝낸다"를 적는다. 이유: "설계와 다른 관찰" 1. 영향: `room-session` 의 하네스 시험(W6)이 한 프로세스에 세션을 둘 세우면 걸린다.
4. `signaling-client/contract.ts` 의 `SignalingJoinFailure` 주석에서 게이트웨이 프레임만 받다 끝난 `join` 의 코드를 정한다(구현은 `SERVER_UNREACHABLE`). 영향: `room-session` 의 오류 변환(W6).
5. 형제 모듈이 같은 `Subscribable` 구현(`emitter.ts`)을 따로 갖고 있다. `protocol` 에 한 벌을 두면 세 모듈(`signaling-client`, `mesh`, `inbox`)이 함께 쓸 수 있다. 급하지 않다.
