# 2026-11-15 W9 공용 서버 검증: `V-P2`, `V-P3`, `V-P5`, `V-P7`

배포된 공용 서버(`wss://agent-chat.tools.camp`, 스택 `agent-chat-signaling`, 서울)를 거쳐 조립한 제품(MCP 진입점 `dist/entry/mcp.js`)을 검증한 기록이다. 기준은 [검증 계획 3.3](../../docs/design/verification-plan.md#33-실제-환경-공용-서버)이고 통과 조건은 바꾸지 않았다.

- 작업 ID: `2026-11-15-w9-public`
- 기준 상태: 브랜치 `main`, 커밋 `a82ed0e` + 커밋하지 않은 작업 트리(W0~W8, G1, G2, W9 조립·재배포 뒤). 이 묶음은 **제품 코드와 `deployments/aws` 를 고치지 않았다.** 새로 만든 것은 시험 스크립트 `tests/e2e/public/*.mjs` 와 이 기록, 그리고 검증 계획 2.3 의 "지금 근거" 칸이다.
- 환경: macOS 27.2 arm64 한 대, Node v26.12.1, TypeScript 7.0.2. AWS 는 서울(`ap-northeast-2`), 기본 프로필(계정 `<ACCOUNT>` 의 **루트 자격 증명**. G2 남은 것 6 그대로). AWS 에는 **조회만** 했다(CloudFormation 출력, CloudWatch 지표, CloudWatch Logs, DynamoDB 강한 일관성 Query·Scan). 스테이지 스로틀·함수 설정·코드는 바꾸지 않았다.
- 빌드: `npx tsc -p tsconfig.json --outDir .work/w9-public/dist`(공용 `dist` 를 건드리지 않으려고 따로 빌드). 모든 실행은 `AGENT_CHAT_DIST=.work/w9-public/dist`, `TMPDIR=<세션 스크래치>/tmp`. MCP 프로세스는 하네스가 만든 임시 `HOME`·임시 `AGENT_CHAT_HOME` 으로 떴다. 실제 홈(`~/.agent-chat`, `~/.claude*`, `~/.codex`)은 건드리지 않았다.
- 참고한 이전 이력과 반영:
  - `2026-11-15-w9-redeploy`: 관찰 1(스로틀 때 접근 로그 줄이 JSON 인지 미확인) → `V-P5` 에서 확인. 관찰 2(함수 로그 `conn.join` 의 `sid` 원문은 설계가 허용한 상관 필드) → `V-P5` 표지에 `sid` 를 넣지 않았다. 관찰 3(동시 입장 "모두 거절") → `V-P7` 에서 제품으로 다시 봤다.
  - `2026-11-15-w9-assembly`: `tests/e2e/scenarios/harness.mjs` 의 `--server` 공용 서버 기본값 처리(서버 인자·`AGENT_CHAT_SERVER` 없음)를 그대로 썼다. `V-P2` 는 조립 담당이 만든 `v-l2.mjs` 를 고치지 않고 돌렸다.
  - `2026-11-15-gate1` 남은 것 3(`NOT_JOINED` 뒤 복구가 한 `ping` 주기 늦음) → `V-P3` 에서 공용 서버로 재현됐다(관찰 2).
  - `2026-11-15-aws-apigw-websocket-probe`(PRE-AWS-06, 10): 종료 통지 14~29ms, 스로틀 프레임 → 제품으로 다시 쟀다.
- 원문 증거: 세션 스크래치 `…/scratchpad/w9/w9-public/`(`logs/*.log`, 받아 온 로그·지표 원문 `*-raw.json`·`v-p2-metrics.json`, 표지 파일 `*-markers.json`. 원문과 표지 파일은 권한 600). **세션이 끝나면 사라진다.** 이 문서에는 방 ID, 참가자 이름 원문, 채팅 본문, SDP, candidate, 계정 ID, API ID 를 적지 않았다.
- 실행 ID: 대역 `U-W9P-NN`, 로컬 실물(준비) `L-W9P-TNN`, 실제 환경 `P-W9P-NN`. 시각은 KST.
- 비용과 부하(검증 계획 6절): 공용 서버에 부하를 건 것은 `P-W9P-05`(20초, 목표 초당 100), `P-W9P-06`~`08`(단계마다 약 90초, 목표 초당 35~240)이다. 이 동안 **스테이지 전체가 스로틀 상태**였다(다른 사용자의 입장에도 영향이 있었을 수 있다). 부하 연결이 보낸 메시지는 합계 59,260건이고 그중 Lambda 까지 간 것은 16,061건이다(아래 표).

## 설계와 다른 관찰

1. **`V-P2` 의 지표가 설계 추정과 정확히 맞았다.** 참가자 4 × `ping` 30초 주기 = 분당 호출 8, 메시지 16(수신 + `pong`). 채팅 200건 구간도 같다. 지표 차이 0 은 이 15분 동안 이 스택을 쓴 다른 연결이 없었기 때문이기도 하다(접근 로그의 `CONNECT`·`DISCONNECT`·다른 방 `relay` 0). 다른 사용자가 있는 때에는 같은 비교가 흔들릴 수 있다.
2. **SIGCONT 뒤 재등록이 약 30초 늦다(G1 남은 것 3 의 공용 서버 재현).** 오래됨으로 걸러진 기록의 연결이 `NOT_JOINED` 를 받고 같은 연결로 `join(resume)` 을 보내면 서버는 "같은 등록"으로 보고 판정 없이 `joined` 를 돌려준다. 기록은 갱신되지 않고, 다음 `ping`(30초 뒤)에 다시 `NOT_JOINED` 를 받아 새 연결로 재등록한다. 그동안 그 참가자는 서버 목록에 없다(새 입장자가 그를 필수 피어로 보지 않는다). 설계 문서([protocol.md 2.4](../../docs/design/protocol.md#24-오류-코드) `NOT_JOINED` 행)에 적힌 동작 그대로라 고치지 않았다. 영향: 노트북이 잠들었다 깨는 경우 재등록이 최대 한 `ping` 주기 늦다.
3. **스테이지 스로틀은 서버 → 클라이언트 전송(`POST /@connections`)에도 걸린다.** 부하 구간마다 `CONNECTION_API` 429 가 59~492건, 함수 로그 `send.failed` 가 12~120건이었다. 이때 클라이언트는 게이트웨이 프레임을 받지 않는다(그 메시지는 클라이언트가 보낸 것이 아니다). 그래서 `pong`, `joined`, 전달되는 `signal` 이 **흔적 없이** 사라진다. [deployment.md 2.5](../../docs/design/deployment.md#25-api-gateway-제약과-대응) 는 "스로틀을 넘으면 보낸 쪽에 `Too Many Requests` 가 온다"만 적었다. 초당 35 단계의 재접속 2회는 게이트웨이 프레임 6건에 `ping` 놓침 6건이었다. 놓침 대부분이 `pong` 유실(제한 시간 10초)이다.
4. **답한 쪽의 `ice`/`ice_timeout` 은 `answer` 유실일 수 있다.** P-W9P-08 의 실패 시도: 답한 쪽은 `ice_state: connected`, `pc_state: connecting`, 후보 양쪽 각 2개로 15002ms 에 `ice`/`ice_timeout`. 같은 쌍의 offer 쪽은 `answer` 를 끝내 받지 못해 `signaling`/`no_answer`(재전송 6, 대부분 게이트웨이 프레임). 답한 쪽은 `answer` 가 도착했는지 알 수 없고, [protocol.md 3.3](../../docs/design/protocol.md#33-재전송-기한-실패) 의 표는 답한 뒤에는 후보만 다시 보내고 분류를 `ice` 로 한다. 제품은 그 표대로 동작했다. 그래서 시그널 유실이 심한 때 에이전트는 "직접 경로가 없다"는 안내를 받는다. ICE 가 `connected` 인데 채널이 열리지 않은 경우는 직접 경로가 있다는 뜻이다.
5. **지속되는 스로틀에서는 재접속이 일어난다.** [protocol.md 2.6](../../docs/design/protocol.md#26-heartbeat) 은 연속 3회 놓치면 재접속하고, 게이트웨이 프레임은 놓침으로 센다. 부하가 70초 이어지면 3회 연속 놓침이 쉽게 나온다(관찰 3 의 `pong` 유실 포함). `V-P7`(나)의 "재접속이 늘지 않는다"는 이 규칙과 함께 채워질 수 없는 경우가 있다. 단발 게이트웨이 프레임으로는 재접속하지 않는다는 [deployment.md 2.5](../../docs/design/deployment.md#25-api-gateway-제약과-대응) 의 문장 자체는 맞다.
6. **만들기·입장 요청이 기한(10초) 안에 끝나지 않는 일이 초당 60 에서 이미 있었다**(`SERVER_UNREACHABLE`, 게이트웨이 프레임 7 = 요청 7번이 모두 버려짐). 부하 연결은 고르게 보내고, 제품은 한 번에 여러 건(offer + 후보 묶음 등)을 몰아 보낸다. 토큰이 비어 있을 때 몰아 보낸 것은 거의 다 버려진다 **[추론]**. 같은 통과율이 제품 쪽에는 더 나쁘게 작용한 것으로 보인다(부하 통과율 44% vs 제품 요청 7/7 폐기).
7. `V-P5` 표지는 모두 0건이었다.
8. **`$disconnect` 뒤에 처리된 메시지가 빈 연결 항목을 다시 만든다.** 끝난 뒤 테이블에 연결 항목 2개가 남았다(참가자 항목·등록 없음, 분 카운터 1). 둘 다 그 초에 닫힌 연결로의 응답 410 이 있다. 클라이언트가 `leave` 를 보내고 바로 소켓을 닫으면, `$disconnect` 가 먼저 처리되어 연결 항목을 지우고 늦게 처리된 `leave` 의 카운터 `UpdateItem` 이 항목을 새로 만드는 것으로 보인다 **[추론. A-AWS-7 의 순서 뒤바뀜]**. 방 ID·이름·key 는 들어 있지 않고 TTL 3시간으로 지워진다. [deployment.md 2.4](../../docs/design/deployment.md#24-dynamodb-데이터-모델) 의 "남은 항목은 TTL 로 치워진다"와 맞으므로 고치지 않았다. `test:store` 의 "남은 항목 0" 확인과 섞이지 않는다(그 시험은 자기 접두어만 본다). 함수 로그 앱 줄의 필드는 W9 재배포 기록과 같다(`sid` 원문은 설계가 허용한 상관 필드라 표지에 넣지 않았다).

## 스로틀 기본값 재검토 의견 (`V-P7` 결과)

- **[실측]** 스테이지 스로틀은 스테이지 전체에 걸린다(A-AWS-11). 다른 연결 하나 묶음이 초당 35건만 보내도 정상 참가자의 `pong` 이 사라져 재접속이 났고, 초당 45 부터 입장이 실패했다. 초당 25·버스트 100 은 **남용 대응이 아니라 비용 상한**으로만 작동한다. 남용 한 건이 공용 서버의 모든 방을 막을 수 있다.
- **[실측]** 정상 사용량: 4명 방의 상시 부하는 분당 8 호출이다. 5명 동시 입장(만들기 1 + 4)은 약 2초 동안 65~75 호출이다(P-W9P-10). 버스트 100 안이라 식은 함수에서도 10/10 성공했다. 8명 동시 입장은 쌍 28개라 이보다 많다(A-RTC-4 의 쌍마다 4~5건 기준 약 140건 **[추론]**). 버스트 100 을 넘으면 넘은 것은 버려지고 재전송으로 메운다. 같은 시각에 다른 방의 입장이 겹치면 더 빨리 닿는다.
- 의견(**[제안]**, 총괄 판단 필요):
  1. 기본값을 올리는 것만으로는 남용을 막지 못한다. 올리면 비용 상한이 함께 오른다. 초당 25 를 유지하되 문서에 "남용 한 건으로 전체가 막힌다"를 한계로 적는 안.
  2. 클라이언트 쪽 완화: 게이트웨이 프레임을 받았을 때 `ping` 놓침을 다르게 세기(예: 스로틀 중에는 재접속 대신 간격을 늘림), 답한 쪽이 열리지 않은 동안 `answer` 도 주기 재전송, `ice_state` 가 `connected` 인 채 기한이 찬 시도는 `signaling` 으로 분류. 모두 프로토콜 변경이라 이 묶음에서 하지 않았다.
  3. 연결별 제한은 core 에 이미 있다(60초 300건). 스테이지 스로틀을 넘기는 부하가 연결을 여러 개로 나누면 그것으로 막지 못한다(이번 부하는 연결당 초당 1~10건이라 연결별 제한에 한 번도 닿지 않았다). 막으려면 주소별 제한 같은 앞단 수단이 필요하다. 어떤 수단이 WebSocket API 에 붙는지는 확인하지 않았다. 범위 밖이다.

## 미실행과 이유

- `V-P4`(130분, 2시간 한도), `V-P6`(`destroy.sh` 재배포): 이 묶음의 범위 밖.
- `V-P7`(가) 의 "환경 변수를 바꿔 새 실행 환경을 강제"하는 방법은 쓰지 않았다(설정 변경 금지). 회차마다 10분 쉬고, 식었는지를 함수 로그의 `INIT_START` 로 적었다.
- WAF, 예약 동시 실행, 스테이지 스로틀 값 변경 시험: 설정 변경이라 하지 않았다.
- 공용 서버 위의 결함 주입(F-01, 02, 04, 07, 10, 11, 14)은 와이어 시험(`V-P1`)이 덮는 범위 밖의 것을 따로 돌리지 않았다.
