## 관찰

1. **P4-05 의 실패는 검증 도구의 결함이다.** 내가 처음 쓴 조건은 "시그널링이 `connected` 가 아닌 10초 표본이 하나 이상 있고 그때도 link open 3"이었다. 끊김을 실제로 보았다는 증거로 넣은 것이다. 실제 재접속은 0.38~1.36초에 끝나 10초 표본에 한 번도 잡히지 않았다(`reconnecting_samples: 0`). 끊김 자체는 진단 로그(`signal.error{socket_closed}`, `signal.state` reconnecting → connected seq 2)와 함수 로그(재등록 `conn.join{joined}` 4), DynamoDB 로 확인됐다. 그 사이 DataChannel 이 닫힌 적이 없다는 것은 전 구간 `link.closed` 0 과 끊김 앞뒤 표본의 link open 3 으로 본다. 끊긴 1초 남짓 동안 보낸 채팅은 없었다(10초 간격이라). 끊김 앞뒤 60초 안의 50건은 모두 전달됐다. 조건을 로그 근거로 바꿨고(위 "고친 것"), 같은 원자료로 다시 판정하면 통과다(P-FL-03a). 고친 판으로 130분을 다시 돌리지는 않았다.
2. **공용 스테이지를 다른 연결이 함께 썼다.** 06:21~06:48 에 이 시험 밖의 연결이 있었다. 06:21~06:32 는 분당 MessageCount 32(우리 16 + 다른 연결 16, 접근 로그 MESSAGE 16 = 우리 8 + 다른 8. 다른 방의 함수 로그 줄은 없음 → 다른 연결 4개가 `ping` 만 보낸 것으로 본다 **[추론]**), 06:33~06:47 은 다른 방의 입장·퇴장·`relay`(함수 로그 다른 방 `conn.join` 7, `relay` 9, `conn.closed` 11)가 있었다. 같은 시각에 다른 담당이 공용 서버로 시험한 것으로 보이나 누구인지는 확인하지 않았다. 이 때문에 (다) 전 구간 합을 판정하지 못했다. 참고 추정 **[추정]**: 16 이 아닌 분에서 우리 몫(16)과 우리 활동(06:20 입장 분, 08:20 재접속 분)을 빼고 남은 것을 다른 연결의 것으로 보면 약 365건이고, 2535 − 365 ≈ 2170 은 (다)의 범위 [2056, 2292] 안이다. 접근 로그에 연결 ID 가 없어 우리 몫을 정확히 나눌 수 없다. 섞이지 않은 96분은 모두 정확히 16 이었다(V-P2 실측과 같다). 채팅이 서버를 지났다면 분당 72건 이상 늘었을 것이다.
3. **지표의 분과 실제 시각이 1분쯤 어긋난다.** 입장(06:20:28)의 몫이 MessageCount 06:21 분(98)에, 재접속(08:20:29~33)의 몫이 08:21 분(24)에 실렸다. 같은 분의 접근 로그와 Invocations 는 실제 시각의 분에 있다. 분 단위로 지표와 로그를 견줄 때는 앞뒤 분을 함께 봐야 한다 **[실측, 이 실행]**.
4. **2시간 한도의 실측**: API Gateway 가 연결을 연결 뒤 약 7199.4~7199.9초에 닫았다(설계의 A-AWS-1 "최대 2시간, 미실측"의 첫 실측). 닫힌 뒤 클라이언트는 `socket_closed` → 백오프(첫 시도) → 새 연결 → `join`(resume) → `connected` 로 1.4초 안에 돌아왔다. `ping` 놓침, 게이트웨이 프레임, `NOT_JOINED` 는 없었다.
5. **RSS 가 천천히 는다(`V-L9` 는 기준 안에서 통과).** `V-L9` 의 끝 증가율은 최대 17.4%(ana)로 20% 기준에 가깝다. 중간에는 107분에 cat 이 98528KB(기준 대비 +20.6%)였다가 110분의 퇴장·재입장 뒤 88944KB 로 내려갔다(판정은 끝 표본으로 한다. 스크립트가 정한 대로다). 퇴장·재입장 뒤 내려가고 그 뒤 다시 는다. 주입이 없는 `V-P4` 의 프로세스도 86~88MB(2분) → 96~99MB(125분)로 늘었다. 탐색 둘(L-FL-03·04): 전체 GC 뒤 살아 있는 힙은 30분에 +1.34MB 뿐이고(그 절반이 컴파일된 코드), `heapUsed`·`heapTotal` 은 분당 약 0.14MB 씩 는다. 늘어난 RSS 의 대부분은 아직 걷히지 않은 힙과 그에 맞춰 커진 힙 공간으로 보인다 **[추론]**. 다만 `arrayBuffers` 가 40분에 0.29 → 1.08MB 로 꾸준히 늘었고, 이것이 걷히는지는 확인하지 않았다. 130분보다 오래 가면 20% 를 넘을 수 있다.
6. 퇴장·재입장 회복(132~200ms)과 소켓 끊기 회복(1006~1011ms)은 130분 동안 일정했다.

## 미실행과 이유

- **고친 `v-p4-long.mjs` 로 130분 다시 실행**: 하지 않았다. 고친 것은 P4-05 의 증거 조건 하나이고, 그 조건이 읽는 원자료(진단 로그의 끊김, `link.closed`, 표본)는 P-FL-03 이 남겼다. 다시 돌려도 공용 스테이지에 다른 연결이 섞이면 P4-07 (다)는 다시 판정하지 못할 수 있다. 필요하면 공용 서버를 다른 시험이 쓰지 않는 시간에 같은 명령으로 130분 다시 돌린다.
- 재배포한 공용 서버(검토 3차 반영 코드)로 `V-P4`: 재배포 전이라 하지 못했다. 이번 결과는 검토 전 서버 코드의 것이다.
- `V-L9` 를 130분보다 길게: 하지 않았다(관찰 5 의 추세 확인용).
- 관찰 5 의 `arrayBuffers` 증가가 걷히는지(강제 GC 뒤 값): 보지 않았다.
- NAT 을 지나는 연결: 같은 PC 의 프로세스끼리라 host 후보로 섰다. 공용 서버를 거친 시그널링만 확인된다.
