# 2026-11-15 W1: 서버 규칙과 자체 호스팅

작업 묶음 W1([구현 계획](../../docs/design/implementation-plan.md#3-작업-묶음))의 구현과 검증 기록이다. 대상은 `signaling-core` 규칙, `RoomStore` 계약 테스트 묶음, 메모리 저장소, ws 리스너, 서버 진입점, 와이어 계약 테스트, 결함 주입, 시험용 시그널링 프록시, 자체 호스팅 실행 안내다.

- 작업 ID: `2026-11-15-w1`
- 기준 상태: 브랜치 `main`, 커밋 `a82ed0e` + 커밋하지 않은 작업 트리. W0 의 산출물(`src/protocol/**`, 각 `contract.ts`, `ports.ts`, `log-port.ts`, `boundaries.test.ts`, `tests/support/proc.mjs`)은 고치지 않았다. 실행하는 동안 다른 묶음이 같은 작업 트리에서 일했다(`src/diagnostics`, `src/shared-state`, `src/setup` 등이 중간에 생겼다).
- 이 묶음이 만든 파일:
  - `src/signaling-core/`: `index.ts`, `core.ts`, `testing.ts`, `core.test.ts`
  - `src/signaling-selfhost/`: `index.ts`, `server.ts`, `memory-store.ts`, `memory-store.test.ts`, `core-rules.test.ts`, `server.test.ts`
  - `src/entry/server.ts`
  - `tests/wire/`: `wire-client.mjs`, `wire-contract.mjs`, `fault-injection.mjs`, `wire-peer.mjs`, `server-entry.test.mjs`, `signal-proxy.test.mjs`, `run-local.mjs`
  - `tests/support/signal-proxy.mjs`
  - `deployments/self-host/`: `README.md`, `agent-chat-server.service`
- 환경: macOS 27.2.1 arm64 한 대, Node v26.12.1, TypeScript 7.0.2, `ws` 8.23.0. 서버와 클라이언트는 모두 이 PC 의 `127.0.0.1` 이다. 포트는 전부 0(임의 포트)으로 열었다. 고정 포트는 쓰지 않았다.
- 빌드와 실행: 공용 `dist` 를 쓰지 않았다. `npx tsc -p tsconfig.json --outDir .work/w1/dist` 로 빌드하고, 프로세스를 띄우는 시험은 `AGENT_CHAT_DIST=.work/w1/dist` 로 그 폴더를 읽게 했다. `npm run build`, `npm test`, `npm run test:wire` 는 지시에 따라 실행하지 않았다(아래 "미실행").
- 로거: `src/entry/server.ts` 는 `src/diagnostics/index.ts`(W7 이 작업 중인 실물)의 `createStdoutLogger`·`createFileLogger` 를 쓴다. 가짜로 바꾸지 않았다. 단위 시험의 로그 포트는 대역이다.
- 참고한 이전 이력:
  - `2026-11-15-w0-contracts`: 계약의 결정 사항을 그대로 따랐다. `ConnBinding.sid`(CONTRACTS-VS-DESIGN-R1-03), `encodeServerMessage` 가 `Result` 를 돌려준다(PROTOCOL-IMPL-R2-02), "W1·W2 가 시계를 주입받는 것이 실제 소켓 시험과 맞물리는지"(344행의 남은 확인). 마지막 항목은 U-W1-03 과 L-W1-08 로 답했다: 리스너는 주입받은 시계로 돌고, 실제 소켓 시험은 조립이 넘긴 실제 시계로 돈다.
  - `2026-11-15-aws-apigw-websocket-probe`: PRE-AWS-05(순서 뒤바뀜), PRE-AWS-09(동시 입장에서 "둘 다 못 봄" 0회)를 규칙 시험의 전제로 썼다. 그 실측을 다시 하지는 않았다. 자체 호스팅에서는 그 뒤섞임이 생기지 않으므로 대역(U-W1-08 의 "동시 처리")으로 만들었다.
  - `2026-11-15-pre-implementation-assumptions`: PRE-RTC-15(`ws` 8.23.0)를 같은 버전으로 썼다. 그 밖의 항목은 이 묶음의 범위가 아니다.
- 원문 증거: 명령 출력은 `.work/w1/*.log`(버전 관리 밖, 보존 대상 아님)에 있다. 재현에 필요한 명령·조건·판정은 이 문서에 적었다. 로그와 이 문서에 방 ID, 참가자 이름, key, SDP 원문은 없다.
- 실행 ID: 대역은 `U-W1-NN`, 로컬 실물은 `L-W1-NN` 이다. 시각은 KST 다.

| F-06 | SIGSTOP 뒤 89562ms 에 목록에서 빠짐, 92389ms 에 `conn.drop{reason: stale}`, 94377ms 에 종료 처리(`conn.closed{outcome: removed}`). 같은 방의 다른 참가자는 오류 없음. `server.stats` 1건: `connections 4, rooms 2, rejected 0, loop_lag_ms 3, rss_mb 39`. 대조군 194회 |
| F-07 | SIGKILL 뒤 6ms 에 목록에서 빠짐. 그 참가자의 `conn.closed` 는 1건(`removed`) |
| F-08 | 한도 12 에서 초과 5건이 모두 503. 그동안 `/healthz` 는 `{"ok":true,"connections":12,"rooms":11}`, 기존 10개 연결의 `ping` 정상. 3개를 닫자 바로 신규 입장. 로그 `conn.refused{reason: max_connections}` 5건. `server.stats.rejected` 는 이 주입에서 보지 않았다(60초 주기. 같은 수를 세는 `conn.refused` 줄로 봤다) |
| F-09 | 핸드셰이크를 흘린 소켓은 10001ms 에 닫힘(148바이트 중 39바이트 보냄). 핸드셰이크는 끝내고 `join` 프레임을 흘린 소켓은 12001ms 에 닫힘(미입장 기한 10초 + 닫기 유예 2초) |
| F-10 | 다른 방에만 있는 이름·없는 이름 → `PEER_NOT_FOUND`, 자기 자신 → `BAD_MESSAGE`, 등록 없이 → `NOT_JOINED`. 다른 방의 연결(같은 이름 포함)에 도착 0건. 로그 `relay{outcome: rejected}` 4건이 코드별로 맞다 |
| F-11 | 같은 이름 10개 동시 `join`: `joined` 1, `NAME_IN_USE` 9. 인계 뒤 옛 연결은 `REPLACED` 를 받고 닫힘. 옛 연결의 종료 처리는 `disconnect/kept`(기록을 지우지 못함). 그 이름으로 보낸 시그널은 새 연결에 도착. 인계 **뒤에** 옛 연결이 보낸 `ping`·`leave` 는 서버가 그 연결을 이미 끊기로 한 뒤라 규칙에 닿지 않는다. 닿는 경우의 조건부 삭제는 대역(U-W1-08 "인계 뒤 옛 연결의 ping 은 NOT_JOINED…")이 본다 |
| F-12 | 연결 302개(등록 100, 미등록 200, 대조군 2)를 60ms 에 열고, 303개가 열린 채 SIGTERM. 19ms 에 종료 코드 0. 시험 쪽 연결이 모두 닫혔고 남은 프로세스 없음 |
| F-13 | 바이너리 10건 모두 `BAD_MESSAGE`, 연결 유지. ping 2만 건을 한꺼번에 보낸 연결은 서버(`ws`)가 끊었다(종료 코드 1006). 폭주 동안 대조군의 가장 긴 왕복 1ms. `rate.limited` 0건 |
| F-14 | `Origin` 세 가지(`https://example.com`, `null`, `http://127.0.0.1`) 모두 HTTP 403. 로그 `conn.refused{reason: origin}` 3건 |

- 주입 14개 모두에서 ①~⑥이 통과했다. 대조군이 주입 중에 실패하거나 오류를 받은 적이 없다. SIGTERM 뒤 종료까지 2~19ms.
- F-06 은 실제로 90초를 기다린다. 줄여서 돌리지 않았다.

## 관찰

1. **상한을 넘는 글과 속도 제한.** [protocol.md 2.3](../../docs/design/protocol.md#23-서버-처리-규칙)은 "1. 크기 → 2. 속도 제한 → 3. 파싱" 순서로 적고, [deployment.md 2.4](../../docs/design/deployment.md#24-dynamodb-데이터-모델)는 "모든 메시지"가 건수를 올린다고 적는다. 처음에는 큰 글을 세지 않고 답했다(U-W1-02 까지). 그러면 한 연결이 16KB 를 넘는 글만 보내 속도 제한에 걸리지 않고 계속 응답과 로그를 만들 수 있다. 그래서 **크기는 먼저 보되(파싱하지 않는다) 건수에는 넣는 것**으로 바꿨다(U-W1-05 부터). 한도 안이면 `MESSAGE_TOO_LARGE`, 한도를 넘으면 `RATE_LIMITED` 뒤 닫는다. 두 문서를 함께 만족하는 해석이지만 통합 담당의 확인이 필요하다.
2. **자체 호스팅에서는 동시 처리가 겹치지 않는다.** 와이어 수준의 동시 입장·생성은 매번 정확히 하나가 통과했다. "읽은 수로 하는 판정"이 겹친 처리에서 정원을 지키는지는 포트 호출을 무작위로 뒤섞는 대역으로만 봤다. 실제 DynamoDB 에서는 미실행이다(A-AWS-14).
3. **제어 프레임 폭주는 `ws` 가 연결을 끊는 것으로 처리된다.** `ws` 8.23.0 은 내보내지 못한 자동 pong 이 60건에 닿으면 그 연결을 끊는다. 한꺼번에 2만 건을 보낸 연결은 매번 끊겼다. 50건씩 10ms 간격으로 보낸 연결은 L-W1-03 에서는 pong 260건 뒤 끊겼고 L-W1-08 에서는 5000건 모두 pong 을 받고 열려 있었다(시점에 따라 다르다). 이벤트 루프 지연은 눈에 띄지 않았다.
4. **F-05 의 "닫힌 뒤 메모리 회복"은 확인하지 못했다.** RSS 는 주입 뒤에도 그대로였다. 확인한 것은 늘어난 양이 묶였다는 것이다.
5. `server.stats` 의 `rss_mb`(39)와 시험이 `ps` 로 잰 값(71~78MB)이 다르다. 잰 시점이 다르다(앞의 것은 60초 뒤, 뒤의 것은 시작 직후와 주입 중). 같은 시점에 견주지는 않았다.

## 미실행 항목과 이유

| 항목 | 이유 |
|---|---|
| `npm run build`, `npm test`, `npm run test:wire` (공용 `dist`) | 여러 묶음이 같은 작업 트리에서 일하는 동안 공용 `dist` 를 쓰지 않기로 했다. 같은 일을 `.work/w1/dist` 로 했다. **스크립트 이름으로 실행한 적은 없다** |
| 공용 서버에 와이어 계약 실행(`V-P1`), 공용 서버의 F-01·02·04·07·10·11·14 | 배포가 없다. W2 와 G6 의 일이다. `wire-contract.mjs` 는 `--url` 만 바꾸면 되게 썼지만 공용 서버에 붙여 본 적은 없다. 속도 제한 항목은 스로틀을 넘지 않게 `--flood-interval-ms` 를 주거나 `--no-flood` 로 건너뛰어야 한다. API Gateway 가 바이너리 프레임을 Lambda 에 넘기는지는 재지 않았다 |
| DynamoDB 구현에 `V-U7` 실행 | W2 의 일이다. `defineRoomStoreContractTests` 는 `idPrefix` 를 받고 시험마다 자기 항목을 포트 연산으로 지운다. 실제 테이블에 돌려 본 적은 없다 |
| 공용 IP 를 가진 다른 컴퓨터, 리버스 프록시와 TLS, systemd, Linux | 이 환경에서 할 수 없다. `deployments/self-host` 의 유닛 파일과 프록시 설정 예시는 실행하지 않은 예시다 |
| `--max-connections` 기본값 2000 까지의 접속 | 연결 303개까지만 열었다 |
| 프록시를 제품 클라이언트(`signaling-client`, `mesh`)와 함께 쓰는 시험 | W3 의 `V-L11` 이다. 자체 시험은 와이어 계약만 아는 클라이언트로 했다 |
| F-13 의 `server.stats.loop_lag_ms` 관측 | 주입이 60초보다 짧다. 대조군의 왕복 시간으로 대신 봤다. `server.stats` 줄 자체는 F-06 에서 봤다 |
