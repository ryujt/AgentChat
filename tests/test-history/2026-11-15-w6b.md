## 스크립트 보강 (`tests/e2e/room/v-l12.mjs`)

통과 기준은 바꾸지 않았다. 확인을 더하거나 넓히기만 했다.

- early-offer: "먼저 온 offer 로 링크가 열렸다"를 더했다. 기존 확인은 `joined` 를 붙든 동안 offer 가 왔고 결국 입장했다는 것까지다. 받은 쪽이 그 offer 를 버리고 3초 뒤 재전송으로 연결해도 통과할 수 있었다. 받은 offer 가 1건이고 입장자 쪽 시도가 3초 안에 열렸으면 그 경우가 아니다.
- partial (5): `state_diverged` 를 anna·cara 에 더해 bert 도 본다.
- partial (4): 유지 구간의 `state.resync` 시각과 계기를 출력한다(판정은 그대로 anna 쪽 `cause` 있는 줄 4회 이상).
- partial 주입의 증거: `get_status` 표본 사이에 링크가 잠깐 열렸다 닫힌 경우를 배제하려고, 양쪽 mesh 로그의 `link.attempt_end` 에서 서로와의 `ok` 가 0건이고 실패한 시도가 있음을 더했다.

## 관찰

- **결함 없음.** `room-session` 과 하위 모듈(signaling-client, mesh, shared-state, inbox, records)에서 고칠 것을 찾지 못했다. 제품 코드는 바꾸지 않았다.
- **w6a 의 남은 위험 "가짜 mesh 의 이벤트 가정"을 실물 코드와 대조했다(정적).** 실물 `src/mesh/mesh.ts` 의 `closeLink` 는 열린 링크면 `endLink` 에서 그 호출 안에 `link-closed` 를 낸다. `shutdown` 은 먼저 `emitter.stop()` 을 불러 그 뒤 이벤트를 내지 않는다. 가짜 mesh 의 가정과 같다. 실행으로 확인한 것은 아니다.
- **부분 mesh 의 교환 박자.** 테스트 시작 뒤 첫 교환이 27.7초, 그 뒤 30.0~30.1초마다였다. B 가 5초마다 쓰는 동안 간격(`gap_ms`)은 30000 에서 늘지 않았다. 주장의 가장 늦은 도착(22.8초)이 35초보다 짧은 것은 이 실행의 박자 때문이다. 교환 직후(30+30k초)의 쓰기가 마침 `set_status` 차례였다(3의 배수 틱). 45초 기준과는 여유가 크다.
- **early-offer 의 주입.** w6a 의 스크립트는 "offer 가 먼저 왔고 결국 입장했다"까지만 봤다. 보강한 확인으로 먼저 온 offer 가 버려지지 않고 그대로 링크가 됐음(154ms, 재전송 0)을 봤다.

## 미실행 항목과 이유

| 항목 | 이유 |
|---|---|
| `npm run build`, `npm test`, `npm run test:e2e -- room` | 공용 `dist` 를 쓰지 말라는 지시. 같은 내용을 `.work/w6b/dist` 로 돌렸다. `tests/e2e/run.mjs` 는 아직 없다(W9) |
| 실제 NAT, 다른 PC, 공용 서버(`wss://`), Linux·Windows | 환경 없음. 모든 `L-` 은 같은 PC 의 로컬 실물이다. 5초·1초 기준은 같은 PC 의 기준이다 |
| MCP 프로세스를 띄우는 `V-L2`~`V-L8` | W9(조립)의 완료 기준이다. W6 의 기준이 아니다 |
| `leave`·입장 실패 정리의 기한 없는 대기가 실제로 멈추는 경우 | 하위 모듈이 끝나지 않는 상황을 만들 수단이 하네스에 없다. 설계가 "기한 없이 기다린다"로 확정했다(`architecture.md` 3.10) |
