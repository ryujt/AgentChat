# 프로토콜 계약

Agent Chat 의 통신 계약을 한 곳에 정한다. 대상은 네 가지다.

1. 시그널링 WebSocket 와이어 계약 (클라이언트 ↔ 서버)
2. WebRTC 연결 절차 (시그널 종류와 처리 규칙)
3. P2P DataChannel 메시지 계약 (에이전트 ↔ 에이전트)
4. 공유 상태 모델과 병합 규칙, 서버 주소 정규화, ICE 서버 설정 검증

- 상태: 설계안. 구현 전이다. 기준 커밋 `a82ed0e`.
- 표기: **[실측]** 은 이 PC 에서 실행해 본 값, **[문서]** 는 공식 문서, **[소스]** 는 소스 코드에서 읽은 값, **[추론]** 은 실측이나 문서에서 끌어낸 것, **[가정]** 은 확인하지 않은 전제, **[제안]** 은 이 설계가 고른 값이다. `PRE-…` 는 구현 전 조사의 실행 ID 다([조사 이력](../../tests/test-history/2026-11-15-pre-implementation-assumptions.md), `PRE-AWS-…` 는 [AWS 실측 이력](../../tests/test-history/2026-11-15-aws-apigw-websocket-probe.md)). 모두 탐색 코드로 한 것이라 제품 검증은 아니다. `A-…` 는 [검증 계획](verification-plan.md#2-먼저-확인할-외부-가정)의 가정 ID 다.

## 0. 원본 규칙

- **구현 후에는 코드의 와이어 스키마가 원본이다.** 원본 위치는 `src/protocol/signaling-wire.ts`, `src/protocol/p2p-wire.ts`, `src/protocol/state-records.ts`, `src/protocol/limits.ts` 다.
- 구현이 끝나면 이 문서의 필드 표는 "설명용"으로 표시하고 코드로 링크한다. 둘이 다르면 코드가 맞고 문서를 고친다.
- 처리 규칙(누가 무엇을 언제 거절하는가)과 그 이유는 계속 이 문서가 소유한다.
- 서버 두 조립(자체 호스팅, 공용)과 클라이언트는 같은 스키마 파일을 import 한다. 스키마를 복사하지 않는다.

## 1. 공통 식별자

| 이름 | 형식 | 만드는 쪽 | 용도 |
|---|---|---|---|
| `room` (room_id) | `^[a-z0-9]{8,32}$` | 클라이언트. 생략 시 무작위 16자(80비트) | 방 식별. **방의 유일한 접근 수단**이므로 진단 로그, 서버 저장소, 보고서에 원문을 남기지 않는다. 직접 정한 ID 는 추측될 수 있다([mcp-interface.md 3.1](mcp-interface.md#31-create_room)) |
| `peer` (참가자 이름) | `^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$`. 예약 이름은 쓸 수 없다 | 에이전트 또는 설치 설정 | 참가자 신원. 방 안에서 유일. offer 주체 판정에 쓴다 |
| `sid` (세션 ID) | `^[a-z0-9]{12}$` 무작위 | MCP 프로세스가 입장할 때마다 | 같은 이름의 재시작을 구분한다 |
| `key` (resume key) | base64url 43자 (무작위 32바이트) | MCP 프로세스 시작 시. **파일에 저장하지 않는다** | 같은 프로세스의 시그널링 재접속임을 증명한다 |
| `cid` (연결 시도 ID) | `^[a-z0-9]{12}\.[0-9]{1,6}$` = `<offer 쪽 sid>.<순번>` | offer 를 만드는 쪽 | 한 연결 시도의 offer·answer·candidate 를 묶는다 |
| 메시지 ID, 기록 ID | `^[a-z0-9]{12}-[0-9a-z]{1,8}$` = `<sid>-<순번>` | 작성자 | 중복 제거, ack 대응, 기록 참조 |

- 이름 비교는 JavaScript 문자열 `<` (UTF-16 코드 단위) 로 한다. 허용 문자가 ASCII 뿐이라 구현 간 차이가 없다.
- **예약 이름**: `user`, `system`, `assistant`, `room`, `you`, `all`, `server`, `agent-chat`(대소문자 무시). 채널 태그의 `from` 이나 사건의 `to` 값과 헷갈리지 않게 하려는 것이다. 클라이언트와 서버가 모두 거절한다.
- `sid` 가 방 안에서 겹칠 확률은 무시한다(36^12).

## 2. 시그널링 WebSocket 와이어 계약

서버는 **방·참가자 등록과 시그널 전달**만 한다. 채팅과 테스트 상태는 서버를 지나지 않는다.

### 2.1 접속

- URL 은 [6절](#6-서버-주소-정규화)로 정규화한 서버 주소다. **URL 경로와 쿼리에 방 ID·이름·key 를 넣지 않는다.** URL 은 프록시와 접근 로그에 남기 때문이다.
- 서브프로토콜과 압축(permessage-deflate)은 쓰지 않는다.
- 프레임은 UTF-8 텍스트이고, 한 프레임이 JSON 객체 하나다. 바이너리 프레임을 받으면 서버는 응답 없이 종료 코드 1003 으로 그 연결을 닫는다(기록은 연결 종료와 같이 지운다). 공용 서버의 API Gateway 가 바이너리 프레임을 Lambda 에 넘기지 않고 1003 으로 닫으므로 **[실측 W2]**, 자체 호스팅도 같게 맞췄다. 제품 클라이언트는 바이너리 프레임을 보내지 않는다.
- `Origin` 헤더가 없는 연결은 허용한다. 브라우저 연결은 헤더 값 하나가 서버에서 지정한 출처와 정확히 같아야 허용한다. 그 외 출처와 중복·잘못된 헤더는 HTTP 403 으로 거절한다. 공용 서버의 허용 출처는 `https://tools.camp` 다. 자체 호스팅 서버는 `--allow-origin` 으로 허용 출처를 지정할 수 있다.
- 인증은 없다. 방 ID 를 아는 것이 입장 자격이다. (범위와 한계는 [README 범위 밖](README.md#6-범위-밖))
- 버전은 URL 이 아니라 `join` 메시지로 협상한다. 이유는 두 가지다. 자체 호스팅 서버와 공용 서버가 같은 경로를 쓴다. URL 에 값을 싣지 않는다. 공용 서버의 접속 단계(`$connect`)는 상태 코드와 본문으로 거절할 수 있지만 **[실측 PRE-AWS-03]**, 이 설계는 그 길을 `Origin` 거절에만 쓴다.

### 2.2 메시지

클라이언트 → 서버는 `action`, 서버 → 클라이언트는 `type` 으로 구분한다.

**클라이언트 → 서버**

| action | 필드 | 성공 응답 | 의미 |
|---|---|---|---|
| `join` | `v`, `id`, `room`, `peer`, `sid`, `key`, `mode`, `seq` | `joined` | 방에 참가자로 등록한다. 재접속 때도 같은 메시지를 보낸다 |
| `signal` | `id`, `to`, `kind`, `cid`, `data` | 없음 (실패 때만 `error`) | 같은 방의 `to` 에게 연결 정보를 전달한다 |
| `ping` | `id` | `pong` | 살아 있음을 알리고 현재 참가자 목록을 받는다 |
| `leave` | `id` | 없음 | 등록을 지운다. 보낸 뒤 클라이언트가 연결을 닫는다 |

**서버 → 클라이언트**

| type | 필드 | 의미 |
|---|---|---|
| `joined` | `re`, `members`, `max_peers`, `ping_interval_ms`, `stale_after_ms` | 등록 완료. `members` 는 **자신을 뺀** 살아 있는 참가자 `{peer, sid}` 목록 |
| `signal` | `from`, `sid`, `kind`, `cid`, `data` | 다른 참가자가 보낸 `signal`. `from`·`sid` 는 서버가 **보낸 연결의 등록**에서 붙인다(`sid` 는 그 연결을 등록할 때의 `join.sid`) |
| `pong` | `re`, `members` | `ping` 응답. `members` 형식은 `joined` 와 같다 |
| `error` | `code`, `message`, `re?`, `retry_after_ms?`, `supported?` | 요청 거절 또는 연결 종료 예고 |

**필드 검증**

| 필드 | 규칙 |
|---|---|
| `v` | 정수. 서버 지원 목록은 `[1]` |
| `id` / `re` | `^[A-Za-z0-9_-]{1,32}$`. 클라이언트가 요청마다 새로 만든다. 서버는 응답의 `re` 에 그대로 돌려준다. 같은 요청을 다시 보낼 때는 같은 `id` 를 쓴다 |
| `mode` | `create` \| `join` \| `resume` |
| `seq` | 정수 1 이상. **접속 순번**이다. 프로세스가 새 연결에서 `join` 을 보낼 때마다 1씩 올린다. 같은 `key` 의 옛 연결과 새 연결 중 어느 쪽이 나중인지 가린다. `key` 와 수명이 같다. 방을 나갔다 다시 들어가도 1 로 돌아가지 않고 이어 센다. 1 부터 다시 세면, 서버에 옛 기록이 남아 있을 때 다시 들어가는 `join` 이 `REPLACED` 로 거절된다 |
| `to` | `peer` 형식. 자기 자신이면 `BAD_MESSAGE` |
| `kind` | `offer-request` \| `offer` \| `answer` \| `candidate` |
| `cid` | `offer`·`answer`·`candidate` 는 필수. `offer-request` 는 생략 |
| `data` | `offer`·`answer`: `{sdp: string}` (≤ 12000자). `candidate`: `{list: [{candidate: string ≤ 1024자, mid: string ≤ 16자}]}` (1~32건. 후보를 묶어 보낸다). `offer-request`: `{}` |

**버전 협상과 호환**

- 클라이언트는 `join.v` 에 자기가 쓰는 버전 하나를 보낸다. 서버는 지원하면 그 버전으로 등록하고, 지원하지 않으면 `UNSUPPORTED_VERSION` 과 `supported` 목록을 돌려준다.
- 클라이언트가 여러 버전을 지원하게 되면 `supported` 와 겹치는 가장 큰 버전으로 한 번만 다시 보낸다. 지금은 버전이 1 하나라 다시 보내지 않고 치명 오류로 끝낸다.
- 뜻이 바뀌지 않는 변경은 선택 필드 추가로 한다. 뜻이 바뀌면 `v` 를 올리고, 서버가 한동안 두 버전을 함께 받는다.
- 모르는 필드는 무시한다(앞으로 필드를 더할 수 있게). 모르는 `action` 은 `BAD_MESSAGE` 로 거절하되 연결은 유지한다. 클라이언트는 모르는 `type` 을 무시하고 진단 로그에 건수만 남긴다.
- 서버는 SDP 를 파싱하지 않는다. 단, `sdp` 나 `candidate` 문자열에 ` typ relay` 가 있으면 전달하지 않고 `RELAY_NOT_ALLOWED` 를 돌려준다. TURN 중계 후보를 막는 세 번째 방어선이다([7절](#7-ice-서버-설정-검증)).

### 2.3 서버 처리 규칙

규칙 코드는 `src/signaling-core` 한 곳에 있다. 저장소(`RoomStore`)와 전송(`ConnectionSink`)만 조립마다 다르다([architecture.md](architecture.md#3-모듈-계약)). 규칙은 **상태 없는 실행, 동시 처리, 순서 뒤바뀜, 유실**을 전제로 쓴다. 공용 서버에서는 메시지마다 Lambda 가 따로 돈다. 연달아 보낸 20건은 10회 중 10회 순서가 바뀌어 도착했다 **[실측 PRE-AWS-05]**.

모든 메시지 공통:

1. 바이트 길이가 `SIGNAL_MAX_MESSAGE_BYTES` 를 넘으면 JSON 을 파싱하지 않는다. 답은 2번을 거친 뒤의 `MESSAGE_TOO_LARGE` 다.
2. 연결별 속도 제한을 센다. **상한을 넘은 글도 센다.** 초과하면 `RATE_LIMITED` 를 보내고 연결을 닫는다. 큰 글을 세지 않으면 한 연결이 16KB 넘는 글만 보내 한도 없이 응답과 로그를 만들 수 있다. 속도 제한의 `RATE_LIMITED` 에는 `re` 가 없다(파싱 전이다).
3. JSON 파싱과 스키마 검증에 실패하면 `BAD_MESSAGE`.

`join`:

1. `v` 가 지원 목록에 없으면 `UNSUPPORTED_VERSION` (`supported` 포함).
2. 이 연결의 등록을 본다.
   - 이미 다른 `(room, peer)` 로 등록돼 있으면 `BAD_MESSAGE`.
   - 이미 **같은** `(room, peer)` 로 등록돼 있으면 판정을 다시 하지 않는다. 목록을 읽어 `joined` 를 다시 보낸다(응답이 사라져 클라이언트가 다시 보낸 경우다). 판정을 다시 하면, 그 사이 들어온 참가자 때문에 방을 만든 쪽이 `ROOM_EXISTS` 를 받게 된다.
3. `(room, peer)` 기록을 읽는다.
   - 기록이 없거나 **오래됨**(`now - lastSeenAt > PARTICIPANT_STALE_MS`) → 새로 쓴다.
   - 기록이 있고 `key` 해시가 같다 → **인계**. 단 `seq` 가 저장된 값보다 클 때만 한다. 연결 ID, `sid`, `seq` 를 바꾼다. 이전 연결이 다른 연결이면 `error{code:"REPLACED"}` 를 보내고 닫는다(최선).
   - 기록이 있고 `key` 해시가 같은데 `seq` 가 저장된 값보다 작다 → 늦게 처리된 **옛 연결의 `join`** 이다. 기록을 바꾸지 않는다. 이 연결에 `REPLACED` 를 보내고 닫는다. `seq` 가 같고 연결 ID 만 다른 경우도 같다. 어느 쪽이 나중인지 가릴 수 없어 인계하지 않는다. 그 클라이언트가 재접속하면 `seq` 가 커져 인계된다.
   - 기록이 있고 `key` 해시, `seq`, 연결 ID 가 모두 같다 → 앞선 처리가 등록(6번) 전에 끊긴 경우다. 기록에 **차지 표시가 없으면** 기록을 그대로 두고 4번으로 간다. **차지 표시가 있으면** 앞선 처리가 이 판으로 판정을 이미 통과했다. 다시 판정하지 않고 등록한 뒤 `joined` 를 보낸다(4~6번을 건너뛴다. 6번의 "차지한 처리가 등록 전에 실패"). 등록된 연결이 같은 `join` 을 다시 보낸 경우(1번 앞의 재전송)와 같은 이유다.
   - 기록이 있고 `key` 가 다르다 → 이전 연결이 실제로 닫혔는지 확인한다(`ConnectionSink.isOpen`). 닫혔으면 새로 쓴다. 열려 있으면 `NAME_IN_USE`.
   - 쓰기는 항상 조건부다. 기록이 없었으면 "기록 없음", 있었으면 "방금 읽은 연결 ID 와 `seq` 그대로"가 조건이다. 동시에 같은 이름으로 들어온 둘 중 하나만 성공하고, 진 쪽은 이 단계를 다시 평가한다.
4. 방의 살아 있는 참가자를 **강한 일관성**으로 읽는다. 오래된 기록은 뺀다.
5. 읽은 목록으로 사후 판정한다. 실패하면 **판정에 쓴 기록**(이번 처리가 새로 쓴 것이든, 3번의 "모두 같다"로 앞선 처리가 남긴 것이든)을 그 판 조건으로 지우고 오류를 돌려준다. 지우지 못했는데 기록이 아직 이 연결·이 `seq` 이면 오류를 보내지 않는다(6번의 "같은 판의 반대 답").
   - `mode=create`: 목록에 다른 참가자가 하나라도 있으면 `ROOM_EXISTS`.
   - `mode=join`: 다른 참가자가 하나도 없으면 `ROOM_NOT_FOUND`. 이 연결의 연속 `ROOM_NOT_FOUND` 횟수를 올린다. `JOIN_MISS_MAX` 에 닿으면 `RATE_LIMITED` 를 보내고 닫는다. 그 회에는 `ROOM_NOT_FOUND` 를 보내지 않고, 그 요청의 `re` 와 `retry_after_ms`(`RATE_WINDOW_MS`)를 실은 `RATE_LIMITED` 하나만 보낸다.
   - `mode=resume`: 방에 대한 조건이 없다. 방이 비어 있으면 다시 만든 것과 같다.
   - 정원(모든 모드): 목록의 참가자 수가 자기를 포함해 `ROOM_MAX_PEERS` 를 넘으면 `ROOM_FULL`.
6. 판정에 쓴 기록을 **차지한다**(`claimPeer`: 연결 ID 와, 판정에 쓴 기록의 `lastSeenAt` 이 그대로일 때만 표시한다). 차지하지 못하면 `SERVER_ERROR` 로 답하고 등록하지 않는다. 그다음 연결을 `(room, peer, sid)` 로 등록하고 `joined` 를 보낸다. 이 연결이 보내는 `signal` 에 서버가 붙이는 `sid` 는 이 등록의 값이다.
   - 이유(검토 1차 SERVER-R1-01): 공용 서버에서는 **같은 연결의 같은 `join`** 이 두 실행에서 겹칠 수 있다(응답이 사라져 클라이언트가 다시 보낸 경우). 둘은 같은 기록으로 판정한다(3번의 "모두 같다" 경우). 한쪽이 판정에 실패해 그 기록을 지우면, 다른 쪽은 이미 통과했어도 기록 없이 등록된 "반쪽 참가자"가 되고, 지워진 사이에 들어온 입장자는 그를 보지 못해 정원과 단일 생성이 깨진다 **[검토 1차 재현: 같은 방을 두 연결이 모두 create, 정원 8 방에 9명 joined]**.
   - 그래서 5번의 삭제는 **판정에 쓴 그 판(`lastSeenAt`)이고 아무도 차지하지 않았을 때만** 한다(`deletePeer` 의 `writtenAt` 조건). 차지가 먼저면 삭제가 실패하고 기록이 남는다. 삭제가 먼저면 차지가 실패해 `joined` 를 보내지 않는다(`SERVER_ERROR`. 클라이언트가 다시 보내 새로 판정받는다). 같은 판을 판정해 통과한 다른 실행도 차지에 성공한다. `putPeer` 로 다시 쓴 판에는 차지 표시가 없다.
   - **같은 판의 반대 답을 보내지 않는다**(검토 2차 SERVER-R2-01). 삭제가 실패했는데 다시 읽은 기록이 아직 이 연결·이 `seq` 면, 같은 `join` 의 다른 처리가 그 판을 차지했거나 새 판을 다시 썼다. 이 처리는 실패 코드를 보내지 않고 `ROOM_NOT_FOUND` 의 연속 횟수도 올리지 않는다. 고치기 전에는 같은 요청에 실패와 `joined` 를 함께 보냈고, 실패가 먼저 닿으면 클라이언트는 등록된 채로 "거절됐다"고 처리했다(첫 `join` 이면 입장 실패, 재접속이면 30초 차단) **[검토 2차 재현: 무작위 섞기 2000회에 모순 441회]**. 다시 읽은 기록이 없거나 다른 연결이면 그 기록은 이 처리의 것이 아니므로 실패 코드를 보낸다.
     - 다시 읽은 기록이 **차지돼 있으면** 그 `join` 은 이미 판정을 통과했다. 이 처리도 등록하고 `joined` 를 보낸다(로그 `conn.join{outcome=joined, cause=claimed}`). 차지한 처리가 `joined` 를 보낸다고 기대하고 조용히 끝내면, 그 처리가 등록 전에 실패한 경우(아래) 이 요청에는 끝내 답이 없다(검토 3차 SERVER-R3-01). 두 처리가 모두 답하면 같은 요청에 `joined` 가 둘 가고, 클라이언트는 두 번째를 버린다(받은 `joined` 의 `re` 가 기다리는 요청이 아니다).
     - 차지돼 있지 않으면 같은 `join` 의 다른 처리가 새 판을 썼고 아직 판정 중이다. 답은 그 처리가 한다. 이 처리는 로그(`conn.join`, `outcome=superseded`)만 남긴다.
   - **차지한 처리가 등록 전에 실패**(검토 3차 SERVER-R3-01): 차지(`claimPeer`) 뒤 등록(`bind`)이 저장소의 일시 실패(DynamoDB 5xx·스로틀·요청 기한)로 던지면 그 요청에는 `SERVER_ERROR` 가 가고, 함수 기한(Lambda 10초)에 걸리면 답이 없다. 클라이언트는 같은 연결에 같은 `join` 을 다시 보낸다. 그 재전송은 등록이 없어 3번에서 차지된 자기 기록을 본다. **다시 판정하지 않고** 등록해 `joined` 로 답한다. 다시 판정하면 그 사이의 방 변화 때문에 만든 쪽이 `ROOM_EXISTS`, 들어온 쪽이 `ROOM_NOT_FOUND` 를 받는데, 상대는 이미 그를 멤버로 보고 있다. 또 지워지지 않는 기록(차지돼 `writtenAt` 삭제가 실패하고, 등록이 없어 종료 통지도 지우지 못한다)이 90초 동안 정원에 세어지고 그 방 ID 의 `create` 를 막는다 **[검토 3차 재현: 메모리 저장소, bind 1회 실패 뒤 재전송 5회가 모두 superseded, 종료 통지 뒤 기록이 남고 30초 뒤 같은 방 ID 의 create 가 ROOM_EXISTS]**. 재전송 없이 연결이 끝나면 그 기록은 여전히 남는다(오래됨으로 빠질 때까지 정원에 세어진다).
   - 저장소의 기록 읽기(`getPeer`, `listPeers`)는 차지 표시를 싣는다(`claimed: true`). `putPeer` 는 그 표시를 쓰지 않는다(새 판은 차지되지 않은 판이다).
   - 앞선 처리가 쓰고 등록 전에 끊긴 기록("모두 같다")으로 판정에 실패해도 그 판을 지운다. 지우지 않으면 실패를 받은 연결의 기록이 90초 동안 정원에 세어진다.
   - 남는 틈 1: 한 처리가 판정에 실패해 그 판을 **지운 뒤**, 같은 `join` 의 나중 처리가 빈 자리에 기록을 **새로 써서**(새 판) 다시 판정하면 통과할 수 있다(그 사이 다른 입장자도 실패해 나갔다). 그러면 같은 요청에 실패와 `joined` 가 차례로 간다. 클라이언트는 먼저 받은 답을 따른다. 실패가 먼저면 입장 실패나 차단으로 처리하고 그 소켓을 닫으므로, 등록은 종료 통지에서 지워진다(그때까지 자리 하나가 정원에 세어진다). 두 처리가 새 판에서 다시 판정하는 것은 클라이언트가 실패 뒤 다시 보낸 것과 같아 막지 않았다 **[검토 2차 재현: 같은 섞기 2000회에 93회. 고치기 전 441회]**. 막으려면 거절한 `join` 을 연결 항목에 표시해 두는 저장소 연산이 더 필요하다.
   - 남는 틈 2: 지운 뒤 같은 연결의 또 다른 처리가 같은 밀리초 값으로 다시 쓰면 판이 구별되지 않는다(서로 다른 실행의 시계가 같은 ms 를 내야 한다). 실패한 쪽의 오류(`ROOM_FULL` 등)가 `joined` 보다 늦게 오면 클라이언트는 그것을 버린다(이미 받은 `joined` 가 이긴다).
   - 등록(`bind`)한 뒤 `joined` 전송이 "연결 없음"(공용 서버의 410)이면, 종료 통지가 이 처리의 등록보다 먼저 끝났을 수 있다. 방금 만든 등록과 기록(연결 ID 조건)을 지우고 로그를 `outcome=gone` 으로 남긴다(검토 2차 SERVER-R2-02. [deployment.md 2.4](deployment.md#24-dynamodb-데이터-모델)).

**"쓰고 나서 읽고 판정"이 보장하는 것과 못 하는 것**

- 전제: 강한 일관성 읽기에서는 동시에 들어온 둘 중 **적어도 한쪽이 상대를 본다.** 나중에 쓴 쪽의 읽기는 먼저 쓴 쪽의 쓰기보다 뒤에 일어난다. 쓰기 뒤 강한 일관성 조회 20회에서 "둘 다 못 봄"은 0회였다. "한쪽만 봄"이 11회, "둘 다 봄"이 9회였다 **[실측 PRE-AWS-09]**. 그러므로 **두 입장자가 같은 목록을 본다고 가정하지 않는다.**
- 그래서 판정은 순위 비교가 아니라 **자기가 읽은 목록의 수**로 한다.
  - 정원을 넘지 않는다. 통과한 입장자 가운데 가장 늦게 쓴 쪽은 나머지를 모두 보고도 통과한 것이다.
  - `create` 는 많아야 한 명이 성공한다. 둘이 성공했다면 서로를 못 본 것인데, 그런 경우는 없다.
- 대가: 수십 ms 안에 겹친 입장자끼리는 **둘 다 거절될 수 있다.** 정원이 하나 남았을 때의 동시 입장(둘 다 `ROOM_FULL`), 동시 `create`(둘 다 `ROOM_EXISTS`), `create` 와 `join` 의 겹침이 그렇다. 거절된 쪽은 자기 기록을 지우므로 다시 시도하면 된다.
- 막지 못하는 것: 없는 방에 `mode=join` 둘이 동시에 들어오면 서로를 보고 둘 다 통과할 수 있다. 서버에는 "방" 기록이 없어 구분할 수 없다. 이 경우는 클라이언트 규칙이 정리한다([3.3](#33-재전송-기한-실패): 연결할 상대가 남지 않은 `join` 은 `ROOM_NOT_FOUND`).
- 이 판정 방식 자체는 DynamoDB 에서 재지 않았다 **[가정]**. 실측한 것은 위 전제와, 다른 두 방식(카운터+트랜잭션, 단일 항목 집합+조건식)이 4명 동시 입장에서 정원 2를 넘지 않았다는 것이다 **[실측 PRE-AWS-09]**. 배포 뒤 `V-P1` 에서 정원 직전 동시 입장으로 확인한다. 초과가 한 번이라도 나오면 조건식 방식으로 바꾼다.

`signal`:

1. 보낸 연결의 등록(`room`, `peer`, `sid`)을 찾는다. 없으면 `NOT_JOINED`. 전달하는 `signal` 의 `from` 과 `sid` 는 이 등록의 값이다. 보낸 쪽의 참가자 기록은 읽지 않는다(시그널마다 읽기가 하나 늘지 않게).
2. 같은 방의 `to` 기록을 읽는다. 없거나 오래됐으면 `PEER_NOT_FOUND`.
3. `to` 의 연결로 `signal` 을 보낸다. 전송이 "연결 없음"으로 실패하면 그 기록을 지우고(연결 ID 조건부) `PEER_NOT_FOUND`. 전송이 **스로틀**에 걸렸으면(공용 서버의 HTTP 429) 아무 오류도 보내지 않고 로그만 남긴다. 그 응답도 스로틀 토큰을 써서 요구량을 키우고, 보낸 쪽은 시도 안에서 같은 `signal` 을 3초 뒤 다시 보내기 때문이다(검토 1차 SERVER-R1-03). 그 밖의 전송 오류는 `SERVER_ERROR` 다. 두 오류 모두 `re` 에 요청의 `id` 를 싣는다.

`ping`:

1. 등록을 찾는다. 없으면 `NOT_JOINED`.
2. 참가자 기록의 `lastSeenAt` 을 갱신한다. 조건은 둘이다. 연결 ID 가 같고, 저장된 `lastSeenAt` 이 아직 오래되지 않았다(`now - lastSeenAt ≤ PARTICIPANT_STALE_MS`). 조건이 맞지 않으면 `NOT_JOINED`. 다른 연결에 인계됐거나, 기록이 지워졌거나, 이미 오래된 경우다.
   - **오래된 기록은 `ping` 으로 되살리지 않는다.** 오래된 기록은 목록과 정원 판정에서 빠져 있었다. 그 사이 다른 참가자가 그 자리를 채웠을 수 있어, 되살리면 정원을 넘는다. 자체 호스팅은 90초 정리로 그 소켓을 닫지만 공용 서버에서는 소켓이 열린 채 남는다(멈췄다 깨어난 프로세스). 그 연결은 `NOT_JOINED` 를 받고 **새 연결로** 다시 등록하며, 그때 정원을 다시 판정받는다. 이 연결의 등록은 남아 있으므로 같은 연결로 `join` 을 다시 보내면 판정 없이 `joined` 만 다시 받는다(`join` 2번). 그래서 클라이언트는 `ping` 의 `NOT_JOINED` 에 같은 연결로 다시 등록하지 않는다([2.4](#24-오류-코드). 검토 2차 CONNECT-R2-01).
3. 살아 있는 참가자 목록을 읽어 `pong` 을 보낸다.

`leave` 와 연결 종료 통지: 참가자 기록을 **연결 ID 조건부로** 지우고 연결 등록을 지운다. 조건부이므로, 늦게 도착한 옛 연결의 종료 통지가 새 연결의 기록을 지우지 못한다.

응답(`joined`, `pong`, `error`)의 전송이 스로틀에 걸려도 같은 요청에 다른 글을 또 보내지 않는다. 클라이언트의 재전송(`join` 1~3초, `ping` 5초)이 메운다.

서버가 보내는 글: `joined`, `signal`, `pong`, `error` 는 모두 `protocol` 의 `encodeServerMessage` 로 만든다. 이 함수는 클라이언트가 받을 때와 같은 스키마로 먼저 본다. 걸리면 규칙 코드의 결함이다. 그 글을 보내지 않고, 그 요청에 `SERVER_ERROR` 로 답하고 로그를 남긴다. 스키마에 맞지 않는 `joined` 를 그대로 보내면 클라이언트는 그것을 버리고 요청 기한까지 기다린다. 서버 → 클라이언트 방향에는 크기 상한을 걸지 않는다(전달하는 `signal` 은 받은 것에 `from` 과 `sid` 가 붙어 조금 길어진다).

서버가 하지 않는 것:

- 입장·퇴장을 다른 참가자에게 알리지 않는다. 참가자의 존재와 끊김은 P2P 에서 판정한다([4절](#4-p2p-datachannel-계약)). 이유: 시그널링 연결이 끊겨도 DataChannel 은 살아 있을 수 있어, 서버 연결 상태를 참가자 상태로 쓰면 틀린다.
- 메시지를 저장하거나 다시 보내지 않는다.
- 관전자([4.6](#46-관전자))를 모른다. 관전자는 보통 참가자로 등록되고 정원에 세어진다. 관전자 표시는 P2P `hello` 에만 있다.

| `UNSUPPORTED_VERSION` | `v` 미지원 | 아니오 | **치명**. 재접속하지 않는다 |
| `NOT_JOINED` | 등록 없이 `signal`·`ping`. 인계됐거나 오래된 기록의 `ping` | 아니오 | **`ping` 의 답이면** 같은 연결로 다시 등록하지 않고 곧바로 그 연결을 버리고 재접속한다(대기는 첫 회 상한 1초 안. [2.7](#27-재접속)). `ping` 의 `NOT_JOINED` 는 대개 이 연결의 등록이 남은 채 기록만 오래됐거나 지워졌거나 인계된 경우인데, 서버는 등록된 연결의 `join` 을 다시 판정하지 않고 `joined` 만 다시 보내므로 같은 연결로는 목록에 돌아가지 못한다. 그런데도 `connected` 로 알리면 다음 `ping`(30초)까지 상대의 시그널이 모두 `PEER_NOT_FOUND` 로 끝난다(검토 2차 CONNECT-R2-01). **`signal` 의 답이거나 `re` 가 없으면** 같은 연결에 `join(mode=resume)` 을 다시 보낸다. 서버는 `signal` 에서 등록부터 찾으므로 이 경우는 등록이 없고, 같은 연결의 `join` 이 정원을 다시 판정받는다. 같은 연결에서 또 받으면 그 연결을 버리고 재접속한다. **`re` 가 지금 등록으로 보낸 요청(기억하는 `signal`, 지금 `ping`)이거나 `re` 가 없을 때만 처리한다.** 다시 등록할 때 보낸 `signal` 의 기억을 비우므로, 모르는 `re` 의 `NOT_JOINED` 는 재등록 전에 보낸 요청의 늦은 답이다. 로그만 남기고 버린다(응답 순서가 바뀌는 공용 서버에서 정상 연결을 버리지 않게. 검토 1차 CONNECT-R1-02) |
| `ROOM_NOT_FOUND` | `mode=join` 인데 방에 아무도 없음 | 아니오 (연속 `JOIN_MISS_MAX` 회면 닫는다) | 입장 실패로 보고 |
| `ROOM_EXISTS` | `mode=create` 인데 이미 참가자가 있음 | 아니오 | 생성 실패로 보고 |
| `ROOM_FULL` | 정원 초과 | 아니오 | 입장 실패. 재접속 중이었다면 상한 간격으로 계속 시도한다([2.7](#27-재접속)) |
| `NAME_IN_USE` | 살아 있는 다른 연결이 같은 이름을 씀 | 아니오 | 입장 실패. 다른 이름으로 다시 하라고 안내한다. 재접속 중이었다면 상한 간격으로 계속 시도한다 |
| `PEER_NOT_FOUND` | `signal` 대상이 없음 | 아니오 | 그 피어와의 연결 시도를 즉시 끝낸다 |
| `RELAY_NOT_ALLOWED` | relay 후보가 든 `signal` | 아니오 | 해당 시도 실패. 버그 또는 설정 위반으로 기록 |
| `RATE_LIMITED` | 속도 제한 초과, 또는 없는 방 입장의 반복 | 예 | 입장 중이면 입장 실패. 아니면 `retry_after_ms` 뒤 재접속 |
| `REPLACED` | 같은 이름·같은 key 의 더 새로운 연결이 등록됨 | 예 | 이미 버린 소켓이면 무시한다. 지금 쓰는 소켓이면 끊김과 똑같이 다뤄 재접속한다. **치명이 아니다.** 첫 `join` 의 답으로 받았으면 입장 실패로 보고한다(재접속 루프는 등록된 뒤에만 돈다) |
| `SERVER_ERROR` | 서버 내부 실패 | 아니오 | 요청에 따라 다르다. `join`: 같은 연결에 다시 보낸다. `ping`: 놓친 것으로 센다([2.6](#26-heartbeat)). `signal`: 그 시도의 시그널을 다시 보낸다([3.3](#33-재전송-기한-실패)) |

- **종료 코드에는 의미를 두지 않는다.** 서버가 연결을 닫을 때 클라이언트가 보는 종료 코드를 서버가 고를 수 있는지 확인하지 않았다 **[가정 A-AWS-5]**. 게이트웨이가 스스로 닫을 때는 유휴 1001, 크기 초과 1009 였다 **[실측 PRE-AWS-07, 08]**. 닫기 전에 `error` 를 보내는 것이 유일한 사유 전달 수단이고, 이것도 최선 전달이다.
- **게이트웨이 프레임**: `type` 필드가 없는 서버 프레임은 프로토콜 메시지가 아니다. 공용 서버에서 본 것은 스로틀을 넘었을 때의 `{"message":"Too Many Requests"}` 다. 이때 연결은 유지되고 **그 메시지는 버려진다** **[실측 PRE-AWS-10]**. 프레임에 `re` 가 없어 어느 요청이 사라졌는지 알 수 없다. 그래서 그때의 상태로 다룬다.
  - `join` 응답을 기다리는 중이면: 1~2초(무작위) 뒤 같은 `join` 을 같은 연결에 다시 보낸다. 요청 기한(`SIGNAL_REQUEST_TIMEOUT_MS`)까지만 한다.
  - `ping` 응답을 기다리는 중이면: 그 `ping` 을 놓친 것으로 센다. 연결을 버리지 않는다.
  - 진행 중인 연결 시도가 있으면: 그 시도들의 시그널을 다시 보낸다.
  - 위 세 가지는 겹쳐서 적용한다. 본문은 로그에 남기지 않는다(길이와 건수만).
  - 길이 0 인 프레임은 무시하고 건수만 센다. 라우트 응답을 켠 API 에서는 메시지마다 빈 프레임이 왔다 **[실측 PRE-AWS-04]**. 이 설계는 라우트 응답을 만들지 않으므로 오지 않아야 한다([deployment.md 2.2](deployment.md#22-api-gateway-라우트)).
- **흔적 없이 사라지는 메시지**도 있다. 배포 직후 연달아 보낸 20건 중 2건이 접근 로그에 500 으로 남고 상대에게 도착하지 않았다. 원인은 모른다. 이후 260건에서는 없었다 **[실측 PRE-AWS-05]**. 그래서 계약은 유실을 전제로 한다([2.7](#27-재접속)).

### 2.6 heartbeat

- 클라이언트는 등록된 동안 `SIGNAL_PING_INTERVAL_MS` 마다 `ping` 을 보낸다. 응답은 **같은 `re` 의** `pong` 뿐이다. 다른 수신 활동은 응답으로 치지 않는다.
- `SIGNAL_PONG_TIMEOUT_MS` 안에 `pong` 이 없거나, 그 사이 게이트웨이 프레임이나 그 `ping` 의 `SERVER_ERROR` 를 받으면 **놓친 것**이다. 놓치면 `SIGNAL_PING_RETRY_MS` 뒤 다시 보낸다. 연속 `SIGNAL_PING_MISS_MAX` 회 놓치면 연결을 버리고 재접속한다. `pong` 을 받으면 횟수를 0 으로 돌린다.
- 한 번 놓쳤다고 재접속하지 않는 이유: 스로틀에 걸렸을 때 모든 클라이언트가 재접속·재등록하면 부하가 더 는다.
- `ping` 은 세 가지 일을 한다. (가) 공용 서버의 유휴 끊김을 막는다. (나) 서버가 참가자 기록을 살아 있다고 볼 근거(`lastSeenAt`)를 갱신한다. (다) 참가자 목록을 새로 받아 mesh 의 빈 연결을 메운다([3.1](#31-접촉-시작-규칙)).
- WebSocket ping 프레임은 쓰지 않는다. 프레임만으로도 유휴 끊김은 막혔지만 **[실측 PRE-AWS-07]**, (나)와 (다)를 하지 못한다.
- 서버는 타이머로 참가자를 지우지 않는다. 오래된 기록은 **읽을 때 걸러내고**, 인계·전송 실패 때 지운다. 공용 서버가 스스로 타이머를 돌릴 수 없기 때문이다. 자체 호스팅 조립은 추가로 주기 정리를 돌려 죽은 소켓을 닫지만, 판정 기준은 같은 `PARTICIPANT_STALE_MS` 다.

### 2.7 재접속

- **시그널링 연결과 DataChannel 은 수명이 독립이다.** 시그널링이 끊겨도 열린 DataChannel 을 닫지 않는다. 채팅은 계속된다.
- 끊김은 정상 사건이다. 원인이 서버 재시작이든, 공용 서버의 최대 연결 2시간 **[실측 `V-P4`: 119.99~120.00분에 끊김, 1.4초 안에 재등록, DataChannel 유지]**([이력](../../tests/test-history/2026-11-16-final-long.md)) 이든, 유휴 600초 **[실측 PRE-AWS-07]** 든 같은 절차를 쓴다.
- 재접속 담당 루프는 클라이언트에 하나만 둔다. 절차: 대기(위 표) → 접속 → `join(mode=resume, 같은 peer·sid·key, seq 는 1 올림)` → `joined.members` 로 mesh 보정.
- **재접속은 대부분 새 등록이다.** 공용 서버는 소켓이 닫히면 정상 종료든 강제 종료든 14~29ms 안에 종료 통지를 처리해 기록을 지웠다 **[실측 PRE-AWS-06]**. 인계는 옛 기록이 남아 있을 때만 일어난다(통지 누락, 아직 닫히지 않은 옛 소켓).
- 그래서 재접속하는 동안에는 **이름과 자리가 서버에서 비어 있다.** 그 사이 다른 참가자가 자리를 채우면 `ROOM_FULL`, 같은 이름의 다른 프로세스가 등록하면 `NAME_IN_USE` 를 받는다. 이때 **멈추지 않는다.** 상한 간격(30초)으로 계속 시도하고, 처음 한 번 사건으로 알린다. 열린 DataChannel 은 그대로다. 다른 참가자는 살아 있는 링크를 새 등록 때문에 닫지 않는다([3.2 교체 확인](#32-시그널별-처리)).
- 재접속을 멈추는 경우(**치명**)는 `UNSUPPORTED_VERSION` 하나다. 이때 시그널링 상태는 `detached` 가 되고 `get_status` 와 수신 사건으로 복구 방법과 함께 알린다. 열린 DataChannel 은 그대로 둔다.
- 전달 의미: 시그널 전달은 **최대 1회**이고 순서 보장이 없다. 재접속 뒤 재생은 없다. 유실은 **보낸 쪽이 시도 안에서 다시 보내** 메운다([3.3](#33-재전송-기한-실패)). 받는 쪽은 중복과 역순을 견딘다([3.2](#32-시그널별-처리)).

### 2.8 방 수명

- 서버에 "방" 기록은 없다. **살아 있는 참가자가 한 명 이상 있는 동안** 방이 있다.
- 마지막 참가자가 나가거나 오래되면 방은 없어진다. 같은 ID 로 다시 `create` 할 수 있다.
- 자체 호스팅 서버가 재시작하면 등록이 모두 사라진다. 참가자들이 `resume` 으로 다시 등록하면 방이 복구된다. 그 사이의 신규 `join` 은 `ROOM_NOT_FOUND` 를 받는다.
- 채팅 기록과 테스트 상태는 서버에 없다. 모든 참가자가 나가면 로컬 기록 파일에만 남는다.

## 3. WebRTC 연결 절차

토폴로지는 full mesh 다. 참가자 쌍마다 `PeerConnection` 하나와 DataChannel 하나를 둔다.

### 3.1 접촉 시작 규칙

- **받기는 `join` 을 보낸 순간부터 한다.** 클라이언트는 `join` 을 보내기 전에 mesh 와 시그널 처리기를 준비하고, `joined` 보다 먼저 온 `signal` 도 바로 처리한다. `signal` 을 **보내는** 것은 `joined` 를 받은 뒤다.
  - 이유: 공용 서버에서는 `joined` 와 다른 참가자의 `signal` 을 서로 다른 Lambda 가 보낸다. 서버는 참가자 기록을 먼저 쓰고 `joined` 를 보내므로, 그 사이 다른 참가자가 목록에서 입장자를 보고 보낸 `offer` 가 `joined` 보다 먼저 올 수 있다 **[추론. 콜드 스타트 640~990ms 와 따뜻한 전송 42ms 의 차이 PRE-AWS-04, 05]**. 그 `offer` 를 버리면 입장이 기한까지 멈춘다. 자체 호스팅 서버에서는 생기지 않는 순서다.
  - `joined` 전에 온 `offer` 는 바로 받아 pc 를 만들고 원격 설명을 적용한다. 그 결과로 내보낼 `answer` 와 후보는 **`joined` 를 받을 때까지 들고 있다가** 보낸다(최대 64건). 서버는 등록이 끝나기 전에 온 `signal` 을 `NOT_JOINED` 로 거절하기 때문이다. 입장이 실패하면 버린다.
- **대상**: 가장 최근 참가자 목록(`joined` 또는 `pong` 의 `members`)에 있고, 열린 링크가 없고, 진행 중인 시도가 없는 피어.
- **상대 `sid` 의 기준**: 링크의 상대 `sid` 는 **그 시도의 시그널에 서버가 붙여 준 `sid`** 다. offer 쪽은 `answer` 에 붙은 값, answer 쪽은 `offer` 에 붙은 값을 쓴다. 목록의 `sid` 는 대상을 고르는 데만 쓴다. 목록은 최대 30초 낡을 수 있기 때문이다.
- 열린 링크의 상대 `sid` 가 목록의 `sid` 와 다르고, 그 링크가 **그 목록을 요청하기 전에** 열린 것이면 상대가 다시 시작했을 수 있다. 링크를 바로 닫지 않는다. [3.2의 교체 확인](#32-시그널별-처리)을 하고, 확인에 실패했을 때만 닫고 대상에 넣는다.
- **방법**: 내 이름이 상대 이름보다 작으면 `offer` 를 보낸다. 크면 `offer-request` 를 보내고 상대의 `offer` 를 기다린다. **offer 는 항상 이름이 작은 쪽만 만든다.**
  - 근거: 양쪽이 동시에 offer 하면 채널이 열리지 않았다 **[실측 PRE-RTC-09]**. "작은 ID 가 offer" 규칙으로 4피어 mesh 와 재입장이 동작했다 **[실측 PRE-RTC-05, 09]**.
  - `offer-request` 는 이 설계가 더한 것이다 **[가정 A-RTC-2]**. 서버가 입장을 알리지 않으므로, 이름이 큰 쪽이 먼저 상대를 알게 된 경우 연결을 시작할 수단이 필요하다.
- **시점**: `joined` 를 받았을 때, 시그널링 재접속 직후, `pong` 을 받을 때마다, 링크가 닫히거나 시도가 실패한 직후(1초 뒤 1회. 그 뒤로는 `pong` 주기).
- 목록에 없는 피어에게는 시도하지 않는다. 열린 링크의 상대가 목록에 없어도 링크는 유지한다(상대의 시그널링만 끊긴 상태일 수 있다).
- **닿지 않음**: 같은 피어와의 시도가 `UNREACHABLE_AFTER_FAILS`(2)회 연속 실패하면 그 피어를 "닿지 않음"으로 표시하고 사건을 한 번 낸다([mcp-interface.md 3.4](mcp-interface.md#34-get_status)). 첫 실패 뒤 1초 만에 다시 시도하므로 약 31초 안에 알린다. 재시도는 `pong` 주기로 계속한다. `PEER_NOT_FOUND` 로 끝난 시도는 세지 않는다(상대가 떠난 것이다).

### 3.2 시그널별 처리

| 받은 것 | 처리 |
|---|---|
| (공통) `offer`·`answer`·`candidate` | `cid` 의 앞부분은 offer 쪽의 `sid` 여야 한다. offer 쪽이 나면 내 `sid`, 상대면 서버가 붙인 `sid` 다. 다르면 버린다 |
| `offer-request` (내 이름이 작음) | ① 그 피어와 진행 중인 시도가 있으면 **다시 보낸다.** answer 를 아직 못 받았으면 같은 `cid` 의 offer 와 후보 묶음, 받았으면 후보 묶음만. **예외:** answer 를 받은 시도인데 `offer-request` 에 서버가 붙인 `sid` 가 그 answer 의 `sid` 와 다르면 상대가 다시 시작한 것이다. 옛 상대와의 pc 는 새 상대와 열릴 수 없으므로 그 시도를 이벤트 없이 끝내고 새 `cid` 로 `offer` 를 보낸다(아래 "진행 중인 시도가 바뀌는 경우"와 같다. 검토 1차 CONNECT-R1-01). ② 열린 링크가 있으면 아래 "교체 확인"을 한다. ③ 둘 다 없으면 새 시도를 시작해 `offer` 를 보낸다 |
| `offer-request` (내 이름이 큼) | 무시하고 로그 |
| `offer` | ① `cid` 가 현재 시도와 같으면 중복이다. answer 를 이미 보냈으면 **answer 와 후보 묶음을 다시 보낸다**(상대가 answer 를 못 받았다는 뜻이다). `cid` 가 **열린 링크의 `cid` 와 같아도** 중복이다. 상대가 answer 를 받기 전에 다시 보낸 offer 가 늦게 온 것이므로 버린다(교체 확인을 하지 않는다. 검토 1차 CONNECT-R1-03). ② 같은 `sid` 에서 순번이 이미 본 값보다 작으면 무시한다(늦게 온 옛 offer). ③ 열린 링크가 있으면 "교체 확인"을 한다. ④ 그 밖에는 그 피어의 기존 pc 를 닫고 새 pc 로 받아 `answer` 를 같은 `cid` 로 보낸다. 대기 큐에 같은 `cid` 의 후보가 있으면 원격 설명을 적용한 뒤 넣는다. 닫은 pc 가 진행 중인 시도의 것이었으면 아래 "진행 중인 시도가 바뀌는 경우"를 따른다 |
| `answer` | 현재 시도의 `cid` 와 같고 아직 원격 설명이 없을 때만 적용한다. 이어서 시도 큐의 후보를 넣는다. 아니면 무시(같은 `cid` 의 중복 answer 는 답한 쪽의 재전송이다. [3.3](#33-재전송-기한-실패)) |
| `candidate` | 아래 "후보 처리" |
| `error{PEER_NOT_FOUND}` (`re` 가 내 `signal`) | 그 피어와의 시도를 `peer_gone` 으로 즉시 끝낸다 |
| `error{SERVER_ERROR}` (`re` 가 내 `signal`) | 그 시도의 시그널을 다시 보낸다([3.3](#33-재전송-기한-실패)) |
| 게이트웨이 프레임 | 진행 중인 모든 시도의 시그널을 다시 보낸다 |
| `error{RELAY_NOT_ALLOWED}` (`re` 가 내 `signal`) | 그 시도를 `ice` / `failed` 로 즉시 끝내고 pc 를 닫는다. 버그 또는 설정 위반으로 기록한다(로그 `link.attempt_end` 의 `error_code`). [3.3 의 실패 분류](#33-재전송-기한-실패)에 이 경우의 사유를 따로 두지 않는다 |

- 위 세 `error` 는 **그 `signal` 을 보낸 시도**에만 적용한다. 오류가 가리키는 `cid` 가 그 피어의 현재 시도와 다르면 옛 시도의 오류다. 버린다. `cid` 가 없는 `offer-request` 의 오류는 시도가 아직 `offer` 를 기다리는 중일 때만 본다.

**진행 중인 시도가 바뀌는 경우** (`offer` ④에서 닫은 pc 가 진행 중인 시도의 것일 때, 그리고 `offer-request` ①의 예외)

- 예: J 가 옛 B(`sid` b1)와 시도 중인데, 다시 시작한 B(`sid` b2)가 `offer b2.1` 을 보낸다. 또는 B 가 자기 시도를 먼저 끝내고 순번을 올려 다시 건다.
- offer 쪽도 같다: A 가 옛 B(`sid` b1)의 answer 를 받아 채널을 기다리는데, 다시 시작한 B(`sid` b2)가 `offer-request` 를 보낸다. A 는 그 시도를 끝내고 새 `cid` 로 offer 한다. 옛 후보 묶음만 다시 보내면 b2 는 `offer` 를 받지 못해 15초 뒤 `no_offer` 로, A 는 `ice_timeout` 으로 끝난다 **[검토 1차 CONNECT-R1-01 재현]**. `answer` 를 받기 전이면 상대 `sid` 를 모르고, 같은 offer 를 다시 보내면 b2 도 받을 수 있으므로 ①대로 한다.
- **이것은 시도의 끝이 아니다.** mesh 는 실패를 알리지 않는다(`attempt-failed` 없음). 받는 쪽에게는 그 피어와의 시도가 이어지는 것이다. 실패로 알리면 입장 중인 참가자는 [3.3](#33-재전송-기한-실패)의 "하나라도 실패하면 입장 전체 실패"로 방을 나가게 되는데, 새 pc 는 수십 ms 뒤에 열릴 수 있다.
- `PEER_CONNECT_TIMEOUT_MS` 는 **바뀐 때부터 새로 잰다.** 새 pc 가 열릴 시간을 온전히 준다. 남은 시간만 주면, 늦게 다시 시작한 상대와의 시도가 열리기 직전에 끝나는 일이 되풀이될 수 있다. 진단 값(후보 수, 재전송 횟수, 걸린 시간)도 바뀐 뒤의 것만 센다.
- 그래서 피어 하나와의 시도가 처음 시작한 때부터 15초를 넘겨 이어질 수 있다. 입장 기한(`JOIN_MESH_TIMEOUT_MS`)은 늘지 않는다([3.3](#33-재전송-기한-실패)).
- `offer-request` 를 보내고 기다리던 시도가 첫 `offer` 를 받는 것은 여기에 들지 않는다. 그 시도가 이어지는 것이고 기한을 새로 재지 않는다.

**후보 처리**

- 보내는 쪽: 로컬 후보를 `CANDIDATE_BATCH_MS`(100) 동안 모아 `candidate` 메시지 하나로 보낸다. ` typ relay` 는 넣지 않는다.
  - 근거: host 후보는 약 3ms, srflx 후보는 45~73ms 에 나왔다 **[실측 PRE-RTC-04]**. 100ms 면 보통 한 묶음에 든다. 묶으면 공용 서버의 호출 수와 순서 뒤바뀜이 함께 준다. 묶음 전송은 실측하지 않았다 **[가정 A-RTC-2]**.
- 받는 쪽은 `cid` 로 셋 중 하나를 고른다.
  1. `cid` 가 현재 시도와 같다 → 원격 설명이 있으면 넣는다. 없으면(offer 쪽이 answer 를 기다리는 중) **시도 큐**에 둔다.
  2. 현재 시도가 없거나 `cid` 가 다르고, 내가 answer 쪽이고, 순번이 그 `sid` 에서 지금까지 본 offer 의 순번보다 크다 → **아직 오지 않은 offer 의 후보**다. 피어별 **대기 큐**에 둔다. 대기 큐는 피어당 하나이고 가장 큰 순번의 `cid` 것만 담는다. 더 큰 순번이 오면 비우고 새로 시작한다. 더 작은 순번은 버린다. 첫 후보를 넣고 `PEER_CONNECT_TIMEOUT_MS` 가 지나면 비운다.
  3. 그 밖(옛 시도의 후보)은 버린다.
- 두 큐는 각각 최대 `CANDIDATE_QUEUE_MAX`(32)건이다. 같은 후보 문자열은 시도마다 한 번만 넣는다(재전송으로 중복이 온다). ` typ relay` 는 버린다.
- `offer-request` 를 보내고 기다리는 쪽은 `offer` 가 올 때 `cid` 를 처음 안다. 그 전에 온 후보는 2번 규칙으로 보관된다.
- 대기 큐가 필요한 이유: answer 쪽에는 `offer` 가 오기 전까지 그 `cid` 의 시도가 없다. "현재 시도와 같을 때만"으로 구현하면 먼저 온 후보를 버린다. 공용 서버에서는 20ms 간격으로 보낸 메시지도 3회 중 1회 순서가 바뀌었다 **[실측 PRE-AWS-05]**. 같은 PC 에서는 상대의 검사 패킷으로 주소를 알게 되어 연결될 수 있으나, 주소 제한형 NAT 뒤에서는 실패할 수 있다 **[추론, 미실측]**.

**교체 확인** (열린 링크가 있는 피어에게서 새 연결 요청이 왔을 때)

- 대상: 열린 링크가 있는데 그 피어 이름으로 `offer-request` 나 새 `cid` 의 `offer` 가 온 경우. 그리고 [3.1](#31-접촉-시작-규칙)의 `sid` 불일치. 열린 링크와 같은 `cid` 의 `offer` 는 대상이 아니다(중복으로 버린다).
- 그 링크로 P2P `ping` 을 바로 보낸다. `REPLACE_PROBE_MS`(2000) 안에 `pong` 이 오면 링크는 살아 있다. **요청을 버리고 링크를 유지한다.** 오지 않으면 링크를 닫고(`replaced`) 요청을 처리한다.
- 확인하는 동안 온 요청은 피어마다 가장 새 것 하나만 들고 있는다.
- 이유:
  - 살아 있는 참가자가 같은 이름의 다른 프로세스에게 링크를 뺏기지 않는다. 시그널링만 끊긴 참가자의 이름을 서버에서 다른 프로세스가 차지할 수 있다([2.7](#27-재접속)).
  - 늦게 도착한 옛 `offer-request` 가 멀쩡한 링크를 끊지 않는다.
  - 상대가 실제로 링크를 잃었다면 내 `ping` 도 답을 받지 못하므로 2초 뒤 교체된다. 상대 프로세스가 죽고 새 프로세스가 들어온 경우도 같다.
- 열린 링크를 새 pc 로 바꾸는 동작의 안전성은 확인이 필요하다 **[가정 A-RTC-3]**.

그 밖의 규칙:

- 내 참가자 목록에 없던 피어가 보낸 `offer` 와 `offer-request` 도 받는다. 서버는 같은 방의 참가자에게만 전달하므로, 도착했다는 것이 같은 방이라는 보증이다(동시 입장, 끊긴 사이의 입장, `joined` 보다 먼저 온 시그널).
- 시도 큐 근거: 원격 설명 적용 전에 candidate 를 넣어 실패한 사례가 참조 프로젝트에 있다 **[소스]**.
- ICE 재시작은 쓰지 않는다. 실패하면 pc 를 닫고 새 시도를 한다. 새 pc 재연결은 157~340ms 였다 **[실측 PRE-RTC-09]**.

### 3.3 재전송, 기한, 실패

**재전송.** 시그널은 사라질 수 있다([2.4](#24-오류-코드)). 시도가 열리기 전까지 보낸 쪽이 다시 보낸다. 받는 쪽 처리는 모두 여러 번 받아도 결과가 같다([3.2](#32-시그널별-처리)).

| 시도의 상태 | `SIGNAL_RESEND_MS`(3000)마다 다시 보내는 것 |
|---|---|
| `offer-request` 를 보냈고 `offer` 를 못 받음 | `offer-request` |
| `offer` 를 보냈고 `answer` 를 못 받음 | 같은 `cid` 의 `offer` 와 후보 묶음(지금까지 모은 전부) |
| `answer` 를 주고받았고 채널이 아직 안 열림 (offer 쪽) | 후보 묶음 |
| `answer` 를 보냈고 채널이 아직 안 열림 (answer 쪽) | 처음 만든 `answer` 와 후보 묶음 |

- 바로 다시 보내는 계기: 게이트웨이 프레임, 내 `signal` 에 대한 `SERVER_ERROR`. 한 시도에서 `SIGNAL_RESEND_MIN_GAP_MS`(1000)보다 자주 하지 않는다.
- **새 `cid` 를 만들지 않는다.** 같은 `cid` 를 다시 보내야, 먼저 보낸 것이 이미 도착한 경우에 상대가 만든 pc 를 버리지 않는다.
- 총 기한은 늘리지 않는다. 주기 재전송은 한 시도에 최대 4회다(15초 / 3초).
- 진단 값 `resends`(`attempt-failed` 의 `diag`, 로그 `signal.resend`)는 **다시 보낸 횟수를 계기와 상관없이 합한 수**다. 주기 재전송(최대 4회)에 더해 게이트웨이 프레임·`SERVER_ERROR` 계기, 받은 `offer-request` 에 대한 다시 보내기(3.2 ①), 중복 `offer` 에 대한 `answer` 다시 보내기가 든다. 그래서 4를 넘을 수 있다. 상대가 `offer-request` 를 계속 보내면 offer 쪽 값이 8이 됐다 **[실측 W3b]**. 계기는 로그의 `cause` 로 가린다.
- 근거: 유실 2/20 과 스로틀 폐기 **[실측 PRE-AWS-05, 10]**. 참조 프로젝트에도 answer 를 5초 기다렸다가 다시 하는 장치가 있다 **[소스]**. 3초라는 값은 **[제안]** 이다.
- 재전송한 `offer` 로 상대가 `answer` 를 다시 만들지는 않는다. 처음 만든 `answer` 를 그대로 다시 보낸다.
- **answer 쪽도 `answer` 를 주기마다 다시 보낸다(검토 1차, 총괄 결정 V-P7 나 2-가).** 답한 쪽은 자기 `answer` 가 닿았는지 알 수 없고, offer 쪽은 `answer` 를 받아야 채널을 연다. 예전에는 offer 쪽의 `offer` 재전송(→ 중복 `offer` 에 대한 `answer` 다시 보내기)에만 기댔는데, 공용 서버 스로틀 아래에서는 그 `offer` 재전송도 함께 사라질 수 있다 **[실측 W9 P-W9P-08]**. 받는 쪽(offer 쪽)은 같은 `cid` 의 중복 `answer` 를 무시하므로 결과가 같다. 주기와 횟수(3초, 최대 4회)는 다른 상태와 같고, 시도당 서버 호출은 주기마다 1건 늘어난다(후보 묶음과 함께 보낸다).

**기한**

| 이름 | 값 | 근거 |
|---|---|---|
| `PEER_CONNECT_TIMEOUT_MS` | 15000 (시도 시작 → DataChannel open) | 라이브러리는 "응답 없음"을 스스로 실패 처리하지 않고, 도달 불가도 39.5초 뒤에야 알린다 **[실측 PRE-RTC-07]**. 같은 PC 연결은 11~25ms **[실측 PRE-RTC-03]**. 실제 NAT 에서의 시간은 미실측(A-RTC-1) |
| `HELLO_TIMEOUT_MS` | 5000 (open → 상대 `hello`) | **[가정]** |
| `JOIN_MESH_TIMEOUT_MS` | 20000 (`joined` 수신 → 모든 필수 링크 동기화 완료) | 15초 + 여유 5초. 접속·등록 기한과 합쳐도 40초로, 알려진 가장 짧은 tool 호출 한도 60초 **[실측 PRE-MCP-05, 문서 PRE-ALT-08]** 안이다 |
| `REPLACE_PROBE_MS` | 2000 | **[제안]** P2P `pong` 은 같은 PC 에서 수 ms 다. 실제 망의 왕복 시간은 미실측 |

**실패 분류.** 시도가 열리지 못하고 끝나면 mesh 가 단계와 사유를 알린다.

| 단계 `stage` | 사유 `reason` | 뜻 |
|---|---|---|
| `signaling` | `no_offer` | `offer-request` 를 다시 보냈는데도 `offer` 가 오지 않았다 |
| `signaling` | `no_answer` | (offer 쪽) `offer` 를 다시 보냈는데도 `answer` 가 오지 않았다. (answer 쪽) `answer` 를 보낸 뒤 ICE 는 `connected`·`completed` 가 됐는데 기한 안에 채널이 열리지 않았다. 내 `answer` 가 상대에 닿지 않은 것으로 본다 |
| `signaling` | `peer_gone` | 서버가 `PEER_NOT_FOUND` 를 돌려줬다 |
| `ice` | `ice_timeout` | `offer` 와 `answer` 는 오갔지만 기한 안에 채널이 열리지 않았다. answer 쪽은 기한에 ICE 가 `connected`·`completed` 가 아닐 때만 이 분류다 |
| `ice` | `failed` | pc 상태가 `failed` 또는 `closed` 가 됐다 |
| `session` | `hello_timeout`, `hello_mismatch`, `version`, `sync_timeout` | 채널은 열렸지만 P2P 절차가 끝나지 않았다. 이 단계는 `room-session` 이 판정한다([4절](#4-p2p-datachannel-계약)) |

- **`signaling` 단계의 실패는 직접 경로가 없다는 뜻이 아니다.** 상대 프로세스가 멈췄거나, 유령 기록이거나, 시그널이 거듭 사라진 것이다. 직접 연결이 안 된다고 볼 수 있는 것은 `ice` 단계다. 에이전트에게 주는 안내를 나눈다([mcp-interface.md 3.2](mcp-interface.md#32-join_room)).
- **answer 쪽의 `no_answer`.** answer 쪽은 자기 `answer` 가 도착했는지 알 수 없다. offer 쪽은 `answer` 를 받아야 DTLS·SCTP 를 시작하므로, `answer` 가 거듭 사라지면 answer 쪽은 ICE 가 연결된 채 채널을 못 연다. 이것을 `ice` 로 나누면 직접 경로가 있는데 "직접 경로가 없다"고 안내하게 된다 **[실측 W9 P-W9P-08: 공용 서버 스로틀 아래 answer 쪽 `ice_state: connected` 인데 `ice`/`ice_timeout`, 같은 쌍의 offer 쪽은 `no_answer`]**. 그래서 기한에 ICE 가 연결돼 있으면 `signaling`/`no_answer` 로 나눈다(Gate 3). 검토 1차부터는 answer 쪽도 주기마다 `answer` 를 다시 보낸다(위 재전송 표).
- pc 상태가 `failed` 또는 `closed` 가 되면 기한을 기다리지 않고 실패 처리한다. 두 상태를 모두 처리한다 **[실측 PRE-RTC-06]**.
- 서버가 `RELAY_NOT_ALLOWED` 를 돌려준 시도도 `ice` / `failed` 다([3.2](#32-시그널별-처리)). relay 후보는 설정과 mesh 의 필터가 막으므로 결함이 있을 때만 나온다. 사유를 따로 만들지 않고 "pc 가 닫혔다"에 넣었다. `peer_gone` 이 아니므로 필수 목록에서 빠지지 않고 연속 실패로 센다.
- 진행 중인 시도가 새 `cid` 로 바뀌는 것은 실패가 아니다. 표의 어느 사유도 내지 않는다([3.2](#32-시그널별-처리)).
- 닫은 pc 의 콜백이 늦게 올 수 있다 **[실측]**. 모든 콜백은 "현재 시도인가"를 먼저 검사한다.
- **입장 중 실패는 입장 전체의 실패다.** `joined.members` 의 모든 피어(필수 목록)와 `JOIN_MESH_TIMEOUT_MS` 안에 링크가 열리고 동기화가 끝나야 입장 성공이다. 하나라도 실패하면 `leave` 를 보내고 모든 링크를 닫은 뒤 오류를 돌려준다.
  - 필수 목록에서 빼는 경우: 그 피어에 대해 `PEER_NOT_FOUND` 를 받았다. 그 피어가 `bye{leave|shutdown}` 을 보냈다.
  - `mode=join` 인데 필수 목록이 모두 빠지고 열린 링크도 없으면 `ROOM_NOT_FOUND` 로 끝낸다. 아무도 없는 방에 들어간 것이기 때문이다([2.3](#23-서버-처리-규칙)의 없는 방 동시 입장).
  - 상대의 P2P 버전이 달라서 실패했으면 `PEER_VERSION_MISMATCH` 로 따로 돌려준다. 직접 연결 실패와 원인이 다르다.
  - `JOIN_MESH_TIMEOUT_MS` 에 **아직 시도 중인** 필수 피어가 있으면 그 시도를 그 자리에서 끝낸다(`mesh.expireAttempt`). mesh 는 기한이 찼을 때와 같은 분류(`no_offer`, `no_answer`, `ice_timeout`)로 알린다. 도중에 바뀐 시도([3.2](#32-시그널별-처리))는 자기 기한이 입장 기한보다 늦을 수 있어서다. 바뀌지 않은 시도는 15초 안에 끝나므로 이 경우에 닿지 않는다.
- 입장 **뒤에** 목록에 나타난 피어와의 연결 실패는 입장을 되돌리지 않는다. [3.1](#31-접촉-시작-규칙)의 "닿지 않음"으로 알린다.
- TURN, 서버 중계, 다른 피어를 통한 중계로 바꾸는 경로는 없다.

### 3.4 DataChannel 설정

- 채널은 offer 쪽이 만든다. 라벨 `agent-chat`. 순서 보장, 신뢰 전송(기본값. `maxRetransmits`·`maxPacketLifeTime` 을 주지 않는다) **[실측 PRE-RTC-08]**.
- 쌍마다 채널은 하나다. 모든 P2P 메시지가 이 채널을 쓴다.

## 4. P2P DataChannel 계약

### 4.1 봉투

텍스트 메시지 하나가 JSON 객체 하나다. 공통 필드는 `v`(=1)와 `t`(타입)다.

- **발신자는 봉투가 아니라 링크로 정한다.** 수신 쪽은 그 DataChannel 이 연결된 피어 이름(시그널링에서 서버가 붙인 `from`)을 발신자로 쓴다. 본문에 적힌 이름을 믿지 않는다.
- 한 프레임은 **직렬화한 뒤** `P2P_MAX_FRAME_BYTES`(65536) 이하다. 라이브러리 기본 한도는 262144바이트이고 초과 전송은 예외가 난다 **[실측 PRE-RTC-08]**.
- `v` 가 내 것과 다른 프레임을 받으면 `bye{version}` 을 보내고 링크를 닫는다. 저장소를 다른 날 설치한 PC 끼리는 버전이 다를 수 있다.

### 4.2 타입

| `t` | 필드 | 방향·시점 | 의미 |
|---|---|---|---|
| `hello` | `peer`, `sid`, `wall`, `client{name,version}`, `observer?` | 채널이 열리면 양쪽이 먼저 보낸다 | 신원 확인. `peer`·`sid` 가 이 시도의 시그널에 서버가 붙인 값([3.1](#31-접촉-시작-규칙))과 다르면 링크를 닫는다. `wall` 은 시계 차이 경고에만 쓴다. `observer` 는 관전자 표시다(불리언. 선택 필드. [4.6](#46-관전자)). 새 구현은 늘 싣는다(참가자 `false`, 관전자 `true`). 없으면 관전자를 모르는 구버전이다 |
| `state` | `records[]`, `snap?` | 스냅샷(`snap: true`)과 기록이 생길 때마다의 변경 | 공유 상태 기록 묶음([5절](#5-공유-상태-모델과-병합-규칙)) |
| `sync_end` | `count`, `test_id?`, `test_elapsed_ms?`, `sf?` | 스냅샷을 다 보낸 뒤 1회 | "내가 가진 기록을 모두 보냈다". `test_id` 와 `test_elapsed_ms` 는 보내는 쪽의 현재 테스트와, **보내는 순간** 그 테스트의 경과 시간(0 이상의 정수, ms)이다. 둘은 함께 싣는다. 테스트가 없으면 둘 다 뺀다. 받는 규칙은 [5.5](#55-파생-판정)에 있다. `sf` 는 **답으로 보내는 `sync_end` 에만** 싣는다. 상대 스냅샷을 병합한 뒤에 뜬 내 스냅샷의 지문이다([5.4](#54-동기화-절차)) |
| `chat` | `id`, `to`, `text`, `wall`, `rr?` | 에이전트가 보낼 때 | 채팅. `to` 가 `null` 이면 방 전체, 이름 배열이면 대상 지정. `rr: true` 는 읽음 확인 요청이다(선택 필드. [4.3](#43-채팅-전달)) |
| `ack` | `id`, `read?` | `chat` 을 받은 쪽 | 수신 확인. `read: true` 는 읽음 확인이다(선택 필드. `rr` 을 단 글에만) |
| `ping` | `n`, `sc`, `sf` | 5초마다. 교체 확인 때는 즉시 | 링크 생존 확인. `sc` 는 내 복제본의 기록 수, `sf` 는 지문이다([5.4](#54-동기화-절차)) |
| `pong` | `n` | `ping` 을 받으면 즉시 | `ping` 의 `n` 을 돌려준다 |
| `bye` | `reason` (`leave`\|`shutdown`\|`version`\|`protocol_error`) | 링크를 닫기 직전 | 의도한 종료임을 알린다 |

"제어"(중단 요청, 제한 도달)는 별도 타입이 아니라 `state` 의 `stop` 기록이다. 재입장자도 스냅샷으로 받아야 하기 때문이다. "presence"는 `state` 의 `presence` 기록과 링크 사건(`hello`, `bye`, 끊김)의 조합이다.

### 4.3 채팅 전달

- **채팅은 작성자가 각 수신자에게 직접 보낸다. 다른 피어가 대신 전달하지 않는다.** 링크가 없는 피어는 받지 못하고, 보낸 쪽은 그 사실을 결과로 받는다.
- 대상 지정 메시지는 대상에게만 보낸다. 방 전체 메시지는 열린 링크 전부에 보낸다.
- `ack` 의 뜻: 수신 쪽이 형식을 검증하고, 중복을 걸렀고, **로컬 기록 파일에 쓰기를 요청했고 수신함(inbox)에 넣었다.** 에이전트가 읽었다는 뜻이 아니다.
- 보낸 쪽은 수신자별로 `CHAT_ACK_TIMEOUT_MS`(5000) **[가정]** 를 기다린다. 결과는 수신자별로 `delivered` / `not_connected` / `ack_timeout` 이다. `ack_timeout` 은 **결과 불명**이다. 실패 확정이 아니다.
- 자동 재전송과 끊긴 동안의 보관(outbox)은 없다. 에이전트가 `send_message` 의 `resend_of` 로 **같은 `id`** 를 다시 보낼 수 있다. 이미 받은 쪽은 중복으로 걸러내고 `ack` 만 다시 보낸다.
- **읽음 확인(점검 전용, 2026-11-16).** `ping_room` 이 보내는 점검 글에만 `rr: true` 를 단다. 받는 쪽은 보통 `ack` 를 바로 보내고, 그 사건을 자기 에이전트가 처음 꺼내 갔을 때(wait·confirm 결과 또는 채널) `ack{id, read: true}` 를 한 번 더 보낸다. 두 필드 모두 선택 필드라 `v` 는 그대로다. 구버전은 모르는 필드를 버리므로 `rr` 을 단 글을 보통 글로 받고(읽음 확인이 오지 않는다), `read` 를 단 `ack` 는 이미 받은 `ack` 로 본다(아무 일도 없다). 보낸 쪽은 `read` 를 단 `ack` 를 전달 판정에 쓰지 않는다.
- 한 피어에 대해 확인받지 못한 `chat` 이 50건을 넘으면 그 피어로의 새 전송은 즉시 `not_connected` 로 실패한다(느린 피어 보호) **[제안]**.
- **속도 제한** **[제안]**: 보내는 쪽은 60초에 `CHAT_SEND_RATE_MAX`(60)건까지만 보낸다. 넘으면 보내지 않고 tool 오류로 돌려준다. 받는 쪽은 한 피어에게서 60초에 120건을 넘게 받으면 넘는 것을 버리고 잘못된 프레임으로 센다([4.4](#44-중복순서크기)). 규칙을 지키는 발신자는 받는 쪽 한도에 닿지 않는다. 한 참가자가 다른 PC 의 수신함과 기록 파일을 채우지 못하게 하는 것이다.

### 4.4 중복·순서·크기

- **중복 제거**: 수신 쪽은 최근 `SEEN_ID_CAPACITY`(4096)개의 `chat.id` 를 기억한다. 이미 본 `id` 는 수신함에 넣지 않고 `ack` 만 보낸다.
- **자기 메시지**: 자기가 보낸 메시지는 자기 수신함에 넣지 않는다. 이름이 자기와 같은 발신자의 프레임은 버린다.
- **순서**: 한 발신자의 메시지는 보낸 순서로 도착한다(채널이 보장). 서로 다른 발신자 사이의 전체 순서는 없다. 수신함 순서는 도착 순서다. `wall` 은 표시용이다.
- **크기**: `chat.text` 는 UTF-8 `CHAT_MAX_TEXT_BYTES`(16384) 이하 **[제안]**. 그리고 **직렬화한 `chat` 프레임**이 `P2P_MAX_FRAME_BYTES` 이하여야 한다. 따옴표나 제어 문자가 많으면 직렬화하면서 길어지기 때문이다. 둘 중 하나라도 넘으면 **보내기 전에** `INVALID_ARGUMENT` 로 거절한다. 그래서 전송 단계의 크기 초과는 생기지 않는다. 두 검사는 `protocol` 의 `encodeP2PFrame` 이 한다. 받는 쪽과 같은 스키마로 먼저 보고(`BAD_FRAME`), 직렬화한 크기를 본다(`FRAME_TOO_LARGE`). 받는 쪽이 거절할 프레임을 만들지 않는다. 시그널링의 `encodeClientMessage` 와 `encodeServerMessage` 도 같은 방식이다([2.3](#23-서버-처리-규칙)).
- `state` 프레임은 49152바이트를 목표로 기록을 나눠 담는다. 기록 하나는 직렬화해 32768바이트 이하라([5.1](#51-기록)) 항상 한 프레임에 든다.
- **스냅샷과 변경은 `protocol` 의 `packStateFrames` 로 나간다.** 이 함수도 기록마다 받는 쪽과 같은 검증(스키마, 글자 필드 4096바이트, 기록 32768바이트)을 먼저 한다. 하나라도 걸리면 프레임을 하나도 만들지 않고 `BAD_FRAME` 으로 실패한다. 받는 쪽은 걸린 기록만 버리므로([5.3](#53-병합)), 그대로 보내면 보낸 쪽은 성공으로 알고 받는 쪽만 그 기록이 없어 지문이 계속 어긋난다. 검증을 통과한 값을 싣는다. 모르는 필드는 실리지 않는다.
- **잘못된 프레임**: JSON·스키마 위반과 크기 초과는 버리고 건수를 센다. 1분에 5건을 넘으면 `bye{protocol_error}` 를 보내고 링크를 닫는다.

### 4.5 링크 생존 판정

| 이름 | 값 | 근거 |
|---|---|---|
| `P2P_PING_INTERVAL_MS` | 5000 | ICE 만으로는 상대 소실 감지에 약 27초가 걸린다 **[실측 PRE-RTC-06]** |
| `P2P_DEAD_AFTER_MS` | 15000 (마지막 생존 증거 이후) | 2초/6초 설정에서 5.4~7.2초에 감지했다 **[실측 PRE-RTC-15]** |

- 판정 타이머는 기한(마지막 생존 증거 + `P2P_DEAD_AFTER_MS`)보다 100ms 먼저 건다(`mesh` 의 `DEAD_TIMER_LEAD_MS`). 기한에 딱 맞춰 걸면 타이머가 늦게 깨는 몫(같은 PC 의 4~6 프로세스에서 1~3ms)과 증거를 처리한 지연만큼, 상대가 죽은 때부터 15초를 넘겨 끊김을 알게 된다. 앞당기기 전 `V-L4` 에서 SIGKILL 뒤 15002ms 를 봤다 **[실측 W9, [이력](../../tests/test-history/2026-11-15-w9-assembly.md)]**. 그래서 "15초 안에 끊김으로 본다"가 지켜지게 했다. ping 주기(5초)에 견주면 작은 값이라 멀쩡한 링크를 닫는 일은 늘지 않는다 **[추론]**.
- 생존 증거는 두 가지다. (가) **자기 `ping` 에 대한 `pong`**(`n` 이 같다). (나) 받은 `state` 와 `sync_end` 프레임.
  - (나)를 치는 이유: 채널이 하나이고 순서를 지키므로 `pong` 이 큰 스냅샷 프레임 뒤에 줄을 선다. 느린 회선에서 스냅샷이 15초 넘게 걸리면 `pong` 만 보는 판정은 멀쩡한 링크를 닫고, 다시 열어 또 전체를 보내는 일을 되풀이한다 **[추론, 실제 망 미실측]**.
  - `chat` 과 `ack` 는 증거로 치지 않는다.
- 링크가 닫힌 뒤의 처리. 참가자 표시는 [mcp-interface.md 3.4](mcp-interface.md#34-get_status)가 정한다.

| 사건 | 이후 |
|---|---|
| `bye{leave\|shutdown}` 수신 | 재시도하지 않는다 |
| 생존 증거 없음, pc `failed`/`closed`, 채널 닫힘 | 상대가 참가자 목록에 있으면 [3.1](#31-접촉-시작-규칙)대로 다시 시도한다 |
| `hello` 불일치, `protocol_error` | 다음 시그널링 `pong` 주기에 다시 시도한다 |
| `bye{version}` 수신, 또는 `v` 불일치로 내가 닫음 | **그 `sid` 와는 다시 시도하지 않는다.** 상대가 새 `sid` 로 다시 들어오면 시도한다. 입장 중이면 `PEER_VERSION_MISMATCH` 다([3.3](#33-재전송-기한-실패)) |

### 4.6 관전자

사람이 콘솔에서 방을 지켜보는 참가자다. 진입점과 출력은 [architecture.md 3.14](architecture.md#314-monitor) 가 정한다. **[사용자 요청 2026-11-16. 구현 2026-11-16. `V-U12`, `V-L13`, `V-P8`]**

서버는 채팅을 지나보내지 않고(2절), 다른 참가자도 채팅을 대신 전하지 않는다([4.3](#43-채팅-전달)). 그래서 관전자도 **같은 시그널링으로 들어와 기존 참가자 전원과 DataChannel 을 직접 연다.** 서버나 다른 참가자를 거쳐 채팅을 받는 경로는 만들지 않는다. TURN·중계도 없다.

**표시: `hello.observer`**

- 선택 필드 추가다. P2P `v` 는 1 그대로다(2.2 의 "뜻이 바뀌지 않는 변경은 선택 필드 추가"). **시그널링 와이어는 바뀌지 않는다.** 서버는 관전자를 모르고 보통 참가자로 등록한다. 공용 서버를 다시 배포하지 않는다.
- 새 구현은 `hello` 에 `observer` 를 **늘 싣는다**(참가자 `false`, 관전자 `true`). 필드가 없으면 상대는 관전자를 모르는 구버전이다(아래 호환). 구버전은 모르는 필드를 버린다(`z.object` 의 기본 동작. 스키마를 바꾸지 않아도 받는다).
- 관전자인지는 **링크마다 그 링크의 `hello` 로** 안다. 서버 목록(`joined`·`pong` 의 `members`)에는 표시가 없어 `hello` 전에는 알 수 없다.
- 자기 신고다. 관전자라고 속여도 할 수 있는 일이 줄 뿐이다(아래 받는 쪽 처리). 참가자라고 속인 관전자는 보통 참가자다. 참가자가 프로토콜을 따르는 협력 관계라는 가정([5.3](#53-병합))은 그대로다.

**관전자가 하는 것과 하지 않는 것**

| 일 | 관전자 | 이유 |
|---|---|---|
| 시그널링 `join` | `mode=join` 만 쓴다. 방을 만들지 않는다 | 빈 방을 지켜볼 일이 없다. 관전자만 있는 방을 만들지 않는다 |
| 입장 판정 | 참가자와 같다. `joined.members` 전원과 기한(`JOIN_MESH_TIMEOUT_MS`) 안에 연결·동기화해야 하고, 하나라도 실패하면 나간다([3.3](#33-재전송-기한-실패)) | 채팅은 작성자가 각 수신자에게 직접 보낸다. 링크가 없는 참가자의 글은 볼 수 없으므로 "일부만 보는 관전"을 만들지 않는다 |
| `hello` | `observer: true` | |
| `chat` | **보내지 않는다** | 읽기 전용이다 |
| `ack` | 받은 `chat` 마다 참가자와 같이 보낸다 | 보낸 쪽이 `ack_timeout`(결과 불명)을 받지 않게 한다 |
| `state` 변경 | **보내지 않는다.** `presence` 도, 기한의 `stop{time_limit}`([5.5](#55-파생-판정))도 쓰지 않는다 | 공유 상태에 기록을 쓰지 않는다. 기한 중단은 기한을 본 참가자가 쓴다 |
| 스냅샷 교환, `sync_end`(경과 시간 포함), `ping` 의 `sc`·`sf` | 참가자와 같다. 받은 기록을 병합한 복제본 전체를 보낸다 | 지문 비교([5.4](#54-동기화-절차) 5번) 때문이다. 관전자가 빈 스냅샷을 보내면 지문이 늘 달라, 상대가 30초마다 교환을 시작하고 "진전 없음" 경고(`state_diverged`)를 낸다. 관전자의 복제본에는 남이 쓴 기록만 있다. 이것은 기존 참가자끼리의 스냅샷과 같은 상태 복제이고([5.4 상태 복제와 채팅 중계의 구분](#54-동기화-절차)) 채팅은 들어 있지 않다. 경과 시간은 큰 값만 따르는 규칙이라 관전자의 값이 실제로 흐른 시간을 넘지 않는다([5.5](#55-파생-판정)) |
| 중단을 병합했을 때의 즉시 교환(5.4 의 6번) | 참가자와 같다 | 위와 같다. 새 기록을 만들지 않는다 |
| `bye` | 사용자가 끝내면 `bye{shutdown}`. 재시도 대상이 아니다(4.5) | |

**받는 쪽의 처리** (관전자를 아는 참가자. 링크의 `hello.observer` 가 `true`)

| 관전자 링크에서 받은 것 | 처리 |
|---|---|
| `chat` | 참가자의 글과 같이 받아 `ack` 하고 기록 파일과 수신함에 넣는다. 수신함 사건은 `data.observer: true` 다(사람이 관전 콘솔에서 쓴 글. 2026-11-16 부터. 그 전에는 버리고 잘못된 프레임 `observer_chat` 으로 셌다. 옛 버전 참가자는 여전히 그렇게 센다) |
| `state` 변경(`snap` 없음) | 기록을 모두 버리고 잘못된 프레임으로 센다(코드 `observer_write`) |
| `state` 스냅샷 | 받는다. 다만 `author` 가 그 관전자인 기록은 버리고 병합의 `ignored` 로 센다(5.3 의 받을 때의 검증) |
| `hello`, `sync_end`, `ping`, `pong`, `ack`, `bye` | 참가자와 같다 |

- **관전자는 참가자로 세지 않는다.** `get_status` 의 `participants` 에서 빼고 `observers` 에 싣는다. 준비 표시(`shown_as`), `waiting_for_you`, 기록 도달 범위(`sent_to`·`not_connected`), 경고와 `notice` 의 `unreachable` 에 들지 않는다([mcp-interface.md 3.4](mcp-interface.md#34-get_status)).
- **채팅 송신은 관전자를 다른 수신자와 같이 다룬다.** 방 전체 글은 동기화된 링크 전부에 가므로([4.3](#43-채팅-전달)) 관전자에게도 간다. 관전자의 `ack` 는 결과의 `delivered` 에 실린다. 대상 지정 글은 대상에게만 간다. 관전자를 대상으로 지정할 수는 있다. 관전자도 글을 보낼 수 있다(사람이 콘솔에서 입력한 지시). 관전자의 글 송신은 참가자와 같은 규칙(직접 전송, `ack`, 속도 상한)이다.
- 관전자 링크가 동기화까지 열릴 때마다 수신함 사건 `peer` / `observer_joined`, 닫힐 때마다 `peer` / `observer_left`(`data.reason` 은 닫힌 사유)를 넣는다. **감시받는다는 사실을 숨기지 않는다.** 관전자 링크가 닫혀도 `disconnected`·`left` 사건은 내지 않는다(참가자 사건이 아니다).
- 관전자의 이름 규칙은 참가자와 같다(1절. 예약 이름 금지, 방 안에서 유일). 기본 이름은 `observer-<무작위 4자>` 다.

**관전자가 볼 수 없는 것 (한계)**

- **대상 지정 채팅**(`to` 가 이름 배열)은 대상에게만 간다. 관전자가 대상이 아니면 보지 못한다.
- **관전자가 들어오기 전의 채팅.** 서버와 참가자는 채팅을 저장하거나 다시 보내지 않고, 스냅샷에 채팅이 없다(5절 머리). 공유 상태(테스트, 시나리오, 주장, 검증, 중단, `presence`)는 스냅샷으로 받으므로 들어온 때의 모습을 본다.
- **정원.** 관전자도 `ROOM_MAX_PEERS`(8) 가운데 하나를 차지한다. 서버가 관전자를 모르기 때문이다.
- **직접 연결.** 기존 참가자 가운데 하나라도 직접 연결이 안 되면 관전자 입장이 실패한다(`DIRECT_CONNECT_FAILED`).
- **나중에 들어오는 참가자에게 관전자는 입장 필수 피어다.** 입장자는 `hello` 를 받기 전에는 목록의 누가 관전자인지 모른다. 그 입장자가 관전자와 직접 연결하지 못하면 그 `join_room` 이 `DIRECT_CONNECT_FAILED` 로 실패하고 `peers` 에 관전자 이름이 실린다. 관전자를 끝내면 풀린다. 시그널링 `join` 에 표시를 더하면 피할 수 있지만 서버 와이어와 공용 서버를 바꿔야 해서 이번에는 하지 않았다 **[제안]**.
- **관전자 혼자 남은 방.** 참가자가 모두 나가도 관전자가 있는 동안 서버에서 방이 살아 있다([2.8](#28-방-수명)). 같은 ID 의 `create` 는 `ROOM_EXISTS` 다. 관전자는 계속 지켜본다(참가자가 다시 들어올 수 있다). 끝내는 것은 사람이 한다.
- **구버전 참가자에게는 감시 사실이 알려지지 않는다**(아래 호환).

**구버전과의 호환**

| 조합 | 일어나는 일 |
|---|---|
| 새 관전자 ↔ 구버전 참가자(`hello.observer` 가 없다) | 구버전은 관전자를 보통 참가자로 본다. 관전자는 `presence` 를 쓰지 않으므로 그 참가자의 `get_status` 에 `status: null`, `shown_as: not_ready` 인 참가자로 보이고 관전자 사건도 없다. 관전자가 채팅과 변경을 보내지 않으므로 상태와 채팅은 깨지지 않는다. 관전자 쪽은 `hello.observer` 가 없는 상대마다 한 번 "이 참가자는 관전자를 모른다(감시 사실이 그쪽에 표시되지 않는다)"는 알림(`system` / `observer_unaware`)을 낸다 |
| 새 참가자 ↔ 구버전 참가자 | 서로 보통 참가자다. 새 참가자의 `hello.observer: false` 는 구버전이 버린다. 바뀌는 것 없음 |
| 관전자 ↔ 관전자 | 서로를 관전자로 본다. 링크는 맺는다(full mesh). 둘 다 채팅과 변경을 보내지 않는다 |

## 5. 공유 상태 모델과 병합 규칙

서버가 테스트 상태를 저장하지 않으므로, 참가자가 각자 복제본을 갖고 서로 맞춘다. 목표는 두 가지다. (가) 모든 참가자가 같은 목표·역할·제한·검증 기록을 본다. (나) 재입장자가 현재 목표와 역할 현황을 받는다.

**채팅 본문은 공유 상태가 아니다.** 늦게 들어온 참가자에게 지난 채팅을 주지 않는다.

### 5.1 기록

모든 기록의 공통 필드: `kind`, `author`(작성자 이름), `lc`(논리 시각), `wall`(작성자의 벽시계 ms, 표시용), `body`. 기록은 두 종류다.

- **키 기록**: `key` 로 식별한다. 같은 키에는 값이 하나만 남는다(last-writer-wins).
- **추가 기록**: `rid`(고유 ID)로 식별한다. 한 번 쓰면 바꾸지 않는다. 모든 복제본의 합집합이 전체다.

| kind | 종류·식별 | 쓸 수 있는 사람 | body |
|---|---|---|---|
| `presence` | 키 `presence/<peer>` | 그 `peer` 본인만 | `client`, `tools[]`, `role`, `status`(`joined`\|`ready`\|`working`\|`left`), `listening`, `note` |
| `test` | 키 `test` | 누구나. **방에 `test` 기록이 없을 때만** | `test_id`, `request`, `started_wall`, `max_duration_min`, `max_scenarios` |
| `stop` | 추가 | 누구나 | `test_id`, `reason`(`user`\|`time_limit`), `detail` |
| `scenario` | 추가 | 누구나 | `test_id`, `title`, `plan`, `actor?`, `verifier?` |
| `claim` | 추가 | 작성자가 곧 행동한 사람 | `test_id`, `scenario`, `action`, `expected`, `observed`, `outcome`(`pass`\|`fail`), `steps` |
| `verification` | 추가 | **주장 작성자가 아닌 사람** | `test_id`, `claim`, `result`(`confirmed`\|`refuted`\|`unable`), `evidence` |

역할은 **본인이 자기 `presence` 에 쓴다.** 다른 참가자의 역할을 대신 쓸 수 없다. 누구도 지휘자가 아니다. 역할 합의는 채팅으로 한다.

**상한** **[제안]**

| 이름 | 값 | 거는 곳 |
|---|---|---|
| 글자 필드 하나 | UTF-8 4096바이트 | 입력 검증 |
| `STATE_RECORD_MAX_BYTES` | 32768 (기록 하나를 직렬화한 크기) | 입력 검증. 넘으면 기록을 만들기 전에 `INVALID_ARGUMENT` |
| `STATE_MAX_RECORDS` | 2000건 | **로컬 쓰기만** |
| `STATE_MAX_BYTES` | 1048576 (복제본 전체의 직렬화 크기 합) | **로컬 쓰기만** |
| `STATE_MERGE_MAX_RECORDS` | 4096건 | 병합(링크 보호) |

- **상한은 로컬 쓰기에만 건다.** 복제본이 `STATE_MAX_RECORDS` 나 `STATE_MAX_BYTES` 에 닿으면 새 `scenario`·`claim`·`verification` 을 거절한다(`STATE_FULL`). "닿는다"는 기록 수가 이미 `STATE_MAX_RECORDS` 이상이거나, 그 쓰기로 직렬화 크기 합이 `STATE_MAX_BYTES` 를 넘게 되는 것이다. 그래서 상한이 걸린 기록의 로컬 쓰기는 복제본을 그 크기 위로 올리지 않는다.
- **`presence`, `test`, `stop` 은 상한과 무관하게 쓸 수 있다.** 상태가 꽉 찼다고 중단 요청이나 입장이 막히면 안 되기 때문이다. `presence` 는 이름마다 하나, `test` 는 방에 하나, `stop` 은 참가자마다 많아야 하나라 수가 작다.
- **병합은 유효한 기록을 항상 받는다.** 상한 때문에 받은 기록을 버리면 참가자마다 다른 기록을 버리게 되어 복제본이 영구히 갈린다. 그래서 동시에 쓴 기록이 합쳐지면 상한을 조금 넘을 수 있다(많아야 참가자 수 − 1건).
- `STATE_MERGE_MAX_RECORDS` 는 규칙을 따르는 참가자끼리는 닿지 않는 값이다. 받은 기록으로 복제본이 이 수를 넘게 되면 프로토콜 위반으로 보고 `bye{protocol_error}` 로 그 링크를 닫는다.
- 자동 삭제는 없다. 방 하나에 테스트는 한 번이므로([5.5](#55-파생-판정)) 옛 테스트의 기록이 쌓이지 않는다. 상한에 닿았으면 새 방에서 한다.
- 바이트 상한의 근거: 스냅샷은 링크가 열릴 때마다 전부 간다. 1MiB 는 1Mbps 회선에서 약 8초다. 입장 기한 20초 안에 들게 한 값이다 **[추론, 실제 망 미실측]**.

### 5.2 논리 시각

`lc = max(지금까지 본 가장 큰 lc + 1, 현재 벽시계 ms)`.

- 어떤 값을 **본 뒤에 쓴** 기록은 시계가 어떻든 그 값보다 크다.
- 서로 못 보고 동시에 쓴 경우에만 벽시계가 순서에 영향을 준다. 동률은 `author` 문자열 비교로 가른다.
- **범위.** `lc` 와 `wall` 은 0 이상 `2^53 − 1`(안전 정수의 끝. `protocol` 의 `STATE_CLOCK_MAX`) 이하의 정수다. 스키마가 그 밖의 값을 거절한다. 그 위에서는 1 을 더해도 값이 바뀌지 않아 위 성질이 깨진다.
- 정상 시계로는 끝에 닿지 않는다. 벽시계가 낼 수 있는 가장 큰 값(8.64e15)이 더 작고, 거기서 1 씩 올려 닿으려면 3.6e14 번을 써야 한다.
- **끝에 닿았을 때.** 지금까지 본 가장 큰 `lc` 가 `2^53 − 1` 이면 다음 기록을 만들 수 없다. 그 쓰기를 `INVALID_ARGUMENT` 로 거절하고 이상으로 기록한다. **값을 접거나 낮춰 쓰지 않는다.** 그러면 본 뒤에 쓴 기록이 지는 일이 조용히 생긴다. 이 상태는 결함이나 위조로 만든 기록 하나를 병합했을 때만 생긴다. 기록은 지워지지 않고 스냅샷으로 퍼지므로, 그 방에서는 그 뒤로 누구도 기록을 쓸 수 없다(`presence`, `stop` 포함). 새 방에서 해야 한다. 위조를 막는 것은 [범위 밖](README.md#6-범위-밖)이다 **[제안. 설계에 없던 경우를 구현 전에 정했다. [W0 이력](../../tests/test-history/2026-11-15-w0-contracts.md)의 PROTOCOL-IMPL-R2-03]**.

### 5.3 병합

- 키 기록: `(lc, author)` 가 더 큰 쪽을 남긴다.
- 추가 기록: `rid` 가 없으면 넣는다. 있고 내용이 같으면 버린다.
- 식별자가 같은데 내용이 다르면(키 기록은 `(lc, author)` 까지 같을 때) **정규 직렬화한 바이트**(키를 정렬한 JSON 의 UTF-8)를 비교해 작은 쪽을 남기고 이상으로 기록한다. "먼저 온 것을 유지"로 하면 도착 순서에 따라 결과가 달라지기 때문이다.
- 병합은 **교환·결합·멱등**이다. 같은 묶음을 여러 번, 어떤 순서로 받아도 결과가 같다. 상한이 병합에 끼어들지 않으므로([5.1](#51-기록)) 이 성질이 상한 근처에서도 유지된다.

받을 때의 검증:

| 검사 | 위반 시 |
|---|---|
| **변경**(`snap` 이 없는 `state`)의 `author` 가 그 링크의 피어와 같은가 | 버리고 건수를 센다 |
| 그 링크가 **관전자** 링크(`hello.observer: true`)인데 변경이 왔는가 | 모두 버리고 잘못된 프레임으로 센다([4.6](#46-관전자)) |
| 관전자 링크에서 온 **스냅샷**에 `author` 가 그 관전자인 기록이 있는가 | 그 기록만 버린다(`ignored`) |
| `presence` 의 키가 `presence/<author>` 인가 | 버린다 |
| `verification.author` 가 대상 `claim.author` 와 다른가 | 저장은 하되 **판정에서 뺀다** (자기 검증 무효) |
| 스키마와 크기 | 버린다 |

스냅샷(`snap: true`)에는 다른 사람이 쓴 기록이 들어 있다. 재입장자에게 떠난 참가자의 기록까지 전하려면 필요하다. 그래서 스냅샷의 `author` 는 링크 피어와 달라도 받는다. **이 설계는 참가자가 프로토콜을 따르는 협력 관계라고 가정한다.** 스냅샷에 남의 기록을 위조해 넣는 참가자는 막지 못한다(서명 없음, [범위 밖](README.md#6-범위-밖)).

### 5.4 동기화 절차

**스냅샷 교환.** 한 링크에서 스냅샷을 주고받는 한 번을 "교환"이라 한다. 링크가 열릴 때의 첫 동기화와 그 뒤의 재동기화가 같은 규칙을 쓴다.

- **보내기(시작)**: 가진 **모든 기록**을 `state{snap: true}` 프레임들로 보내고 `sync_end`(`sf` 없음)를 보낸다. 보낸 쪽은 그때부터 상대의 `sync_end` 를 **기다린다.** 기다림은 상대의 `sync_end` 를 하나 받으면 끝난다. `RESYNC_MIN_GAP_MS` 가 지나도 끝난다. 기다리는 중에 다시 보내도 기다림을 새로 시작하지 않는다.
- **답하기**: 기다리는 중이 **아닐 때** 상대가 시작한 스냅샷과 `sync_end` 를 받으면, 병합한 뒤 자기 스냅샷과 `sync_end{sf}` 로 **한 번** 답한다. `sf` 는 그 스냅샷의 지문이다.
- 기다리는 중에 받은 `sync_end` 에는 답하지 않는다. 양쪽이 동시에 시작한 경우다.
- **`sf` 가 있는 `sync_end` 는 답이다. 답에는 어느 경우에도 답하지 않는다.** 그래서 교환은 되풀이되지 않는다.
- 한쪽만 시작해도 양쪽이 서로의 기록을 모두 받는다.

**절차**

1. 링크가 열리면 양쪽이 `hello` 를 보낸다.
2. 이어서 양쪽이 각자 스냅샷을 보낸다(첫 동기화). 받은 프레임을 처리하기 전에 보내므로 양쪽이 동시에 시작한 교환이 된다.
3. 상대의 `sync_end` 를 받으면 그 링크는 "동기화됨"이다.
4. 이후 로컬에서 기록이 생기면 열린 모든 링크에 `state` 로 보낸다(변경). 받은 쪽은 그것을 다른 링크로 넘기지 않는다.
5. **지문 비교.** P2P `ping` 에 내 복제본의 기록 수 `sc` 와 지문 `sf` 를 싣는다. 받을 때마다 내 값과 비교한다. `STATE_DIVERGE_PINGS` 회 연속 다르고, 그 링크의 **재동기화 간격**이 지났으면 교환을 시작한다. 양쪽이 각자 판단한다.
6. **중단은 기다리지 않는다.** 복제본이 **병합으로** "중단됨"([5.5](#55-파생-판정))이 되는 순간, 그 기록을 받은 링크를 뺀 열린 모든 링크에서 교환을 바로 시작한다. 재동기화 간격과 무관하다. 변경으로 받았든 스냅샷으로 받았든 같다. "중단됨"은 한 번만 되므로 복제본마다 테스트당 한 번이다. 로컬에서 쓴 `stop` 은 4번대로 열린 모든 링크에 변경으로 간다.

**재동기화 간격과 진전 판정**

| 이름 | 값 | 뜻 |
|---|---|---|
| `STATE_DIVERGE_PINGS` | 2 | 연속으로 달라야 하는 `ping` 수. 가는 중인 변경 때문에 잠깐 다른 것을 거른다 **[제안]** |
| `RESYNC_MIN_GAP_MS` | 30000 | 재동기화 간격의 기본값 **[제안]** |
| `RESYNC_MAX_GAP_MS` | 300000 | 재동기화 간격의 상한 **[제안]** |

- 간격은 링크마다, 그 링크의 양쪽이 각자 갖는다. **내가 그 링크에서 마지막으로 스냅샷을 보낸 때**(시작이든 답이든)부터 잰다. 답하기와 6번은 간격을 따지지 않는다.
- **재동기화는 멈추지 않는다.** 간격만 바뀐다. 그 링크가 어떤 기록을 받을 유일한 길일 수 있기 때문이다.
- **진전 판정**은 답(`sync_end{sf}`)을 받은 쪽이 그것을 병합한 직후에 한 번 한다. 그때 양쪽은 서로의 스냅샷을 모두 받은 상태다. 판정 시점이 이 한 순간으로 고정돼 있다. 그 뒤의 `ping` 에서 다시 다르다는 것은 판정에 쓰지 않는다.

| 답을 병합한 직후 | 판정 | 그 뒤 |
|---|---|---|
| 내 지문이 `sf` 와 같다 | **맞음** | 간격을 기본값으로 되돌린다 |
| 다르다. 나는 기다리는 중이었고, 기다리기 시작한 뒤로 내 복제본에 **다른 곳에서 들어온 기록**(로컬 쓰기, 다른 링크의 병합)이 없었다 | **진전 없음**. 주고받아도 없어지지 않는 차이다 | 간격을 2배로 늘린다(상한 `RESYNC_MAX_GAP_MS`). 이상으로 기록하고 `state_diverged` 사건과 `get_status` 경고를 낸다(링크마다 한 번) |
| 다르다. 그 밖의 경우(기다리는 동안 다른 곳에서 기록이 들어왔다. 또는 기다리는 중이 아니었다) | 판정하지 않는다 | 간격 그대로 |

- `sf` 가 없는 `sync_end`(동시에 시작한 교환)로는 판정하지 않는다.
- 같은 링크에서 상대가 보낸 변경은 "다른 곳에서 들어온 기록"이 아니다. 상대가 답의 스냅샷을 뜨기 전에 쓴 것이라 그 스냅샷에도 들어 있다.
- `ping` 의 지문이 한 번이라도 같으면 그 링크의 간격을 기본값으로 되돌리고 경고를 거둔다.
- **교환 뒤에 새로 생긴 차이는 진전 없음이 아니다.** 새 불일치로 5번을 다시 탄다. 다른 참가자가 계속 기록을 쓰는 동안에도 간격은 늘지 않고 경고도 나지 않는다.
- 진전 없음은 규칙을 따르는 참가자끼리는 생기지 않는다. 한쪽이 검증에서 버리는 기록([5.3](#53-병합))을 상대가 갖고 있을 때, 곧 버그나 위조에서만 생긴다. 그런 링크에서 같은 스냅샷을 30초마다 끝없이 보내지 않으려고 간격을 늘린다.

**그 밖**

- **지문**: 기록마다 식별 문자열을 만든다(추가 기록은 `rid`, 키 기록은 `key`·`lc`·`author`). 그것을 정렬해 이은 것의 SHA-256 앞 12자리다. 보고서의 "상태 지문"과 같은 값이다.
- **5번이 필요한 이유.** 변경은 작성자가 자기 링크로만 보낸다. 작성자와의 링크가 끊긴 참가자는 그 변경을 받지 못한다. 작성자가 방을 떠나면 그 링크는 다시 열리지 않는다. 지문 비교가 없으면, 멀쩡한 링크로 이어진 두 참가자의 복제본이 달라도 맞출 계기가 없다([5.6](#56-사례)의 "작성자가 떠난 경우", "한 쌍만 끊긴 경우").
- **6번이 필요한 이유.** 5번만으로는 중단이 늦게 닿는다. 직전에 교환이 있었던 링크에서는 간격이 지날 때까지, 간격이 늘어난 링크에서는 몇 분까지 기다린다. 그동안 끊긴 쪽의 `start_scenario` 가 계속 성공한다. 중단은 실행 통제의 수단이라 다른 기록과 같은 지연을 받아들이지 않는다.
- 양방향으로 전부 보내므로, 끊겼다 다시 붙은 두 피어도 서로 빠진 기록을 채운다.
- 입장자는 **첫 동기화가 끝난 뒤에** 자기 `presence` 를 쓴다. 이유는 5.6의 재입장 사례에 있다.
- 비용: 참가자 N명이면 입장자가 같은 기록을 최대 N−1번 받는다. 6번 때문에 중단 때 참가자마다 스냅샷을 (열린 링크 수 − 1)번 더 보낸다. 8명이 모두 이어져 있으면 방 전체로 42번이다. 테스트당 한 번이다. 복제본 크기에 상한이 있어([5.1](#51-기록)) 받아들인다.

**작성자와 링크가 없는 참가자에게 닿는 시간** **[추론. 규칙에서 계산한 값이다. 실측하지 않았다]**

작성자와 받는 쪽이 서로 끊겨 있고, 둘 다 다른 참가자 한 명과 이어져 있을 때다. 링크를 여러 번 건너야 하면 건널 때마다 더해진다.

| 기록 | 걸리는 시간 |
|---|---|
| `stop` (6번) | 링크 하나를 더 건너는 시간. 스냅샷이 작으면 1초 안이다. 상한(1MiB)에 가까운 스냅샷을 1Mbps 회선으로 보내면 약 8초다. 그 링크의 직전 교환이나 늘어난 간격과 무관하다 |
| 그 밖의 기록 (5번). 그 링크에서 직전 30초 안에 교환이 없었다 | `ping` 두 번. 약 10초 |
| 그 밖의 기록 (5번). 직전 30초 안에 교환이 있었다 | 그 교환에서 30초가 지난 뒤의 첫 `ping`. 최대 약 35초. 작성자가 계속 기록을 쓰는 동안에는 이 경우가 보통이다 |
| 그 밖의 기록. 진전 없음으로 간격이 늘어난 링크 | 최대 약 5분 |

**상태 복제와 채팅 중계의 구분**

- **채팅(`chat`)은 어떤 경우에도 작성자와 수신자를 잇는 링크로만 간다.** 링크가 없으면 가지 않고, 보낸 쪽은 `not_connected` 를 받는다. 스냅샷과 재동기화에는 채팅이 들어 있지 않다. 채팅을 다른 피어로 돌리는 경로는 없다.
- 공유 상태는 모든 참가자가 같은 사본을 갖기로 한 자료다. 스냅샷은 처음부터 남이 쓴 기록을 담는다. 재동기화(5번, 6번)는 같은 스냅샷 교환을 열린 링크에서 한 번 더 하는 것이다. 새 전달 경로도 새 메시지 종류도 생기지 않는다. 6번도 받은 기록 하나를 골라 넘기는 것이 아니라 스냅샷 전체를 다시 맞추는 것이다.
- 그 결과, A–B 링크가 끊긴 동안 B 가 쓴 `stop` 은 C 의 복제본을 거쳐 A 에게 닿는다. 이것은 직접 연결에 실패한 두 참가자의 **대화를 이어 주는 중계가 아니다.** A 와 B 사이의 채팅은 여전히 전달되지 않는다.
- 제어 기록(`stop`, `test`)만 맞추도록 좁히지 않은 이유: 주장과 검증이 빠지면 참가자마다 판정과 보고서가 달라진다. 그리고 재입장자에게는 이미 스냅샷으로 전부 준다. 기록의 글자 필드도 함께 간다는 점은 받아들인다. `send_message` 는 상태 기록을 만들지 않으므로 채팅이 이 길로 새지 않는다.

### 5.5 파생 판정

복제본에서 계산하는 값이다. 저장하지 않는다. 기한을 뺀 나머지는 같은 기록 집합이면 모든 참가자가 같은 답을 낸다.

| 판정 | 규칙 |
|---|---|
| 현재 테스트 | 키 `test` 의 값. 없으면 "테스트 없음". **방 하나에 테스트는 한 번이다.** `test` 기록이 있으면 진행 중이든 중단됐든 새 테스트를 시작할 수 없다. 동시에 시작한 둘은 키 기록이라 하나만 남는다 |
| 중단됨 | 현재 `test_id` 의 `stop` 기록이 하나라도 있다. **한 번 중단되면 되돌릴 수 없다** |
| 중단 시점 | 현재 `test_id` 의 `stop` 기록 가운데 `(lc, author, rid)` 가 가장 작은 것 |
| 기한 | 각 참가자가 아래 "경과 시간"으로 잰다. `max_duration_min` 을 넘으면 그것을 본 참가자가 `stop{time_limit}` 을 쓴다 |
| 유효 시나리오 | 현재 `test_id` 의 `scenario` 를 `(lc, author, rid)` 로 정렬한 앞쪽 `max_scenarios` 개. 그 뒤는 **한도 초과**로, 주장을 받을 수 없다 |
| 주장 상태 | 유효한 `verification`(작성자 ≠ 주장 작성자) 중 `refuted` 가 있으면 **반박됨**. 없고 `confirmed` 가 있으면 **확인됨**. 둘 다 없으면 **미확인** |
| 중단 뒤 기록 | 주장의 `lc` 가 중단 시점의 `lc` 보다 크다 |
| 보고 분류 | **중단 뒤 기록**인 주장은 따로 분류하고 성공·실패에 세지 않는다. 그 밖에서, 성공 = `outcome=pass` 이고 확인됨. 실패 = `outcome=fail` 이고 확인됨, 또는 `outcome=pass` 인데 반박됨. 나머지는 미확인 |

**경과 시간.** 기한 판정에 PC 사이의 시계 차이를 쓰지 않는다.

- 각 프로세스는 현재 테스트에 대해 두 값을 기억한다. **기준 시각**(자기 벽시계의 한 시점)과 **이미 흐른 시간**(기준 시각까지 테스트가 흐른 시간)이다. 경과 시간 = 이미 흐른 시간 + (지금 자기 벽시계 − 기준 시각).
- **처음 알았을 때.** `test` 기록이 내 복제본의 현재 테스트가 되는 순간에 이미 흐른 시간을 0 으로, 기준 시각을 지금으로 둔다. 내가 시작했든, 변경으로 받았든, 스냅샷으로 받았든 같다. 동시에 시작한 둘 가운데 진 쪽이 이긴 테스트로 넘어갈 때도 같다.
- **보낼 때.** `sync_end` 마다 내 현재 테스트의 `test_id` 와 보내는 순간의 경과 시간(`test_elapsed_ms`)을 싣는다. 테스트가 없으면 둘 다 싣지 않는다.
- **받을 때.** `sync_end` 를 받을 때마다 같은 규칙을 쓴다. 입장, 재입장, 다시 열린 링크의 첫 동기화, 테스트 도중의 재동기화, 답을 가리지 않는다.
  1. 받은 `test_id` 가 내 현재 테스트와 다르면 무시한다.
  2. 받은 값이 **지금 내 경과 시간보다 클 때만**, 이미 흐른 시간을 받은 값으로, 기준 시각을 지금으로 **함께** 바꾼다. 작거나 같으면 무시한다.
- **두 값을 함께 바꾸는 이유.** 받은 값은 상대가 잰 "지금까지 흐른 시간"이다. 기준 시각을 그대로 두고 이미 흐른 시간만 바꾸면 (지금 − 기준 시각)이 한 번 더 더해진다. 테스트 10분째에 10분을 받으면 20분이 된다. 스냅샷 교환은 테스트 도중에도 일어난다. 링크가 닫혔다 다시 열릴 때 하고, 부분 mesh 에서는 30~35초마다 한다([5.4](#54-동기화-절차)). 그때마다 값이 불어나면 테스트가 제한보다 훨씬 일찍 중단되고, 중단은 되돌릴 수 없다.
- **`test_id` 를 함께 보는 이유.** 보낸 쪽의 현재 테스트가 내 것과 다를 수 있다. 서로 닿지 않는 동안 각자 테스트를 시작한 두 참가자가 다시 이어졌을 때다. 둘 가운데 하나만 남는데, 진 쪽은 자기 스냅샷을 보낼 때 아직 그것을 모른다. 진 테스트가 30분 먼저 시작됐다면, `test_id` 를 보지 않으면 남은 테스트의 경과 시간이 30분 는다. 큰 값만 따르는 규칙이라 한 번 늘어난 값은 줄지 않고 다른 참가자에게 퍼진다.
- 이 규칙에서 나오는 성질 **[추론. 규칙에서 끌어낸 것이다. `V-U3` 으로 확인한다]**:
  - 같은 값을 여러 번 받아도, 두 참가자가 서로의 값을 번갈아 받아도 경과 시간이 불어나지 않는다. 받은 값은 건너오는 동안 흐른 시간만큼 뒤져 있어서, 이미 맞춰진 참가자의 값보다 크지 않다.
  - 입장자는 0 에서 시작해, 받은 값 가운데 가장 큰 것을 따라간다.
  - 받은 값 때문에 경과 시간이 줄지 않는다.
  - 벽시계가 도중에 바뀌지 않고 시계 빠르기가 같으면, 어느 참가자의 경과 시간도 테스트가 시작된 뒤 실제로 흐른 시간을 넘지 않는다. 모자랄 수만 있다.
- `started_wall` 은 표시용이다. 판정에 쓰지 않는다.
- 벽시계끼리 비교하지 않는 이유: `started_wall + 제한` 을 각자의 벽시계와 비교하면, 시계가 70분 앞선 PC 는 60분짜리 테스트를 받자마자 `stop{time_limit}` 을 쓴다. 중단은 되돌릴 수 없으므로 그 PC 한 대가 방의 테스트를 시작하자마자 끝낸다.
- 오차: 받은 값은 스냅샷이 건너오는 시간만큼 뒤진다. PC 마다 시계 빠르기도 조금 다르다. 합쳐서 수 초로 본다 **[추론]**. 가장 먼저 기한에 닿은 참가자가 `stop` 을 쓰고, 전파되면 모두 중단된다.
- 한계 **[추론]**: 경과 시간은 각자의 벽시계로 잰다. 테스트 도중에 한 PC 의 벽시계가 앞으로 바뀌면(수동 변경, 큰 시각 보정) 그 PC 의 경과 시간이 그만큼 는다. 큰 값을 따르는 규칙이라 그 값이 다음 교환에서 다른 참가자에게 퍼지고, 테스트가 그만큼 일찍 끝난다. 뒤로 바뀌면 그 PC 의 값만 작아진다. 다른 참가자가 제때 `stop` 을 쓴다. 0 보다 작은 값은 0 으로 센다.

**중단 뒤 기록의 판정.** `lc` 는 "본 뒤에 쓰면 더 크다"만 보장한다. 중단을 본 뒤에 쓴 주장은 반드시 중단 뒤 기록이 된다. 중단을 아직 못 본 채 거의 동시에 쓴 주장은 시계에 따라 어느 쪽으로도 갈 수 있다. 이 차이는 받아들인다. 판정 자체는 모든 복제본에서 같다.

### 5.6 사례

| 사례 | 일어나는 일 | 결과 |
|---|---|---|
| **두 참가자가 동시에 `start_test`** | 키 `test` 에 두 값. `(lc, author)` 가 큰 쪽이 남는다 | 진 쪽의 `test_id` 로 쓴 기록은 현재 테스트가 아니므로 판정에서 빠진다. 진 쪽 에이전트는 "테스트가 바뀌었다"는 수신 사건을 받는다 |
| **중단 뒤 `start_test`** | `test` 기록이 이미 있다 | 거절한다. 제한을 다시 정하려면 새 방에서 시작해야 한다([mcp-interface.md 3.9](mcp-interface.md#39-start_test)) |
| **한도 직전에 두 참가자가 동시에 `start_scenario`** | 둘 다 자기 복제본에서는 한도 안이라 성공한다. 합쳐지면 한도+1 | 정렬 순서가 뒤인 시나리오가 "한도 초과"가 된다. 그 작성자는 수신 사건을 받고, 그 시나리오로는 `record_claim` 이 거절된다 |
| **한 주장에 확인과 반박이 함께** | 둘 다 남는다 | 반박됨으로 분류한다. 보고서에 두 증거를 모두 싣는다 |
| **중단과 새 시나리오가 동시에** | `stop` 과 `scenario` 가 둘 다 남는다 | 중단됨이 이긴다. 시나리오는 기록에 남지만, 이후 새 시나리오는 모두 거절된다 |
| **중단 뒤에 쓴 주장** | 이미 있는 시나리오 ID 로 `claim` 이 온다 | 받는다. "중단 뒤 기록"으로 분류해 보고서에 따로 싣고 성공·실패에 세지 않는다 |
| **재입장** | 재입장자는 빈 복제본으로 시작한다. 링크마다 스냅샷을 받는다 | `test`, `stop`, 시나리오, 주장, 검증, 모든 `presence` 를 받는다. `join_room` 결과에 현재 목표와 역할 현황을 싣는다 |
| **재입장자의 옛 `presence`** | 스냅샷에 재입장자 자신의 옛 `presence`(예: `left`)가 들어 있다 | 재입장자는 동기화 뒤에 새 `presence` 를 쓰므로 `lc` 가 옛 값보다 크다. 먼저 쓰면 시계가 뒤로 간 PC 에서 옛 값에 질 수 있다 |
| **떠난 참가자의 기록** | 작성자가 방에 없어도 다른 참가자의 복제본에 남아 있다 | 재입장자와 신규 입장자가 스냅샷으로 받는다 |
| **작성자가 떠난 경우** | A–B 링크가 끊긴 사이 B 가 `stop` 을 쓰고 방을 떠난다. `stop` 은 C 에만 갔다. A–C 링크는 멀쩡해 다시 열리지 않는다 | C 가 `stop` 을 병합하는 순간 A–C 링크에서 교환을 시작한다(5.4의 6번). A 가 `stop` 을 받는다. `stop` 이 아닌 기록이었다면 A 와 C 의 지문이 다르므로 5번으로 맞춰진다 |
| **한 쌍만 끊긴 경우** | A–B 가 서로 닿지 않는 채로 방에 남는다(둘 다 C 와는 이어져 있다) | A 와 B 가 쓴 기록은 C 와의 재동기화로 서로에게 닿는다(약 10~35초). `stop` 은 바로 닿는다. A–B 사이의 채팅은 가지 않는다. 양쪽 `get_status` 가 상대를 "닿지 않음"으로 보인다 |
| **끊긴 쌍의 한쪽이 계속 기록을 쓴다** | 위 상태에서 B 가 몇 초마다 기록을 쓴다. A–C 교환이 끝난 직후에 B 의 새 기록이 C 에 도착하는 일이 되풀이된다 | 교환 뒤에 생긴 차이는 진전 없음으로 세지 않는다. A–C 의 간격은 30초 그대로이고 재동기화가 계속된다. `state_diverged` 는 나지 않는다. A 는 B 의 기록을 최대 약 35초 늦게 받는다. 이 상태에서 B 가 쓴 `stop` 도 6번으로 바로 A 에게 닿는다 |
| **맞출 수 없는 차이** | 한쪽이 검증에서 버리는 기록을 상대가 갖고 있다(버그나 위조) | 답을 받은 쪽이 진전 없음으로 판정한다. 그 링크의 간격이 30초 → 60초 → 120초 → 240초 → 300초로 늘고 경고가 난다. 재동기화는 멈추지 않으므로 받을 수 있는 기록은 계속 받는다. `stop` 은 간격과 무관하게 간다 |
| **상한 직전의 동시 쓰기** | 복제본이 1999건일 때 두 참가자가 하나씩 쓴다. 합치면 2001건 | 둘 다 받는다. 복제본은 2001건으로 같아진다. 이후 로컬 쓰기는 `STATE_FULL`. `stop` 은 계속 쓸 수 있다 |
| **식별자는 같고 내용이 다른 기록** | 버그나 위조로만 생긴다 | 모든 참가자가 직렬화 바이트가 작은 쪽을 남긴다. 이상으로 기록한다 |
| **시계가 앞선 PC** | 그 PC 가 쓴 키 기록의 `lc` 가 크다 | 동시 쓰기에서 그 PC 가 이긴다. 그 값을 본 다른 PC 가 나중에 쓰면 `lc+1` 이므로 다시 이긴다. 영구히 덮어쓰지 못하는 일은 없다 |
| **시계가 크게 다른 PC 와 시간 제한** | 시계가 70분 앞선 PC 가 60분 제한의 테스트를 받는다 | 기한은 각자의 경과 시간으로 재므로 바로 중단되지 않는다. `hello.wall` 로 본 차이가 60초를 넘으면 `get_status` 에 경고를 싣는다. 기록의 `wall`(표시용)이 어긋난다는 뜻이다 **[가정 A-TIME-1]** |
| **테스트 도중에 경과 시간을 다시 받는다** | 60분 제한의 테스트 10분째에 A–C 링크가 닫혔다 다시 열린다. 양쪽 `sync_end` 가 10분을 싣는다. 부분 mesh 에서는 A–C 가 30~35초마다 교환하며 같은 일을 되풀이한다 | 받은 값이 자기 경과 시간보다 크지 않으므로 양쪽 모두 무시한다. 경과 시간은 10분 그대로다. 몇 번을 주고받아도 불어나지 않고, 테스트는 60분에 끝난다 |
| **서로 닿지 않는 동안 각자 시작한 테스트** | A 가 테스트를 시작한다. 30분 뒤, A 와 닿지 않는 B 가 따로 시작한다. 그 뒤 A–B 링크가 열린다 | `(lc, author)` 가 큰 쪽이 남는다. 진 쪽이 보낸 `sync_end` 는 `test_id` 가 달라 무시된다. 진 테스트의 30분이 남은 테스트의 경과 시간에 섞이지 않는다. 진 쪽은 남은 테스트를 처음 안 것으로 0 에서 시작하고, 상대의 값이 더 크면 따른다 |
| **링크가 끊긴 동안 생긴 기록** | 끊긴 쌍은 서로의 변경을 못 받는다 | 그 링크가 다시 열리면 전체 동기화로 채운다. 다시 열리지 않으면 다른 링크의 재동기화로 채운다 |

## 6. 서버 주소 정규화

입력은 `create_room` / `join_room` 의 `server` 인자 또는 환경 변수 `AGENT_CHAT_SERVER` 다. 결과는 접속 URL 하나와, 방을 구분하는 **서버 키**(정규화한 URL 문자열)다. PRD 의 "방은 서버 주소 + room_id 로 구분"에서 서버 주소가 이 서버 키다.

규칙(위에서부터 처음 맞는 것):

| 입력 형태 | 예 | 결과 |
|---|---|---|
| 생략 또는 빈 값 | | `wss://agent-chat.tools.camp` |
| `ws://`, `wss://` 로 시작 | `ws://10.0.0.5:9000` | 그대로 |
| `http://`, `https://` 로 시작 | `https://chat.example.com` | `ws://`, `wss://` 로 바꾼다 → `wss://chat.example.com` |
| 스킴 없음, 호스트가 IP 또는 `localhost` | `203.0.113.5`, `[2001:db8::1]:9000` | `ws://`. 포트 생략 시 `8787` → `ws://203.0.113.5:8787` |
| 스킴 없음, 호스트 이름, 포트 생략 또는 `443` | `chat.example.com` | `wss://chat.example.com` |
| 스킴 없음, 호스트 이름, 다른 포트 | `chat.example.com:8787` | `ws://chat.example.com:8787` |

공통:

- 호스트는 소문자로 바꾼다. 기본 포트(`ws` 80, `wss` 443)는 지운다. 끝의 `/` 는 지운다.
- IPv6 주소는 **입력에서도** 대괄호로 적는다(`[2001:db8::1]`, `[::1]:9000`). 결과에도 대괄호가 남는다. 대괄호 없는 IPv6 는 오류다. 주소와 포트를 가를 수 없기 때문이다(`::1:8787` 은 그대로도 올바른 IPv6 주소다). 추측해서 감싸지 않고, 오류 문구로 대괄호 표기를 알려 준다.
- 경로는 있으면 유지한다. 쿼리, 조각(`#`), 사용자 정보(`user@`)가 있으면 오류다.
- 다른 스킴과 빈 호스트는 오류다. 오류 코드는 `INVALID_ARGUMENT`.
- 근거: IP 주소에는 보통 유효한 TLS 인증서가 없으므로 평문 `ws` 와 자체 호스팅 기본 포트를 고른다. 호스트 이름만 주면 TLS 종단 뒤에 있다고 본다 **[제안]**. 모호하면 스킴을 직접 쓰게 한다.
- **주의**: `ws://` 는 방 ID 와 SDP 가 평문으로 지나간다. 경로 위의 공격자가 연결 정보를 바꿔 끼어들 수 있다. 신뢰하는 망이나 시험용으로만 쓴다([deployment.md](deployment.md#32-tls-종단)).
- **IP 지정은 서버 선택일 뿐이다.** 어떤 주소를 주든 채팅은 DataChannel 로만 간다.

## 7. ICE 서버 설정 검증

- 입력: 환경 변수 `AGENT_CHAT_ICE_SERVERS`. 쉼표로 구분한 URL 목록. 기본값 `stun:stun.l.google.com:19302` **[제안, A-OPS-1]**. `none` 이면 STUN 없이 host 후보만 쓴다.
- 허용: `stun:` 으로 시작하는 URL 만. 뒤에 호스트가 오고, 포트는 있어도 되고 없어도 된다(없으면 3478). IPv6 호스트는 대괄호로 적는다.
- **거절**: `turn:`, `turns:`, `stuns:`, 그 밖의 모든 스킴. 하나라도 있으면 **입장하지 않고** `ICE_CONFIG_REJECTED` 오류를 돌려준다. 일부만 걸러 쓰지 않는다. 기본값으로 바꿔 쓰지도 않는다.
- **`stuns:` 를 받지 않는 이유.** 고정한 `node-datachannel` 0.33.6 은 `stuns:` URL 에 예외를 던진다(`Unknown ICE server protocol: stuns`). 호스트와 포트만 객체로 넘기면 받지만, 그 형태에는 TLS 를 고르는 칸이 없어 평문 STUN 으로 바뀐다 **[실측. [W0 이력](../../tests/test-history/2026-11-15-w0-contracts.md)의 W0-36]**. 사용자가 고른 설정을 조용히 다른 것으로 바꾸지 않으려고 거절한다. 라이브러리가 지원하게 되면 다시 연다.
- **검증을 통과한 값의 모양.** 항목마다 `{url, hostname, port}` 다. `mesh` 는 라이브러리에 `{hostname, port}` 객체로 넘긴다. `url` 문자열을 넘기지 않는다. 같은 라이브러리가 대괄호가 든 IPv6 URL(`stun:[2001:db8::1]:3478`)에도 예외를 던지기 때문이다 **[실측 W0-36]**. `hostname` 은 대괄호 없는 소문자 호스트, `port` 는 URL 에 없었으면 3478 이다.
- 검사 시점은 `create_room`·`join_room` 이다. MCP 프로세스의 시작을 실패시키지 않는다. 시작이 실패하면 에이전트가 이유를 볼 수 없다([architecture.md 5절](architecture.md#5-설정-항목과-기본값)).
- 서버가 ICE 설정을 내려주는 경로는 없다. 설정은 로컬에서만 온다.

relay 를 막는 세 겹:

| 겹 | 위치 | 근거 |
|---|---|---|
| 1. TURN URL 을 받지 않는다 | 설정 로더(`src/protocol/ice-config.ts`) | relay 후보는 TURN URL 을 줬을 때만 생겼다. 라이브러리에 relay 를 끄는 옵션은 없다 **[실측 PRE-RTC-11]**. **이것이 유일하게 확실한 수단이다** |
| 2. ` typ relay` 후보를 보내지도 받지도 않는다 | 클라이언트 mesh | 필터로 양쪽 각 1건이 차단됐다 **[실측 PRE-RTC-11]**. 필터만으로 완전하다는 보장은 없다 **[추론]** |
| 3. ` typ relay` 가 든 `signal` 을 전달하지 않는다 | 서버 | 수정된 클라이언트에 대한 보조 방어 **[제안]** |

연결 뒤 선택된 후보 쌍의 타입으로 relay 여부를 검사하지 않는다. TURN 경유 연결이 `srflx↔prflx` 로 보고된 적이 있어 믿을 수 없다 **[실측 PRE-RTC-11]**.
