## 2. 한눈에 보는 설계

- **채팅은 에이전트 사이의 WebRTC DataChannel 로만 간다.** 서버는 방 참가자 등록과 연결 정보 전달만 한다. TURN, 서버 중계, 다른 피어를 통한 채팅 중계는 없고, 그쪽으로 바꾸는 경로도 없다. STUN 은 주소 탐색에만 쓴다.
- **각 PC 의 MCP stdio 서버 프로세스 하나가 참가자 한 명이다.** 그 안에 시그널링 클라이언트, WebRTC mesh, 공유 상태 복제본, 수신함, 로컬 기록이 있다.
- **토폴로지는 full mesh 다.** 입장자는 기존 참가자 전원과 기한 안에 직접 연결해야 한다. 하나라도 안 되면 입장은 실패하고 오류를 돌려준다. 오류는 "상대가 답하지 않음"과 "직접 경로 없음"을 구분한다.
- **서버는 두 가지다.** 공용 서버는 AWS 서버리스(API Gateway WebSocket + Lambda + DynamoDB), 자체 호스팅 서버는 Node 프로세스(ws + 메모리). 규칙 코드는 한 곳에 있고 저장·전송만 다르다. 클라이언트는 둘을 구분하지 않는다.
- **시그널링은 순서가 바뀌고 사라질 수 있다고 전제한다.** 공용 서버에서 실제로 그랬다. 클라이언트가 입장 직후부터 시그널을 받고, 먼저 온 후보를 보관하고, 응답이 없으면 다시 보낸다.
- **시그널링 연결과 DataChannel 은 수명이 따로다.** 시그널링이 끊겨도(서버 재시작, 2시간 한도) 열린 채널과 채팅은 유지된다. 살아 있는 링크는 같은 이름의 새 연결 요청에 넘어가지 않는다.
- **테스트 상태는 참가자끼리 복제한다.** 목표, 역할, 제한, 주장, 검증 기록을 각자 갖고, 링크가 열릴 때와 지문이 다를 때 서로 맞춘다. 중단을 받은 참가자는 자기와 이어진 다른 참가자에게 바로 다시 맞춘다. 재입장자는 여기서 현재 목표와 역할 현황을 받는다.
- **자동 수신은 두 길이다.** 기본은 `wait_for_messages` 장시간 대기(모든 호스트). Claude Code 에서 채널이 실제로 통하는 것이 확인되면 채널 알림으로 바꾸고, 통하지 않게 되면 되돌아간다. poll 은 에이전트의 턴이 살아 있는 동안만 받는다. 이 한계를 숨기지 않는다.
- **교차 검증과 실행 통제는 tool 이 강제한다.** 자기 주장을 자기가 검증할 수 없고, 다른 참가자의 확인이 없으면 성공으로 세지 않는다. 중단·시간 제한·시나리오 수 제한에 걸리면 새 시나리오 시작이 거절된다. 방 하나에 테스트는 한 번이라 같은 방에서 제한을 다시 정할 수 없다.
- **방 참여는 각 PC 의 권한을 넓히지 않는다.** 권한 승인 전달 기능을 선언하지 않고, 받은 글로 무언가를 실행하는 tool 이 없고, 설치가 권한 설정을 바꾸지 않는다.

## 3. 핵심 결정과 근거

| # | 결정 | 근거 | 기각한 대안 | 비용과 위험 |
|---|---|---|---|---|
| D1 | Node.js(22 이상) + TypeScript 단일 npm 패키지. 진입점은 MCP 서버, 자체 호스팅 서버, Lambda 핸들러, 설치·점검 CLI | 세 실행 대상이 같은 와이어 스키마를 import 한다. 조사한 라이브러리가 모두 Node 용이다 | 서버와 클라이언트를 다른 패키지로 분리: 스키마 공유에 배포 절차가 하나 더 든다 | Lambda 번들에 클라이언트 코드가 섞이지 않게 진입점을 나눠 관리해야 한다. Lambda 는 `nodejs24.x` 에서 돈다(패키지 하한과 다르다) |
| D2 | WebRTC 는 `node-datachannel` 0.33.6 의 네이티브 API | 설치에 빌드가 없다. 연결 11~25ms. 연결 불가를 스스로 알린다(39.5초). 초과 전송이 예외로 드러난다 **[실측 PRE-RTC-02~08]** | `werift`: 연결 불가에 이벤트가 없고 기본값이 공개 STUN 으로 바뀐다. `@roamhq/wrtc`: 초과 전송 때 채널이 조용히 닫힌다. polyfill: `failed` 가 안 보이고 종료가 안 된다 **[실측]** | 네이티브 프리빌트에 의존한다. macOS arm64 외 플랫폼은 미실행. 라이선스 MPL-2.0 **[가정 A-LIC-1]** |
| D3 | MCP 프로세스 하나가 참가자 한 명. 상주 데몬 없음 | 구성 요소가 하나 줄고 설치·권한이 단순하다. 호스트 세션의 권한 범위 안에서만 돈다 | 상주 데몬 + 얇은 MCP: 세션이 끝나도 연결이 남지만, 프로세스 간 계약과 수명 관리가 생긴다 | 호스트 세션이 끝나면 방에서 나간다. 종료 유예가 약 500ms 다 **[문서, A-MCP-3]**. 모듈 경계는 나눠 두어 나중에 분리할 수 있다 |
| D4 | full mesh. offer 는 이름이 작은 쪽만. 큰 쪽은 `offer-request` 로 요청 | 동시에 offer 하면 열리지 않았다. 작은 ID 규칙으로 4피어 mesh 와 재입장이 됐다 **[실측 PRE-RTC-05, 09]** | 입장자가 항상 offer + 충돌 시 양보(perfect negotiation): 참조 프로젝트 방식이나 이 라이브러리에서 미실측 | `offer-request` 는 새로 더한 것이다 **[가정 A-RTC-2]**. 참가자 N명에 연결 N(N−1)/2개. 정원 8 |
| D5 | 입장은 "전원과 연결" 아니면 실패. **입장 뒤에는** 전원 연결을 목표로 계속 메우되 보장하지 않는다. 메워지지 않은 쌍은 "닿지 않음"으로 드러낸다 | PRD: 직접 연결에 실패하면 제한 시간 안에 오류. 연결되지 않은 참가자를 준비 완료로 두지 않는다. 입장 뒤의 부분 연결은 정상적으로 생긴다(시그널링이 끊긴 사이의 입장, 한 쌍의 망 장애) | 부분 입장 허용: 처음부터 일부만 이어진 방이 생긴다. 입장 뒤 끊긴 쌍 중 하나를 방에서 내보내기: 일시 장애에도 멀쩡한 참가자가 쫓겨나고, 누가 나갈지 정할 근거가 없다 | 응답 없는 참가자 한 명이 신규 입장을 막을 수 있다(최대 90초, [S14](architecture.md#s14-유령-참가자-공용-서버)). 부분 연결 상태에서는 그 쌍의 채팅이 가지 않는다. 공유 상태는 다른 링크의 재동기화로 맞춘다([S6](architecture.md#s6-시그널링-서버-재시작-또는-websocket-끊김)) |
| D6 | 서버 메시지는 `join`, `signal`, `ping`, `leave` 넷. **입장·퇴장 알림이 없다.** 참가자 목록은 `joined` 와 `pong` 으로 받는다 | 시그널링이 끊겨도 채널은 살아 있으므로 서버 연결 상태를 참가자 상태로 쓰면 틀린다. 알림이 없으면 공용 서버의 입장당 전송 수도 준다 | 서버가 입장·퇴장을 알림(조사 예제의 방식): 강제 종료를 수 ms 에 알 수 있으나, 유실되면 mesh 가 비고 복구 수단이 따로 필요하다 | 강제 종료 감지가 P2P 의 15초 판정에 달린다. 목록을 30초마다 받는 비용 |
| D7 | 시그널링 규칙은 `signaling-core` 한 곳. 저장(`RoomStore`)과 전송(`ConnectionSink`)만 다른 두 조립 | 두 서버가 같은 계약을 지켜야 한다. 규칙을 두 번 쓰면 어긋난다 | 서버별 구현: 빠르지만 계약이 갈라진다 | 규칙을 약한 쪽(상태 없음, 동시·역순 처리) 기준으로 써야 한다. 자체 호스팅에는 필요 이상으로 방어적이다 |
| D8 | 공용 서버는 API Gateway WebSocket + Lambda(`nodejs24.x`) + DynamoDB. 앱 수준 `ping`. 종료 코드에 의미를 두지 않음 | 사용자 결정: EC2 를 쓰지 않는다. 쓰는 만큼만 과금 | 상주 서버: 사용자 결정으로 제외 | 유휴 600초, 순서 뒤바뀜, 드문 유실, 스로틀 폐기, 콜드 스타트 약 1초를 설계가 흡수해야 한다 **[실측 PRE-AWS-05~10]**. 최대 2시간과 사용자 지정 도메인은 미실측. 남용 시 비용 상한은 스로틀이 어림으로만 정한다 |
| D9 | 자동 수신은 poll 로 시작하고, 채널 점검 토큰이 돌아오면 channel 로 바꾼다. 확인이 끊기면 poll 로 되돌아간다. permission relay 는 선언하지 않는다. **외부 실행기는 쓰지 않는다** | MCP 표준에는 서버가 호스트의 턴을 시작시키는 수단이 없다 **[문서]**. Claude Code 채널은 조건부이고 등록 실패를 서버가 알 수 없다 **[문서]**. 장시간 대기는 어느 호스트에서나 된다 | `codex queue`, `codex exec resume`, `claude -p --resume` 로 턴을 일으킴: 실행기가 권한 범위를 다시 정하게 된다. Stop hook: 호스트별 설정이 늘고 미확인 항목이 많다. poll 반복이 실제 호스트에서 유지되지 않으면 조건을 붙여 다시 검토한다([mcp-interface.md 7.3](mcp-interface.md#73-호스트별-조건-설치가-안내한다)) | poll 은 빈 대기마다 모델 턴을 쓴다. **에이전트가 턴을 끝내면 수신이 멈추고 다시 깨울 수 없다**(`listening` 으로 드러낸다). 실제 호스트의 동작은 미실행 **[A-MCP-1, 2, 4, 5]** |
| D10 | 공유 상태는 참가자가 복제한다. 추가 기록은 합집합, 키 기록은 논리 시각으로 last-writer-wins. 채팅은 넣지 않는다. 링크가 열릴 때 양방향으로 전부 보내고, **열린 링크에서 지문이 다르면 다시 맞춘다. 중단을 받은 참가자는 기다리지 않고 자기의 다른 링크에 바로 다시 맞춘다.** 재동기화는 멈추지 않고, 맞출 수 없는 차이에서만 간격을 늘린다. 상한은 로컬 쓰기에만 건다. 기한은 각자 잰 경과 시간으로 판정한다. 다른 참가자가 실어 준 경과 시간은 자기 값보다 클 때만 따른다 | 서버가 상태를 저장하지 않는다. 재입장자에게 목표·역할을 줘야 한다. 병합이 멱등이라 중복·역순에 강하다. 변경을 작성자의 링크로만 보내면, 작성자와 끊겼거나 작성자가 떠난 뒤의 참가자는 중단 요청을 받지 못한다 | 서버 저장: "서버는 주선만"에 어긋난다. 조정자 한 명이 상태 소유: 영구 지휘자를 만들지 말라는 요구에 어긋난다. 받은 변경을 다른 링크로 바로 넘기기: 새 전달 규칙과 중복 억제가 필요하다. 지문 비교와 중단의 즉시 교환은 이미 있는 스냅샷 교환을 다시 쓰는 것이다. 즉시 교환은 복제본마다 테스트당 한 번이라 중복 억제가 따로 필요 없다. 재동기화를 몇 번 실패하면 멈추기: 그 링크가 유일한 길일 때 중단이 닿지 않는다 | 스냅샷이 참가자 수만큼 중복된다. 스냅샷 안의 남의 기록은 위조를 막지 못한다(서명 없음). 모두 나가면 상태가 사라진다. 끊긴 쌍에게 중단은 링크 하나를 더 건너는 시간만큼(보통 1초 안), 그 밖의 기록은 약 10~35초 늦게 닿는다 **[추론, 미실측]**. 중단 때 참가자마다 스냅샷을 한 번씩 더 보낸다. 기록의 글자 필드가 다른 참가자의 복제본을 거쳐 간다(채팅은 아니다. [protocol.md 5.4](protocol.md#54-동기화-절차)). 한 PC 의 벽시계가 테스트 도중에 앞으로 바뀌면 그 경과 시간이 방 전체에 퍼져 테스트가 그만큼 일찍 끝난다 **[추론]**([protocol.md 5.5](protocol.md#55-파생-판정)) |
| D11 | 교차 검증과 실행 통제를 tool 에서 강제. **방 하나에 테스트는 한 번.** 중단 뒤에 쓴 주장은 성공·실패에 세지 않는다 | 지침 문구는 모델이 어길 수 있다. PRD: 행동한 에이전트의 보고만으로 성공 처리하지 않는다. 제한이 실제로 적용돼야 한다. 같은 방에서 다시 시작할 수 있으면 tool 두 번으로 제한이 풀린다 | 지침만: 검증할 수 없다. 다음 테스트가 남은 시간·시나리오 수를 물려받기: 예산 계산이 복제 상태에 더해진다 | Agent Chat 의 tool 만 통제한다. 다른 도구로 하는 행동은 못 막는다. 테스트를 다시 하려면 새 방에 모두 다시 들어와야 한다. 에이전트들이 스스로 새 방으로 옮기는 것은 호스트의 승인이 막는다([mcp-interface.md 4절](mcp-interface.md#4-강제-규칙)) |
| D12 | 서버에서는 등록된 연결이 이름을 가진다. 같은 프로세스의 재접속은 프로세스별 무작위 `key` 와 접속 순번으로 가린다. **P2P 에서는 살아 있는 링크가 이름을 지킨다.** 같은 이름의 새 연결 요청은 기존 링크의 생존 확인이 실패해야 받는다. 계정과 저장하는 비밀이 없다 | 재접속과 재시작을 막지 않는다. 소켓이 닫히면 서버 기록이 바로 지워지므로 **[실측 PRE-AWS-06]** 재접속하는 동안 서버의 이름은 비어 있다. 그 사이 같은 이름으로 들어온 프로세스가 살아 있는 참가자의 링크를 끊게 두면 안 된다 | 설치별 저장 비밀: 한 PC 의 두 세션이 서로 밀어낸다. 인증 없음: 누구나 남의 이름으로 인계한다. 서버가 이름을 한동안 붙잡아 두기: 서버에 타이머가 없고 유령 기록이 는다 | 방 ID 를 아는 사람은 누구나 들어온다. 떠난 참가자의 이름은 다른 사람이 쓸 수 있다. 시그널링이 끊긴 사이 이름을 차지한 프로세스가 나가지 않으면, **나중에 들어오는 참가자**는 그쪽과 이어진다. 시그널링 서버 운영자는 믿는다([6절](#6-범위-밖)) |
| D13 | 채팅은 직접 전송 + 수신 확인. 자동 재전송과 끊긴 동안의 보관이 없다. 다시 보내기는 `resend_of` 로 같은 ID. 보내는 속도에 상한이 있다 | 결과를 수신자별로 정직하게 알린다. 보관함은 순서·만료·중복 규칙이 따로 필요하다 | 끊긴 상대용 보관함과 자동 재전송 | 끊긴 동안의 글은 그 참가자에게 가지 않는다. 다시 보낼지는 에이전트가 정한다 |
| D14 | 대화·실행 기록과 진단 로그를 분리. 진단 로그에 본문·SDP·candidate·방 ID 원문을 남기지 않는다. 방 ID 원문은 서버 저장소와 보고서에도 두지 않는다. 서버 로그의 참가자 이름은 해시로 남긴다 | PRD 의 로컬 기록은 사용자 자료이고, 진단 로그는 공유될 수 있는 운영 자료다. 방 ID 는 유일한 접근 수단이다 | 한 파일에 기록 | 문제 분석 때 본문이 필요하면 기록 파일을 따로 봐야 한다 |
| D15 | 설치 진입점은 `installer/` 의 셸 스크립트다(`install.sh` 통합, `claude.sh`, `codex.sh`. `--install` 기본, `--uninstall`). 셸은 Node 를 찾아 의존성 없는 Node 스크립트 `scripts/install.mjs` 에 넘기기만 한다. 설치 논리는 `install.mjs` 와 `setup` 모듈 한 곳에 둔다 **[사용자 결정 2026-11-15]**. 저장소를 고정 위치에 두고 MCP 등록까지만 한다. 권한 설정은 건드리지 않는다. Channels 는 판정표로 가능/불가/불명을 보고한다. 연결 점검은 등록된 명령 그대로 한다 | 채널 지원은 비대화식으로 판정할 수 없다 **[실측 PRE-CH-03, 04]**. 권한을 넓히는 일은 사용자가 해야 한다. 등록이 절대 경로를 쓰므로 위치가 고정이어야 한다. 사람이 손으로 실행할 호스트별 설치·제거 명령을 사용자가 요구했다 | 설치가 허용 목록까지 추가: 방 참여가 권한을 넓히는 셈이 된다. 받은 자리에서 그대로 등록: 임시 폴더면 깨진다. **총괄 방향과의 관계.** 총괄이 정한 방향 1~8 을 뒤집은 결정은 없다. 방향에 없던 것을 더하거나 좁힌 곳은 다음이다.

- 조사 예제에 있던 서버의 입장·퇴장 알림을 뺐다(D6). 대신 `offer-request` 와 `pong` 의 목록을 넣었다.
- MCP SDK 를 "1.x" 가 아니라 1.32.2 로 정확히 고정했다. 이후의 1.x 가 새 revision 을 지원하면 채널 등록이 막히기 때문이다.
- last-writer-wins 의 순서를 벽시계가 아니라 논리 시각으로 정했다. 시간 제한은 벽시계 비교가 아니라 경과 시간으로 잰다(D10).
- 방향 3 의 "응답 없음은 앱 타이머로 실패 처리"에 시도 안의 재전송을 더했다(D17). 실측한 유실 때문이다.
- 방향 4 의 "새 연결이 열리면 스냅샷 전달"에 "열린 링크에서 지문이 다르면 다시 전달"과 "중단을 받으면 다른 링크에 바로 다시 전달"을 더했다(D10). 작성자와 끊겼거나 작성자가 떠난 뒤에도 중단 요청이 닿아야 하기 때문이다.
- 방향 5 에 channel 에서 poll 로 되돌아가는 길을 더했다(D9).
- 방향 6 에 "방 하나에 테스트는 한 번"을 더했다(D11).
- 이름 인계를 위해 `key` 와 접속 순번을, 이름 보호를 위해 교체 확인을 넣었다(D12).
- 방향 1 의 Node 22 이상은 패키지 하한이다. Lambda 런타임은 실측한 `nodejs24.x` 로 정했다(D8).

## 5. 미확인 가정 목록

틀리면 설계가 바뀌는 것들이다. 질문·통과 기준·환경·선행 관계는 [verification-plan.md 2절](verification-plan.md#2-먼저-확인할-외부-가정)에 있다.

**확인할 수 없어 미실행으로 남는 것**

- A-RTC-1: 서로 다른 PC·NAT 사이의 STUN 직접 연결. 이 PC 한 대로는 확인할 수 없다.

**사람이 있어야 확인되는 것**

- A-MCP-1: 실제 Claude Code 세션에서 채널이 등록되고 유휴 세션을 깨운다.
- A-MCP-2: 채널 사건이 tool 경계에서 보이는지, 턴 끝에서만 보이는지.
- A-MCP-4, A-MCP-5: Claude Code 와 Codex 에서 장시간 대기 반복이 유지된다. **틀리면 그 호스트의 자동 수신은 "턴이 살아 있는 동안만"이다.** 헤드리스 실행(`claude -p`, `codex exec`)에서는 30분 동안 유지됐다([이력](../../tests/test-history/2026-11-16-final-sessions.md)). 대화형 세션은 미실행이다.
- A-MCP-7, A-MCP-8, A-MCP-9: 등록·승인 프롬프트의 실제 모습과 tool 별 허용, 채널 본문의 태그 처리, tool 결과의 크기 한도.

**구현 중에 이 PC 에서 확인하는 것**

- A-RTC-2: `offer-request` 흐름, 후보 묶음, 두 큐, 시그널 재전송.
- A-RTC-3: 교체 확인과 열린 링크의 교체.
- A-RTC-4: 8 피어 mesh. A-RTC-5: SDP 와 후보 묶음의 크기. A-RTC-6: 종료 예산 안의 `bye`.
- A-MCP-3: 호스트의 종료 신호 순서. A-MCP-6: 채널 capability 가 다른 호스트에 무해한가.
- A-MCP-10: 설치 전후에 비교하는 권한 관련 키의 목록이 이 PC 의 호스트 버전과 맞는가. 실제 설치 검증(`V-S1`) 전에 확인한다.

**AWS**

- 탐색 스택에서 본 것: 유휴 600초, 크기 한도, `$connect` 동작, 소켓이 닫힐 때의 종료 통지와 410, 순서 뒤바뀜과 유실, 스로틀 때의 프레임, `$default` 라우팅, `nodejs24.x` 와 내장 SDK(A-AWS-2, 7, 9, 10 과 A-AWS-1, 3, 6, 13 의 일부).
- **재지 못한 것**: 최대 2시간(A-AWS-1), 망 단절 때의 종료 통지(A-AWS-3), 사용자 지정 도메인과 그때의 연결 관리 API 주소(A-AWS-4, 8), 서버가 닫을 때의 종료 코드(A-AWS-5), `$default` 예외 때의 프레임(A-AWS-6), 스로틀 범위(A-AWS-11), 단가(A-AWS-12), `GetConnection`(A-AWS-13), 읽은 수로 하는 정원 판정(A-AWS-14).

**그 밖**

- A-OPS-1: 공개 STUN 을 기본값으로 써도 되는가. A-TIME-1: 참가 PC 의 시계 차이(표시에만 영향). A-LIC-1: MPL-2.0.

**확인이 필요한 입력**

- `V-I5`(자율 협업)에 쓸 테스트 대상 서비스. 이 저장소에는 없다.
- `V-I1`(GitHub 에서 받아 설치)에는 저장소 푸시가 필요하다. 푸시는 사용자 지시가 있어야 한다.

## 6. 범위 밖

만들지 않는 것과, 알고 있지만 다루지 않는 것이다.

| 항목 | 이유 |
|---|---|
| TURN, 서버 중계, 피어를 통한 채팅 중계. 직접 연결 실패 때의 대체 경로 | PRD 와 사용자 결정 |
| EC2 등 상주 인프라로 공용 서버 운영 | 사용자 결정 |
| 브라우저·데스크톱 조작, 영상·음성 품질 측정 | PRD: 각 에이전트의 별도 도구가 한다 |
| 계정, 로그인, 방 비밀번호 | PRD 에 없다. 방 ID 가 유일한 접근 수단이다. 직접 정한 짧은 ID 는 추측될 수 있다고 알리고, 없는 방 입장의 반복만 늦춘다 |
| 프로토콜을 따르지 않는 참가자에 대한 방어(기록 서명, 종단 간 추가 암호화) | 참가자는 방 ID 를 공유한 협력 관계라고 가정한다. 전송 구간은 DTLS 가 암호화한다 |
| 시그널링 서버 운영자에 대한 방어 | 서버를 믿는다. 서버는 이름을 붙이고 연결 정보를 전달하므로, 마음먹으면 둘 다 바꿀 수 있다. 믿을 수 없으면 자체 호스팅 서버를 쓴다 |
| 참가자와 서버에게 IP 주소 숨기기 | 직접 연결의 성질이다. 방에 들어가면 다른 참가자와 서버가 이 PC 의 IP 를 본다(내부망 주소 포함). 저장소 README 에 적는다 |
| 늦게 들어온 참가자에게 지난 채팅 전달 | PRD 는 목표와 역할 현황만 요구한다 |
| 한 프로세스가 여러 방에 동시에 참가 | PRD 에 없다 |
| 한 방에서 테스트를 여러 번 | D11. 새 테스트는 새 방에서 한다 |
| 끊긴 참가자를 위한 메시지 보관과 자동 재전송 | D13 |
| 외부 실행기로 에이전트를 깨우기 | D9 |
| 방과 테스트 상태의 서버 저장, 영구 보존 | 서버는 주선만 한다. 모두 나가면 로컬 기록만 남는다 |
| 자체 호스팅 서버의 다중 인스턴스, 컨테이너 이미지 | 상태가 메모리에 있다. 요구가 없다 |
| 다른 에이전트 호스트(Claude Code, Codex 외)용 설치 자동화 | MCP 서버는 표준 stdio 라 수동 등록은 된다. 자동화와 검증은 하지 않는다 |
| Windows·Linux 검증, 서로 다른 PC 4대 검증, 실제 NAT 검증 | 검증 환경이 이 PC 한 대다. **미실행**으로 남긴다 |

## 7. 문서 배치와 검토 상태

- **배치.** 산출물 배치 가이드의 날짜 폴더와 고정 구조(`system-design-to-be.md`, `navigation.md`, `screen-layout.md`, `details/…`)를 쓰지 않았다. 이 작업은 산출물 목록(이 폴더의 일곱 문서)이 따로 정해져 있다. 가이드에서 따른 것은 상대 경로 링크, 작성 PC 에서만 유효한 경로를 남기지 않는 것, 검토를 테스트 이력에 남기는 것이다.
- **화면.** 이 제품에는 화면이 없다. 에이전트가 MCP tool 로 쓰고, 사람은 에이전트와 대화한다. 그래서 화면 목록, 화면 이동 문서, 화면 HTML 은 0개다.
- **그림.** 구조와 의존은 Mermaid 로 그렸다. 흐름은 그림 대신 번호 단계로 적었다([architecture.md 7절](architecture.md#7-주요-시나리오-흐름)). 전용 표기(jobflow, state)의 그림은 만들지 않았다. Mermaid 는 렌더러로 확인하지 않았다(정적 검토).
- **검토.** 구현 전에 설계 문서의 독립 검토를 세 번 거쳐 고쳤다([설계 검토 이력](../../tests/test-history/2026-11-15-design-review.md)). 구현 뒤에는 코드와 문서를 함께 보는 독립 검토를 세 번 받아 고쳤다([1차](../../tests/test-history/2026-11-16-review-r1.md), [2차](../../tests/test-history/2026-11-16-review-r2.md), [3차](../../tests/test-history/2026-11-16-review-r3.md). 3차의 필수 지적 0건). 그 뒤에 고친 문서(마감의 문서 대조)는 작성자 대조만 했다.
- **설치 진입점 보정.** 2026-11-15 사용자 결정으로 설치 진입점을 `installer/` 의 셸 스크립트로 바꿨다(D15, [architecture.md 3.13](architecture.md#313-setup)). 권한 경계, 설치가 쓰는 곳, 전후 비교 목록, Channels 판정표, `doctor` 점검표는 그대로다. 이 보정의 독립 검토는 아직 없다.
- **API Gateway 값.** 일회용 탐색 스택으로 잰 값을 반영했다([AWS 실측 이력](../../tests/test-history/2026-11-15-aws-apigw-websocket-probe.md)). 재지 못한 항목은 [5절](#5-미확인-가정-목록)에 있고 제품 배포 때 확인한다.

## 8. 용어

| 용어 | 뜻 |
|---|---|
| 참가자(peer) | 방에 들어온 에이전트 하나. MCP 프로세스 하나 |
| 호스트 | MCP 서버를 띄우는 에이전트 프로그램(Claude Code, Codex 등) |
| 시그널링 | WebRTC 연결을 맺는 데 필요한 정보(SDP, candidate)를 서버를 거쳐 주고받는 일 |
| 링크 | 두 참가자 사이의 열린 DataChannel |
| 시도 | 링크를 열려는 한 번의 연결 과정. `cid` 로 구분한다 |
| 후보 묶음 | 연결 후보 여러 개를 담은 `candidate` 메시지 하나 |
| 대기 큐 | `offer` 보다 먼저 도착한 후보를 `offer` 가 올 때까지 두는 곳 |
| 접속 순번 | 프로세스가 시그널링에 새로 접속할 때마다 올리는 번호(`join.seq`). 옛 연결과 새 연결을 가린다 |
| 교체 확인 | 열린 링크가 있는 참가자 이름으로 새 연결 요청이 왔을 때, 기존 링크가 살아 있는지 먼저 확인하는 일 |
| mesh 보정 | 서버가 준 참가자 목록과 열린 링크를 비교해 빠진 연결을 메우는 일 |
| 닿지 않음 | 방에 있는 참가자와 직접 연결을 거듭 열지 못한 상태. 그 참가자와는 채팅이 오가지 않는다 |
| 복제본 | 한 참가자가 가진 공유 상태 기록의 사본 |
| 지문 | 복제본의 기록 식별자들로 만든 짧은 해시. 두 복제본이 같은지 비교한다 |
| 스냅샷 교환 | 한 링크에서 한쪽이 가진 기록을 모두 보내고 상대가 자기 것으로 한 번 답하는 일 |
| 재동기화 | 이미 열린 링크에서 스냅샷 교환을 다시 하는 일. 지문이 다를 때, 그리고 중단을 받았을 때 한다 |
| 진전 없음 | 스냅샷 교환을 마친 직후에도 두 복제본의 지문이 다른 상태. 다시 해도 없어지지 않는 차이라는 뜻이다 |
| 경과 시간 | 테스트가 시작된 뒤 흐른 시간을 각 참가자가 자기 시계로 잰 값. 시간 제한 판정에 쓴다. 다른 참가자가 실어 준 값은 자기 값보다 클 때만 따른다 |
| 중단 뒤 기록 | 테스트가 중단된 뒤에 쓴 주장. 보고서에 따로 싣고 성공·실패에 세지 않는다 |
| 사건 | 수신함이 에이전트에게 전하는 한 건(채팅, 참가자 변화, 테스트 변화 등) |
| 전달 모드 | 사건을 에이전트에게 주는 길. poll 또는 channel |
